## 1. Core model in one paragraph (evidence-backed)
Linnworks has ONE bundle concept, the **composite item**: a "virtual" parent SKU plus child SKUs with quantities, one level deep. Stock lives on children; parent availability is computed. When an order line maps (via channel SKU linking) to a composite parent, Linnworks keeps the parent line (with the price) and adds child rows with sold value 0. Gifts have NO dedicated concept: a free item is an ordinary item line, typically added by the Rules Engine action "Add items to an order" with a 100% discount. Gift wrap is a separate "service" line. The Channel Integration API (how third-party connectors deliver orders) has no bundle, grouping or gift field at all - a connector sends flat lines (SKU, price, qty, % discount, IsService); all bundle semantics come from Linnworks' own SKU linking to composites.

Key quotes:
- docs:inventory-composite-items - "The composite item consists of a parent SKU - a "virtual item" that represents a group of individual items and single child items that create the group." / "It can be a set of different items or a pack of the same."
- docs:inventory-composite-items - "Composites cannot contain another composite." / "The parent SKU must always be set to *Not Tracked* to calculate its stock based on the available stock of the child SKUs."
- docs:inventory-composite-items - "If an order contains a composite SKU, it will list both the composite SKU and the child items of the composite. In addition to this, the child items will have a sold value of zero. ... Linnworks cannot estimate what ratio to split the composite retail price."
- docs:rules-engine-actions - "Many businesses include free gifts, samples or promotional items based on order value, product type, or customer segment." / "**Discount:** Optionally apply a percentage discount to the item. For example, enter 100% for a completely free gift."
- api:channel-integration-endpoint-orders, `OrderItem` fields: TaxCostInclusive, UseChannelTax, IsService, OrderLineNumber, SKU, PricePerUnit, Qty, TaxRate, LinePercentDiscount, ItemTitle, Options, CancelStatus (no parent/group/gift field). Same in `LinnworksNetSDK/Linnworks/Examples/SampleChannel/dotnet/SampleChannel/Models/Order/OrderItem.cs`.

## 3. Integration normalisation (how Linnworks handles per-channel encoding)
- **Catalogue linking is the normaliser.** Every channel line carries a channel SKU; *Inventory Mapping* / *Stock Item Linking* import links it to a Linnworks SKU, which may be a composite parent. The bundle structure therefore comes from Linnworks' catalogue, never from the channel payload. (docs:product-details-channel-sku "You can have different Channel SKUs for one item across different marketplaces, but you will still be able to link them all to one Linnworks SKU.")
- **Third-party connector contract is flat.** The Channel Integration `OrderItem` has no parent, group, gift or promotion fields; only IsService, LinePercentDiscount and free `Options`/order `ExtendedProperties`. A connector that receives parent+children from its platform must decide itself what to send. (api:channel-integration-endpoint-orders)
- **Connector-declared capabilities are UI toggles, not semantics.** Manifest params (`IsListingSupported`, `AllowRefundOnCancel`, batch sizes) and `GlobalConfigSettings` (`IsRefundsVisible`, `IsCancellationsVisible`, `IsShippingMappingVisible`, `IsInventoryMappingVisible`, `IsPosOrderProcessingVisible`, `IsMultilocationEnabled`, `PriceTags`) plus arbitrary `ConfigItem`s (`ValueType` STRING/INT/DOUBLE/BOOLEAN/PASSWORD/LIST/URL/BUTTON, `HidesHeaderAttribute`). Nothing describes line structure. (`SampleChannel/Manifest.txt`; api:channel-integration-endpoint-user-config; `SampleChannel/.../Models/User/ConfigItem.cs`)
- **Per-integration ad-hoc switches for built-in channels**: Magento 2 *Ignore bundle child/parent items* and *Coupon control*; Shopify *Save discount information*; Amazon MCF *Send Composite Parent Items to Amazon* (outbound direction); *Use Channel Tax* per channel.
- **Outbound despatch is per channel line**, so the composite expansion is invisible to the channel (`DespatchItem.SKU` = "Channel SKU from the order item").
- **Unlinked lines** block processing if "Only process an order if all items are linked" is on; Magento coupon control exists precisely to stop coupon lines being unlinked items (docs:magento-2-settings).

## 4. UX patterns worth copying
1. **Two document tables, by design**: pick list *Order items* vs *Order items granular (No Composite Parents)*, packing list *Orders (No Composite Parents)* - operator chooses per template whether parents or components print.
2. **Scan the parent = scan all children** setting, plus mandatory child scans when the setting is on; mobile *Group composites* for multipacks (scan once for a pack of 10).
3. **Reverse lookup report**: "which bundles contain this component" (*Composite Export* with *Childsku*).
4. **Rule-added free item as a normal line with list price + 100% discount**, configured in the same Rules Engine as everything else, with explicit split/merge/resend guard conditions and a documented warning about duplicates.
5. **Rule conditions that understand bundles**: *Has composites*, *Item count (no children)*, *Line count (no parents)* - counts that do not double-count.
6. **Order-row filter/badge** *Has composites* in Open Orders quick filters.

## 5. Anti-patterns
1. **Children value 0, then equal split for customs labels** - a component's value on the label can exceed its real price; no VAT-aware split (conflicts with B-14 rules).
2. **Bundle meaning lives only in catalogue linking**; channel payload cannot say "these 3 lines are one bundle", so a children-only channel (B-06) and per-plugin parent/child conventions need ad-hoc per-channel switches (Magento) that "must exactly match".
3. **Composite orders cannot be split** across orders - no partial back-order of a bundle.
4. **Gift is indistinguishable from goods** after it is added (no flag, no reason, no report, no out-of-stock fallback); duplicates on resend/split are left to the operator to prevent with extra conditions.
5. **Two unrelated kit models** (Composite vs Product Assembly app) that explicitly do not work together; manual untracked parent level is stale until a child moves.

## 6. New use cases (with source)
- **N-1 Rule idempotence across order lifecycle**: an auto-added gift/service must not be added again on merge, split child or resend. Source: docs:adding-items-services-merged-split-resend-orders "Without them, you risk adding the same item or service multiple times by mistake."
- **N-2 Outbound bundle to a 3PL/fulfilment channel**: choose whether to send the parent or the children to an external fulfiller (Amazon MCF). Source: docs:amazon-multi-channel-fulfillment "When , Linnworks will send the composite **parent** item to Amazon ... If the setting is , composite **child** items will be sent".
- **N-3 Per-component serial/compliance codes on a bundle**: which child's IMEI/Transparency code is reported to the channel. Source: docs:back-market-rules "you must use an extended property called *SerialNumberSKU*. This property tells Linnworks which child item's IMEI code to submit"; docs:amazon-transparency-codes "Composite **parent** items cannot be scanned."
- **N-4 Inbound purchasing/stock-in of a bundle explodes to components** (PO and book-in of a parent add children). Source: help 7000024253 "It is not possible to add a composite parent item to a purchase order because it is actually a virtual item."; docs:inventory-stock-in "allows booking all child items in one go".
- **N-5 Bundle weight/dimensions fallback** (parent value if set, else sum of children; never both). Source: docs:inventory-composite-items "Linnworks never sums or doubles parent and child SKUs".
- **N-6 Coupon line as unlinked item blocking processing** - a discount/coupon arriving as a line must be classified so it does not stall the order. Source: docs:magento-2-settings "Coupon control".
