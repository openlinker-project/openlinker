# R4 / code B - order-line identity and line money, traced

Read-only trace of the repository at the worktree HEAD (`9e35aec9d`). Every claim cites `file:line`
with a verbatim quote. Scenario under test: **one channel line (id `L`) is expanded into N component
lines that all keep `id = L`** (the naive way to store a bundle's components in `orderSnapshot.items`).
A second scenario is noted where relevant: **a gift arrives as its own channel line** (own id, price 0).

## 0. Where the line id comes from

- `libs/core/src/orders/domain/types/order.types.ts:254-259` - `export interface OrderItem { id: string; productId: string; variantId?: string; quantity: number; price: number;`
- `libs/core/src/orders/domain/types/incoming-order.types.ts:163-167` - `export interface IncomingOrderItem { /** Item identifier (adapter-provided). */ id: string;`
- Ingestion copies it 1:1, one incoming line -> one OrderItem. `libs/core/src/orders/application/services/order-ingestion.service.ts:584-589`: `resolvedItems.push({ id: item.id, productId: result.internalProductId, variantId: result.internalVariantId, quantity: item.quantity, price: item.price,`. There is no expansion seam anywhere on this path: each `productRef` resolves to exactly one `(productId, variantId)`.
- The entity documents the id as the platform-wide join key. `libs/core/src/orders/domain/entities/order-record.entity.ts:818-821`: "`id` is the address the rest of the platform already keys on: it is the value `reservations.orderLineId`, `shipment_lines.lineId`, `FulfillmentWorkLine.orderLineId` and `ReturnLine.resolvedOrderLineId` all hold - un-FK-able by construction, because `order_records` has no lines table."
- Source ids are per channel line: Allegro `id: lineItem.id` (`libs/integrations/allegro/src/infrastructure/adapters/allegro-order-source.adapter.ts:1006`), PrestaShop `id_order_detail` (`libs/integrations/prestashop/src/infrastructure/mappers/prestashop-order.mapper.ts:78`, and its docblock at :163-166: "a content-derived key such as `${product_id}:${product_attribute_id}` is not unique within one order (customisation, free-gift lines, warehouse splits ...)"), WooCommerce `id: String(item.id)` (`woocommerce-order-source.adapter.ts:363`), Shoper `id: String(line.id)` (`shoper-incoming-order.mapper.ts:294`), Erli `id: String(item.id)` (`erli-order.mapper.ts:204`).

So a gift that the channel sends as its OWN line (PrestaShop free-gift row, WooCommerce 0-priced line) already has a distinct id and is safe on every key below. The risk is entirely in expanding one channel line into components that share its id.

## 2. Hypotheses

**H1. Sale-decrement key `sale:{owner}:{workId}:{orderLineId}` collides - PARTLY TRUE, masked.**
`inventory-sale-decrement.types.ts:130` `return \`sale:${ownerConnectionId}:${workId}:${orderLineId}\`;` with `UQ_inventory_sale_decrements_key ON ("idempotencyKey")` (migration 1909:66-67). The input lines come from WORK lines (handler :93 `for (const line of work.lines)`), and a work cannot hold two lines with the same L (`UQ_fulfillment_work_lines_work_order_line`), so today the key cannot collide - because routing already MERGED the components (#8). The real defect is earlier and worse: the merged work line carries the last component's variant (routing-commit :201-203) and the decrement uses the last component's product (`itemsById` handler :90). If a design keeps components as separate work lines under L, the key DOES collide and the second component is treated as an already-settled replay.

**H2. closeForOrder closes sibling holds - TRUE.**
`reservation.repository.ts:245` `...(orderLineIds !== undefined ? { orderLineId: In([...orderLineIds]) } : {})` then `reservation.service.ts:322-327` loops `releaseHeld` on every returned row. Caller: `inventory-sale-decrement.service.ts:618-620` `orderLineIds: [orderLineId]`. The code itself admits it: `master-absorbed-reservation.service.ts:116-118` "closing it by line would also close the hold that must stay." Compounded by `readClosedLineIds` (#2): siblings are never re-held afterwards.

**H3. Routing conservation keyed by order line - TRUE.**
`routing.types.ts:276` `expected.set(line.orderLineId, (expected.get(line.orderLineId) ?? 0) + line.quantity);` and :283-285 sum plan rows by `orderLineId`. Per-component misallocation passes. Then routing-commit :524-545 merges by `orderLineId` and keeps one variant.

**H4. Unique indexes on fulfillment_work_lines (workId, orderLineId) and shipment_lines (shipmentId, orderId, lineId) - TRUE (both).**
`1864000000000-create-fulfillment-works.ts:159-160` `CREATE UNIQUE INDEX ... "UQ_fulfillment_work_lines_work_order_line" ON "fulfillment_work_lines" ("fulfillmentWorkId", "orderLineId")`; `1874000000000-create-shipment-lines.ts:116-117` `CREATE UNIQUE INDEX ... "UQ_shipment_lines_shipment_order_line" ON "shipment_lines" ("shipmentId", "orderId", "lineId")`. Neither was altered by a later migration (grep of index names). Failure modes differ: work lines are pre-merged (silent wrong variant) or raise `DuplicateFulfillmentWorkLineError`; shipment lines are `.orIgnore()` (silent drop).

**H5. Remainders land on 0-priced lines - TRUE in two allocators, FALSE in two.**
- `reconcileDiscountRounding` (`sales-documents/domain/types/discount-rounding.types.ts:65-67`, used by invoice mapper :145 and fiscal mapper :134): `const single = goodsIndexes.find((index) => result[index].quantity === 1 && toMinor(result[index].unitPriceGross) + gapMinor > 0);` - FIRST quantity-1 goods line, and a 0-priced gift passes when `gapMinor > 0` (0 + gap > 0). A free gift listed before the paid line receives the rounding cent. **Breaks** (only on orders with `discountTotal > 0` and a positive gap).
- `spreadDeliveryAcrossLines` (`delivery-line.types.ts:579-587`): remainder goes to a quantity-1 line, choosing `target === -1 || grosses[index] > grosses[target]` - the first qty-1 line if no larger one exists. If the gift is the ONLY quantity-1 line (paid lines have qty > 1), the gift gets the remainder and stops being free. **Breaks** (spread mode only). A 0-priced line's proportional share is 0 (`Math.max(0, unitPriceGross * quantity)`).
- `distributeOrderDiscount` (`order-discount-split.types.ts:83-89`): remainder to `largest` by `minorTotals` - **safe** unless every line is 0.
- `splitShippingAcrossRates` (`shipping-tax-split.types.ts:126-163`): zero-gross rate gets share 0, remainder to largest part, zero parts filtered - **safe**.

Money-loss summary:
1. No adapter emits a per-line discount; Allegro and PrestaShop expose only an order-level gap (`discountTotal`).
2. Allegro and Erli never set `unitPriceGross`; analytics drops it for every source.
3. No list/original price anywhere (Allegro `originalPrice`, PS `original_product_price`, WC `subtotal`).
4. No parent/child or component-of marker in any wire type or neutral type (WC `meta_data` unread).
5. `reconcileDiscountRounding` and `spreadDeliveryAcrossLines` can move cents onto a 0-priced gift.
6. Fiscal lines carry no `orderLineId`, so any per-component reconciliation must happen upstream.
