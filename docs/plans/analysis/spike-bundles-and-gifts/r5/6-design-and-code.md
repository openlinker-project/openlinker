### R2-C claim refuted: master-absorbed consume does not oversell components today
R2-C: "consumes component holds although Woo/Shoper lowered only the BUNDLE row -> OVERSELL". Current code keeps them: `order-sync.service.ts:515` `const productIds = order.items.map((item) => item.productId);` is passed to `consumeAbsorbedHolds`, which loads positions only for those ids (`master-absorbed-reservation.service.ts:106-107`), and `classify` returns `'unknown-position'` for a hold whose position was not loaded (`:207-208`), which is kept. A component hold sits on a component position, so it is kept until dispatch (under-sell). Safe **by accident**: the explosion PR will be tempted to pass component product ids "to be complete", and THAT creates the oversell. Needs a pinning spec, not a capability.

## 2. New findings (not in the register)

- **N-1 T9 never fires for an order that was ever `awaiting_mapping`.** `order-ingestion.service.ts:480` persists the raw snapshot record (Step 2) before item resolution; a failed resolution throws at `:628`; on the retry `existing` (`:439`) is non-null, so `if (!existing) { notifyOrderReceived(...) }` (`:670-672`) is skipped forever. A gift rule (G-06) and the #3554 order-confirmed email silently never run for such orders. Gift SKUs are a plausible cause of `awaiting_mapping` (C-053). Code reading only; worth a spec.
- **N-2 the order-edit write path lives in `apps/api`**, not core: `apps/api/src/orders/application/services/order-edit.service.ts:181` `function orderEditLockKey`, `:532-533` lock. An `add-order-line` automation executor runs in the worker inside ingestion; it cannot call this service. The add-line writer must move into core (with its refusal rules and lock), which R2-C's "add an `addedLines` section" omits.
- **N-3 operator discount rewrites the paid price**: `order-discount.types.ts:216-221` sets `unitPriceGross` (and `price` when inclusive) to the after-discount figure. A reduction AMOUNT derived as `listUnitPriceGross - unitPriceGross` then mixes the channel's reduction with OL's own discount. Store the channel's reduction explicitly or derive from the channel snapshot only.
- **N-4 Allegro's composition is not resolvable to OL variants.** `productSet.products[].id` is a catalogue-product UUID (r2/phase1/1-allegro.md:32); OL maps offers, not catalogue cards, and `AllegroCheckoutForm.lineItems` does not type productSet at all (`allegro-api.types.ts:75-85`). An inline "composition" from Allegro is only usable as a check (number of products, multipack size), never as the authority.

## 3. Attacks on "data in optional line fields, limits in 2-4 guard-only capabilities"

1. **The proposal breaks its own rule.** DECLARATIONS lists `MasterBundleStockReader` (composition and stock mode = data, as a capability). R2-A proposed the opposite: `Product.composition?: ProductComposition | null` on the product, the three-state `Product.gpsr` precedent. Pick the field.
2. **The proposal merges two reports that disagree.** R2-A: `BundleListingSupportDeclarer` (declaration). R2-C: `BundleOfferComposer` (method that writes). A declaration with no write path describes nothing OL can do; drop it until the write exists.
3. **Field-only fails where absence is not safe: parent + children shapes.** An adapter that does not tag children (today's Shoper and WooCommerce mappers, or a Woo bundle plugin the adapter does not know) emits child lines that look exactly like separately bought items. OL recognises the parent by SKU and explodes it by definition, AND reserves, picks and decrements the children: double reservation and double pick. "Absent = no claim" is the dangerous default here. Needs either a per-connection operator setting (X-03) or a declaration saying "this source emits children as lines". The data.ts row "Reportery źródła (opcjonalnie) - pola trzystanowe wystarczą" is therefore wrong for this shape.
4. **`commercial.reduction` absent = "no reduction reported by the channel" is two-state.** It cannot tell "channel gave none" from "adapter does not read it" (Shoper `discount_perc`, PrestaShop `reduction_percent` are unread per r2/code/B:64-65). Make it three-state (`null` = checked, none), as `buyerTaxId` and `gpsr` are.
5. **`OrderCreateLineStockEffect` is unnecessary for the pilot**: the current code already keeps component holds (section 1, refuted claim), and the pilot is OMS-on. WooCommerce would answer `unknown` per line anyway (bundle-plugin stock settings are per product meta); only PrestaShop could answer, and it already answers `false` for packs.
6. **Guard-only hides misconfiguration.** An out-of-tree or older document adapter that lacks `LineAdjustmentRenderingDeclarer` falls back to "refuses everything", so the gift is folded or omitted from the receipt with nothing on the order. ADR-046's amendment requires a server read with `declared` and `resolvedVia`; each declaration therefore costs an endpoint plus a FE mirror script. Four declarations = four of each, a cost the "2-4" framing hides. For document adapters the better form is a REQUIRED method on `InvoicingPort` and `FiscalizationPort` (five in-tree adapters, all ours), probed only for out-of-tree plugins.
7. **The folding fallback is a document-content decision taken silently.** ADR-082's precedent puts that choice in operator config (`freeDelivery: 'omit' | 'show'`); the adapter declares only device limits (`ReceiptLineNameBudget`).
8. **`componentKey` touches at least 8 sites** (sale key, reversal key, edit-reversal key, handler productId, closed-line gate, hold close, routing input + assignment + commit map, work-line index, narrowForOrder) and one published port. Every miss is silent (non-decrement or early release).
9. **Snapshot stability.** Component keys derived from a definition must come from the frozen order snapshot. ADR-080's cost snapshot already admits "a ready -> awaiting_mapping -> ready round trip loses the snapshot". If the bundle snapshot is lost the same way and re-taken after a definition edit, new component keys orphan existing holds and works and the sale key changes, so a second decrement is possible.

## 4. ADR conflicts

- **ADR-063 (strong).** "OpenLinker never computes a rate". D3c "default to components when VAT rates differ" chooses between one rate for a composite supply and per-component rates: a tax treatment decided in core. Also ADR-063 §6 gate: a component without a rate would block a document whose channel reported one valid rate for the bundle (Allegro `tax.rate`) - a regression. The choice must be operator config per connection or a tax-adviser rule, never a core default.
- **ADR-082 (strong).** Decision 7: "A receipt never carries a zero line, since it registers what was paid." G-10 "list price + 100% line rebate" on receipts is a line that nets to zero. Context: a fiscal printer refuses a name whose rate goes up after it went down. D3c "bundle as one line" on a receipt gives the bundle name a rate that moves when the composition or a component rate changes; decision 9 checks one receipt only, not history.
- **ADR-014 (medium).** Decision 1 "Invariant, not capability... capability-absence would license silent catalog fallback". Same logic: absence of a rendering declaration must not license silently omitting a line from a fiscal document.
- **ADR-046 (medium).** Required-method-on-the-base-port was chosen where every adapter of the role must answer; guard-only optional is the weaker form and needs the `declared/resolvedVia` read.
- **ADR-026 (watch).** A neutral `reduction.reason` is fine; document rendering that BRANCHES on `gift` vs `promotion` (K-02: countries treat a free item differently) is a regime rule and must live in the adapter or operator config.
- **ADR-062 / FulfillmentRouterPort.** The `componentKey` design widens `RoutingInputLine` and must add a variant or line key to `RoutingAssignment` - a breaking change for any out-of-tree router.
- **#3542 invariant** ("the persisted `orderSnapshot` column is ALWAYS the channel original"): any design that materialises component lines must not write them into the snapshot.
- **ADR-002.** No conflict.

## 5. Strongest alternative: derived effective lines (expand in `toDomain`, like the edit overlay)

Mechanism:
1. New column `order_records.bundleSnapshot` (D3 B-10): frozen at first ready ingestion, first-write-wins, never rewritten, carried across delete-and-reinsert like `carryForwardLineCosts`.
2. A pure rule in `orders/domain` (`expandBundleLines`) applied once in `toDomain`, after `orderEdits` and the discount (ordering stated): the effective `Order` replaces each recognised bundle line with component lines whose ids are deterministic from the snapshot (`{lineId}~{index}`), quantity = per-bundle x ordered, in-set prices split with largest remainder (`distributeOrderDiscount` shape), and `partOf {channelLineId, bundleVariantId}`. `channelSnapshot` keeps the bundle line.
3. Everything that keys on `orderLineId` (reservations, closed-line gate, routing input and assignment, work lines, sale and reversal keys, hold close, bench, shipment lines) works unchanged, because each component IS its own order line. `FulfillmentRouterPort` does not change (an optional `bundleGroup` hint for cohesion is additive). D3f falls out of shipment-line quantity coverage.
4. Readers that must speak the channel's language opt in to `channelSnapshot`, as #3542 already forces: source amendment diff, destination mirror (a PrestaShop pack must get the pack SKU), channel writebacks with line ids (Allegro waybill), analytics `order_line_items` (already channel), return-line resolution (#3171 matches by SKU/offerId: match the channel line, then expand), refund ceiling.
5. Capabilities: one document declaration (device limits only: per-line rebate, zero line, zero rate group, minimum line value) as a required method on both document ports; gift and bundle rendering as operator config (`giftsOnDocuments`, bundle one-line vs components) in the ADR-082 shape. Line data as THREE-STATE fields. `Product.composition` three-state field for masters. Children-shape handling as a per-connection operator setting (X-03), not a source declaration. No `OrderCreateLineStockEffect`, no listing declaration in the pilot.

Cost and risk, honestly:

| | Proposal (`componentKey` threaded) | Alternative (derived effective lines) |
|---|---|---|
| Core change | 8+ sites, 2-3 migrations (work lines, reservation column, key compat), published router port change | 1 column, 1 pure rule in `toDomain`, audit of ~6 channel-language readers |
| Failure mode of a miss | Silent: non-decrement (replay), early hold release, wrong variant on a work line | Mostly loud: an OL-minted line id sent to a channel is refused. Silent risk: return-line resolution and refund ceiling reading effective lines |
| Known hazard class | New | Same class as #3542's effective-vs-channel split, already listed and audited |
| Existing in-flight orders | Key format migration/compat needed | No snapshot = no expansion = unchanged |
| Downsides | | Document "one line" mode must re-collapse components (pure, via `partOf`); an operator edit of a component id lands in `unmatchedLineEdits` and must be refused explicitly; ordering of edits, discount and expansion must be fixed and tested; effective totals must still equal channel totals (in-set split must be exact) |

I rate the alternative cheaper and lower-risk for the pilot, but it is unproven: no code was written and the reader audit (step 4) is the part most likely to be incomplete.

## 6. What survives
- Per-order facts as optional fields: **survives**, but as three-state fields (`null` = checked, none), including `reduction` and bundle membership.
- `LineAdjustmentRenderingDeclarer`: **survives**, narrowed to device limits; prefer a required method; the omit/show decision moves to operator config.
- `fulfilmentLineId`/`componentKey`: **survives as a need** (components need their own line identity); the alternative delivers it without threading.
- Collision catalogue: **survives** for sale/reversal keys, work-line index, hold close, routing; **add** the closed-line gate, the handler's `productId`, `RoutingAssignment` without a variant, and N-1; **remove** shipment lines; **downgrade** the master-absorbed oversell to "safe by accident, pin with a spec".
- `MasterBundleStockReader` as a capability, `OrderCreateLineStockEffect`, `BundleListingSupportDeclarer`, optional source reporters: **do not survive for the pilot**.
- "2-4 declarations" as a cost estimate: **refuted** - each guard-only declaration also needs a server read and a FE mirror (ADR-046 amendment).
