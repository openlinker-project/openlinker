# Phase 2 / Researcher 6 - Shopify admin as an operator-UX benchmark (bundles + gifts)

Research date: 2026-11-04. Sources: help.shopify.com, shopify.dev (API 2026-10 "latest"), changelog.shopify.com, community.shopify.com / community.shopify.dev, app store listings. Read-only; no store was opened, so every UI label is quoted from docs, not seen. Points marked (unverified) come from community threads, vendor blogs or my inference.

## 0. How Shopify models the problem (one paragraph)

Shopify is the *channel and the OMS at once*, so the question "what does a bundle look like on the order" is answered by the platform, not per app:
- **Definition**: a bundle is a normal product/variant whose variant carries `productVariantComponents` (component variant + quantity), set with `productVariantRelationshipBulkUpdate`; `ProductVariant.requiresComponents = true` means "cannot be sold without its components". Up to 30 components (fixed), 150 (dynamic), 2,000 units per component, 3 options / 100 variants, no nesting. Once an app assigns components, ONLY that app can manage them. https://shopify.dev/docs/apps/build/product-merchandising/bundles/add-variant-fixed-bundle , https://help.shopify.com/en/manual/products/bundles/shopify-bundles
- **Order shape**: CHILDREN ONLY, grouped. Each component is its own `LineItem` with its own SKU, price (allocated), tax lines, fulfillable quantity; each points to a `LineItemGroup {id, title, quantity, productId?, variantId?, variantSku?, customAttributes}` that represents the parent. There is no parent line. https://shopify.dev/docs/api/admin-graphql/latest/objects/LineItemGroup
- **Money**: "Discounts apply to the parent bundle first, then allocate to components by weighted price. Taxes calculate on individual components." Bundle price is allocated to components "using a weighted price algorithm" (formula not published). https://help.shopify.com/en/manual/products/bundles/shopify-bundles
- **Customised bundles / gifts / add-ons** go through the **Cart Transform Function** (`lineExpand`, `linesMerge`, `lineUpdate`) - "the only API that can alter a cart item's appearance ... or bundle items"; plus **nested cart lines** (parent/child, Aug 2025) for add-ons such as warranty or gift wrap. https://shopify.dev/docs/api/functions/latest/cart-transform , https://shopify.dev/docs/apps/build/product-merchandising/nested-cart-lines
- **Discounts**: every line has `originalUnitPriceSet` + `discountAllocations[]`, each allocation pointing to a `DiscountApplication` (automatic / code / manual / script). There is NO gift flag on a line - only `isGiftCard`. https://shopify.dev/docs/api/admin-graphql/latest/objects/LineItem

## 2. Integration normalisation (how Shopify standardises across apps/channels)

1. **One order shape for all bundle apps that use the native API**: component lines + `LineItemGroup` (title, qty, parent variant/SKU). Apps own the *definition* (components) and the *cart behaviour* (Cart Transform); the *order* is always platform-shaped. Downstream systems read one field (`lineItem.lineItemGroup`).
2. **Money lives only on fulfillable lines**; the group has no price. Bundle price/discounts are allocated to components by a platform algorithm, tax computed per component. This removes "price on parent or children" ambiguity (B-19) - for native bundles only.
3. **One discount model**: original price + allocations referencing an application record. Gifts are not a type; a "free gift" is just a 100% allocation from a BXGY/manual application.
4. **Capability declaration on the variant**: `requiresComponents` + `productVariantComponents` declare "this is a bundle" so channels (POS, Google, Shop) behave; ineligible stores/channels automatically unpublish fixed bundles. Channel support is a list (Online Store, Shop, POS, headless; Google fixed only); third-party marketplace connectors largely don't support it.
5. **Add-ons separate from bundles**: nested cart lines (deliverable add-on, "For:") vs bundle components ("Part of:"), same `line_item.groups` API, distinguished by `deliverable?`.
6. **Ownership/lock**: whoever created the components (app) or the order (app) is the only one allowed to change them - avoids conflicting writers but blocks the operator (no order edit on imported orders).

## 3. UX patterns worth copying
- Bundle stock = floor(min(component available / qty)) computed and shown automatically, with explicit rule text that untracked / continue-selling components are excluded.
- Order lines are always the physical components, with a light caption "Part of: {bundle}" (slip, emails, admin grouped view) - picking is by real SKU, the bundle is context.
- One neutral price model (list price + allocated discounts by named discount) for every channel and promo.
- Add-on vs component distinction (`deliverable?`) with two words: "For:" and "Part of:" - useful for gift wrap vs gift-in-bundle.
- Refund page lets the operator adjust the discount on a returned line in place (no separate edit flow).
- Bundle auto-goes Draft when its definition breaks (deleted component), instead of selling a broken bundle.

## 4. Anti-patterns
- No gift flag: a gift is indistinguishable from a 100% price promo - packers, invoices and returns can't treat it specially.
- Silent oversell when a component is untracked / continue-selling; no hold/substitute workflow for components.
- No auto-recompute of BXGY / bundle discount on partial return -> over-refunds are routine and left to apps.
- Order editing blocked for imported orders and heavily restricted with bundles (can't add a bundle, can't raise component qty, no order-wide discount).
- Bundle definitions can't be imported/exported/bulk-edited; component SKU change forces delete-and-recreate; bundle price doesn't follow component price changes.

## 5. New use cases (not in v2 catalogue)
- NU-1 Add-on nested under a specific parent line (warranty, engraving, gift wrap) - deliverable add-on vs bundle component; removed when parent removed.
- NU-2 Bundle definition breaks after sale-side change (component deleted/renamed) -> bundle auto-unpublished/Drafted; operator notified.
- NU-3 Bundle price drift: component prices change, bundle price does not -> OMS should flag stale bundle price.
- NU-4 Exchange of a bundle (or of one component) - Shopify forbids; OMS needs a rule.
- NU-5 Discount targeting rule must reference the bundle, not components (a component-level promo must not leak into bundles, and vice versa).
- NU-6 Ownership lock: only the integration that created the bundle definition / order may edit it - OMS must know who is the writer of record per bundle.
- NU-7 Same-variant quantity split across locations producing fragments (9+3) of one multipack - pick should be case-level.

## 6. Conflicts / open questions
- Community "child SKUs" thread says downstream sees only parent SKU; official help says order lines list component SKUs. Official doc is newer and authoritative; thread likely describes a non-native app or a misunderstanding.
- Webgility claims native tools can't track component inventory; official docs say availability is computed from components. Vendor claim, discard.
- Cart Transform page names both `lineUpdate` and `update` as Plus-only - which one applies is unclear.
- Weighted allocation formula for bundle price is not published.
