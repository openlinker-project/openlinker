# Phase 2 / 1 - BaseLinker (base.com), part 1: bundles, stock, reservations, picking/packing, integration normalisation

Researched 2026-11-04 from primary sources (base.com help PL/EN/DE, api.baselinker.com, developers.baselinker.com, Base changelog "Spis aktualizacji", Base blog incl. reader Q&A, one Base marketing page). Read-only. Points marked (unverified) are inference or found only in marketing text.

## 0. The BaseLinker model in one paragraph

A bundle ("Zestaw") is a catalog product with `is_bundle = true` and a flat list of components `{product_id: pieces}` (API `addInventoryProduct.bundle_products`). It has its own card (name, SKU, EAN, photos, descriptions, parameters) and its own price; its stock is DERIVED: min over components, per warehouse. Bundle-in-bundle is forbidden ("relationships between two bundles are not allowed"). Expansion happens ONCE, AT ORDER IMPORT, controlled by ONE account-wide switch in Order Manager settings ("rozbijanie zestawów", Zamówienia -> Ustawienia -> Przetwarzanie zamówień): off = one bundle line on the order, components still decremented; on = the bundle line is REPLACED by component lines, each component line carries `bundle_id` pointing to the bundle, and the price difference becomes a discount. Channels never declare "this is a bundle": BaseLinker normalises by LINKING a channel offer / shop product to a catalog bundle ("powiązania"); the bundle definition lives only in Base.

## 2. Reservations and stock deduction (context for B-xx)
- Stock goes down at "realizacja" of the order; default moment = order confirmation; configurable "Zamówienia -> Ustawienia -> Stany magazynowe - moment realizacji". WZ document created at the same moment (strict stock control).
- Optional per-catalog reservations: "Produkty -> Ustawienia -> Katalogi -> Edytuj -> Rezerwacja stanów"; products reserved immediately on order download; reserved qty shown in brackets in the Stan column; order list filter reserved / realised / cancelled; editing order quantities updates the catalog.
- Platform-specific timing: Allegro after full order data ("zielona ikonka T"), eBay after FOD, two-way platforms at download, one-way platforms never.
- Split OFF still decrements components (PL help); the DE help translation says components are "no longer reserved" - conflict, PL original is authoritative (unverified which is current).
- Inventory count (inwentaryzacja) does not remove order reservations, it corrects available stock.

## 3. Integration normalisation (how BaseLinker copes with channels sending bundles differently)
1. The channel never declares anything. All integrations (marketplaces + shop file protocol) send flat lines; the shop protocol line has no bundle/parent/gift/discount field. Normalisation is done by the OPERATOR through linking (powiązania) a channel offer/product to a catalog product or bundle: manual ID entry, "Dopasuj automatycznie" (name/EAN/SKU, main products only), CSV "ID katalogu;ID produktu;ID wariantu", auto-link at import/export.
2. Substitution at import: a linked shop line is rewritten to the catalog product (catalog, IDs, weight, EAN, SKU, location; name only with "Nazwy produktów z magazynu"). Then the single account-wide "split bundles" switch decides parent line vs component lines. Each component line keeps `bundle_id` (API) as the only trace of the parent.
3. Precondition = one stock master: for shops, splitting works only when Base pushes stock to the shop. This is how Base sidesteps "master already decrements components" (B-20) - it does not support it.
4. 2026 shift toward per-integration declarations for IMPORTING definitions: Upgates `include_bundles`, VTEX bundle flag + components, Nexo option "traktuj jako zestawy". This is the first sign of integrations declaring bundle semantics, but only for catalog import, not for order lines.
5. Discounts: since June 2026 marketplace discounts land in a structured discount log (order / item / shipment), "where the platform provides data" - i.e. per-integration capability, silently absent otherwise.
6. Automation hook: order event "Zestaw został rozbity" (June 2026) lets operators chain actions (e.g. tag, status) after a split.

## 4. UX patterns worth copying
- Two creation entry points: from a product multi-select ("Stwórz zestaw z zaznaczonych produktów") and from a dedicated Bundles tab; plus a "każdy z każdym" wizard that generates all variant combinations with editable names/SKU/EAN and a price rule (sum x multiplier + amount).
- Bundle has its own card (SKU/EAN/photos/description) while stock is derived - clean separation of identity from availability.
- Reverse lookup: filter "EAN elementu" - find every bundle that contains a component.
- Relationships tab showing "Bundle" / "Part of the bundle" as read-only relation types.
- Packing colours (white/yellow/green/red + beep on over-pack) and "Produkty domyślnie zebrane/spakowane" to auto-pack non-physical lines (discount line, service) - directly reusable for gift/discount lines.
- Component lines keep a pointer to the bundle (`bundle_id`) plus an automation event when a bundle is split.

## 5. Anti-patterns
- One account-wide split switch: you get EITHER the parent line OR the components, never both. Documents, packing and channel feedback all inherit that single choice.
- Price difference dumped into a generic "rabat" instead of an allocation across components (VAT-mixed bundles undefined).
- No parent/child or gift fields in the integration protocol: channel semantics (Woo parent+children, Shopify groups) are invisible, so double counting is possible and only manual linking prevents it.
- Splitting depends on an unrelated stock-sync setting (Base -> shop) - a hidden coupling operators must discover in an FAQ.
- No pre-built kit / assembly flow; no nesting; no slot-with-choice (cartesian bundle explosion instead).
