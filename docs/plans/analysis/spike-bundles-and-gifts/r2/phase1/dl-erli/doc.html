Marketplace dokumentacja API

Dostęp do API

Komunikacja

API oparte jest na architekturze REST. Wykorzystuje protokół HTTPS, w szczególności metody GET, POST, PATCH.

Autoryzacja

Aby uzyskać dostęp do API należy mieć zarejestrowany sklep na marketplace.
W panelu zarządzania sklepem w sekcji Metoda integracji > Własna integracja po API można znaleźć klucz API służący do autoryzacji.
Należy dołączać klucz API do wszystkich żądań do API w nagłówku authorization, tak jak w poniższym przykładzie: 

curl -X PATCH 'https://erli.pl/svc/shop-api/products/8' \
      -H 'Authorization: Bearer XXXXXXXXXXXXXXX' \
      -H 'User-Agent: SuperShop v8.8 (marketplace-plugin v1.2)' \
      -H 'Accept: application/json' \
      -H 'Content-Type: application/json' \
      -d '{"name": "Krzesło"}'

Limity żądań

Ilość dozwolonych zapytań zmienia się w zależności od obciążenia serwisu.
W przypadku przekroczenia limitu serwer odpowiada z kodem 429.

Zalecamy włączenie opcji keep-alive w kliencie HTTP gdy trzeba wykonać bardzo wiele żądań, aby uniknąć wykonywania za każdym razem kosztownych SSL-owych handshake'ów.

User Agent

Zalecamy wypełnianie nagłówka User Agent tak, aby możliwe było szybsze zidentyfikowanie problemu podczas integracji przez zespół Erli.

Rynki

Sklep prowadzi sprzedaż na swoim rynku bazowym i opcjonalnie na kolejnych rynkach (obecnie dostępne są pl oraz de). Rynek, w kontekście którego ma zostać obsłużone żądanie, wskazuje nagłówek X-ERLI-MARKET: 

curl -X GET 'https://erli.pl/svc/shop-api/products/8' \
      -H 'Authorization: Bearer XXXXXXXXXXXXXXX' \
      -H 'X-ERLI-MARKET: de' \
      -H 'Accept: application/json'

Pominięcie nagłówka oznacza rynek bazowy sklepu. Wartość nie jest wrażliwa na wielkość liter. Podanie rynku, w którym sklep nie działa, kończy się błędem 400.

Nagłówek obsługują:

  • GET /products/{externalId} oraz POST /products/_search - odpowiedź dotyczy wskazanego rynku. Podmieniane są teksty tłumaczone (name, description, nazwy atrybutów i kategorii) oraz pola zależne od rynku - m.in. price, cataloguePrice, taxRate, currency, status, dispatchTime, slug, buyableProblems. Produkt, który nie ma danych dla wskazanego rynku, zwraca dane rynku bazowego. Rynek nie zmienia zestawu wyszukanych produktów.
  • PATCH /products/{externalId} oraz PATCH /products/batch-update - dla rynku innego niż bazowy pola name i description zapisywane są jako tłumaczenia dla tego rynku, a pozostałe pola aktualizują produkt niezależnie od rynku. Przesłanie null albo pustego tekstu w name lub description usuwa ręczne tłumaczenie i przywraca automatyczne - na rynku bazowym takie name jest odrzucane błędem 400, bo wyczyściłoby nazwę samego produktu. W przypadku aktualizacji wsadowej nagłówek dotyczy wszystkich pozycji w żądaniu.

Produkty

Id produktów

W API posługujemy się ID produktów z systemu sklepowego sprzedawcy.

Jeżeli kilka produktów w sklepie sprzedawcy ma ten sam ID (na przykład system sklepowy razem trzyma różne kolory tego samego produktu), to należy ubogacić id zduplikowanych produktów, na przykład 123-czerwony.

Metoda PATCH

Podczas aktualizacji produktu zachęcamy do przesyłania tylko zmienionych pól do marketplace.
Gorąco zachęcamy też do nie wykonywania niepotrzebnych zapytań gdy w produkcie nie wystąpiły żadne zmiany.
Zostaną zmienione wyłącznie pola, które zostaną podane w żądaniu.

Wysłanie żądania PATCH na adres /svc/shop-api/products/8 może mieć następujące przykładowe skutki w zależności od treści żądania:

  • {"name": "Krzesło"} zmieni wyłącznie nazwę produktu;
  • {} nie zmieni produktu, robienie takiego zapytania jest bezcelowe;
  • {"images": []} opróżni tablicę images;
  • {"images": [{"url": "…"}]} zastąpi tablicę images nową jedno-elementową tablicą;
  • {"dispatchTime": {"period": 10}} ustawi pole unit na domyślną wartość "dni",
  • {"externalAttributes": [{"unit": "kg"}]} zwróci błąd, bo obiekt wewnątrz externalAttributes wymaga pola type, więc zastąpienie obiektem bez tego pola jest błędem;
  • {"voluntaryWarrantyIdentifier": null} usunie opcjonalne pole voluntaryWarrantyIdentifier;
  • {"voluntaryWarrantyIdentifier": undefined} nie jest poprawnym JSON.

Dodatkowo pole frozen jest wyjątkowe - zagnieżdżone w nim pola są uaktualniane pojedynczo (np. przesłanie {"frozen": {"price": false, "name": true}} ustawi zedytuje tylko frozen.price i frozen.name; pozostawi pozostałe pola wewnątrz frozen niezmienione). Należy więc przesłać w frozen te zagnieżdżone pola, które mają zostać ustawione.

Mrożenie

Ręczna edycja produktu w panelu sprzedawcy powoduje zmrożenie pola. Zamrożone pola nie są zmieniane przez api. Status zamrożeń pól widać w API w polu frozen, a w edycji produktu w panelu sklepu zamrożone pola są oznaczone ikonką.

Należy unikać używania pola overrideFrozen (bądź przestawiania frozen.… na false), aby nie nadpisać ręcznie zedytowanych informacji w produkcie (np. ręcznie dopracowanych opisów lub uzupełnionych atrybutów).

Dodatkowo próba zmiany pola price na promowanym aktualnie produkcie jest niemożliwa i jest ignorowana.

Cykl życia produktu i obsługa błędów

Poniższy pseudokod pokazuje zalecane flow podczas wysyłania do nas produktów.


        function saveProductInMarketplace($product) {
            // you may need foreach here tohandle products with variants/configurations
            $marketplaceProduct = mapProductToMarketplaceProduct($product);
            $previousData = $db->table('marketplace_product')->findOne($marketplaceProduct['externalId']);
            if ($previousData === null) {
                if ($marketplaceProduct['stock'] <= 0 || $marketplaceProduct['status'] === 'inactive') {
                    return; // no point in sending some old products
                }
                try {
                    $data = array_diff_key($marketplaceProduct, ['externalId' => '']);
                    marketplaceApi('POST', '/products/{$marketplaceProduct['externalId']}', $data);
                    $db->table('marketplace_product')->save($marketplaceProduct);
                    return;
                } catch (ConflictHttpException $e) { // 409
                    // avoid being stuck here during every update
                    $previousData = [];
                }
            }
            $changes = [];
            foreach ($marketplaceProduct as $field => $value) {
                if ($value !== $previousData[$field] ?? null) { // this is deep compare
                    $changes[$field] = $value;
                    // to save space you can play comparing hashes instead of raw values
                }
            }
            if ($changes) {
                marketplaceApi('PATCH', '/products/{$marketplaceProduct['externalId']}', $changes);
                $db->table('marketplace_product')->save($marketplaceProduct);
            }
        }

        function marketplaceApi($method, $path, $body) {
            for ($attempt = 1; $attempt <= 3; $attempt++) {
                try {
                    return makeHttpsRequest(…);
                } catch (ServerException | RequestException $e) {
                    // catch only 5XX and connection problems, let other exceptions escalate
                    if ($attempt === $tries) {
                        throw $e;
                    }
                    sleep((5 ** ($attempt)) * 1000);
                }
            }
        }

Jak widać powyżej, zalecamy wysyłać możliwie mało danych do marketplace - dużo taniej jest sprawdzić coś w lokalnej bazie danych niż wykonywać połączenie HTTPS.

Dodanie/aktualizacja produktu jest asynchroniczna - pozytywna odpowiedź https (kod 202) potwierdza tylko, że dane przeszły podstawową walidację i zostały zapisane w bazie danych. Kolejne etapy przetwarzania to między innymi: przyporządkowanie kategorii, atrybutów, grupy wariantowej, pobieranie obrazków, przyporządkowanie zasad rękojmi/gwarancji/zwrotu, przyporządkowanie dostaw, aktualizacja kupowalności produktu, aktualizacja katalogu produktów (listy produktów, wyniki wyszukiwania, strony produktów).

Ze względu na cachowanie zmiany poczynione w produkcie mogą pojawić się z dodatkowym opóźnieniem (do 20 minut) na stronie produktu, listach produktów i w wynikach wyszukiwania. Nie ma to oczywiście żadnego wpływu na API.

Aktualnie nie ma możliwości usuwania produktów, należy oznaczyć je jako nieaktywne.

Kategorie i atrybuty, warianty produktu

Pola externalAttributes, externalCategories oraz externalVariantGroup są przeznaczone na dane o atrybutach, kategoriach i innych wariantach danego produktu. W tych polach przesyłamy informacje o produkcie z systemu sklepowego sprzedawcy, potem te informacje będą przypisywane do odpowiadających im kategorii/atrybutów w marketplace poprzez panel rozpoznawania kategorii i panel rozpoznawania atrybutów w panelu sprzedawcy w marketplace. Pozwala to oszczędzić dużo pracy programistycznej podczas tworzenia integracji.

Zamiast tego (albo dodatkowo) można przesłać dane o produkcie z identyfikatorami kategorii/atrybutów z Allegro - marketplace utrzymuje aktualne przypisania z kategorii/atrybutów tego konkurencyjnego serwisu - należy wtedy zaznaczyć to w polu source. Analogicznie można przesłać przypisane już dane z identyfikatorami z marketplace - należy wtedy zaznaczyć to w polu source.

Opisy

Opis produktu należy przesłać w polu description z podziałem na sekcje (sections), a sekcje z podziałem na elementy tekstowe lub obrazkowe (items).

Każda sekcja może zawierać tylko jeden lub dwa elementy (items), które zostaną wyświetlone na stronie obok siebie.

W elemencie tekstowym można wykorzystywać wyłącznie określone znaczniki HTML:

  • <h1> tytuł
  • <h2> podtytuł
  • <h3> nagłówek trzeciego poziomu
  • <p> paragraf
  • <b> pogrubienie
  • <br/> łamanie wiersza
  • <ol> lista uporządkowana
  • <ul> lista nieuporządkowana
  • <li> element listy

Przykładowa struktura opisu z dwoma sekcjami: 


            {
                "sections": [{
                    "items": [{
                        "type": "TEXT",
                        "content": "
Nagłówek w lewej kolumnie
opis w lewej kolumnie
"
                    }, {
                        "type": "TEXT",
                        "content": "
opis w prawej kolumnie
"
                    }]
                }, {
                    "items": [{
                        "type": "IMAGE",
                        "url": "https://obrazek-wycentrowany.jpg"
                    }]
                }]
            }

Przykładowy element opisu HTML: 


        <h1>Lorem ipsum</h1>
        <h2>dolor sit amet</h2>
        <p>Ut enim ad minim veniam, quis <b>nostrud</b> exercitation ullamco laboris nisi ut aliquip ex ea commodo consequat.</p>
        <ul>
            <li><b>Duis</b> aute irure dolor in reprehenderit in voluptate.</li>
            <li>Excepteur sint occaecat cupidatat non proident.</li>
        </ul>
        <ol>
            <li><b>Duis</b> aute irure dolor in reprehenderit in voluptate.</li>
            <li>Excepteur sint occaecat cupidatat non proident.</li>
        </ol>

HTML musi spełniać kilka reguł:

  • znaczniki HTML pisane zawsze z małej litery
  • znaczniki HTML nie mogą mieć żadnych atrybutów
  • <br/> musi być zapisany w formie samozamykającej — <br> bez ukośnika jest niedozwolone
  • nagłówki <h1>, <h2>, <h3> mogą zawierać wyłącznie tekst — zagnieżdżone znaczniki są w nich zakazane
  • tekst bezpośrednio na poziomie root (niezawinięty w żaden znacznik) jest niedozwolony
  • zagnieżdżanie znaczników HTML jest zakazane z następującymi wyjątkami:
    • pogrubienie <b> oraz łamanie wiersza <br/> mogą być użyte wewnątrz <p> oraz <li>
    • paragraf <p> może być użyty wewnątrz <li>
    • element listy <li> może być użyty wewnątrz <ol> oraz <ul>

Opisy HTML

Istnieje alternatywny sposób przesyłania opisu w polu description.

HTML przesłany w polu description jako tekst nie ma żadnych ograniczeń wobec przesyłanych znaczników i obrazków. Po przesłaniu zostanie skonwertowany do opisanej powyżej struktury.

Uwaga: opis przesłany jako tekst po konwersji będzie wyglądał inaczej, ponieważ zostaną użyte tylko dozwolone znaczniki, a obrazki będą wyświetlone pojedynczo, zawsze w nowym akapicie.

Obrazki

W polu images oczekujemy zdjęć produktów z dużą rozdzielczością (do 5120x5120), bez znaków wodnych, w jednym z następujących formatów: WebP, PNG, JPEG.

Obrazki produktów, a także obrazki z treści opisów produktów, są pobierane przez marketplace, aby przygotować je w odpowiednich rozmiarach i wyświetlać kupującym z naszych serwerów.

W przypadku problemów z połączeniem lub błędami 5XX, próbujemy pobrać obrazek kilka razy po kilku minutach (a następnie godzinach), następnie zaniechujemy dalszych prób pobierania. W przypadku otrzymania kodu 4XX podczas pobierania, zaniechujemy dalszych prób pobierania. Gdy pobrany plik nie jest obrazkiem, to zaniechujemy dalszych prób pobierania.

Po pobraniu (lub zaniechaniu pobierania) danego url'a już nigdy więcej go nie pobieramy. Jeżeli na przykład system sklepowy sprzedawcy nie zmienia ścieżek do obrazków po zamianie obrazka, to należy do przekazywanej ścieżki dopisywać coś, co pozwoli zauważyć zmianę obrazka. Na przykład do ścieżki https://example.shop/1.png można dopisać crc32, md5 lub datę edycji obrazka i wysłać https://example.shop/1.png#706ecdc3f27eb93a4eae3de433ff127e.

Metody dostawy

Sklep może mieć wybrany jeden z trybów obliczania ceny dostawy: ((aktualnie jest dostępny tylko jeden tryb))

Tryb cenników dostaw

Cennik pozwala wybrać metody dostawy, dla każdej metody dostawy pozwala określić cenę, ilość sztuk w przesyłce, kwotę dopłaty za kolejne sztuki.

Dla każdego produktu sprzedawca wybiera jeden cennik - pierwszy element tablicy packaging.tags jest traktowany jako identyfikator cennika. Można najpierw zapisywać produkty z nieistniejącym cennikiem, a potem w panelu sklepu dodać ten cennik. Listę zdefiniowanych cenników można pobrać z /svc/shop-api/delivery/priceLists.

Jeżeli sprzedawca ma identyczne reguły wysyłki dla wszystkich produktów, to tablica packaging.tags może pozostać pusta, wtedy produkty użyją domyślnego cennika.

Pole packaging.weight proszę wypełnić wagą w gramach.

Zasady gwarancji i zwrotów

Podczas rejestrowania sklepu sprzedawca ustala domyślne zasady rękojmi (obligatoryWarranty), gwarancji (voluntaryWarranty) i zwrotu (returnTerms). Sprzedawca może potem stworzyć kolejne zasady i zmieniać domyślne zasady w każdej z tych 3 grup. Domyślne zasady rękojmi/gwarancji/zwrotu są przypisywane do produktu, chyba że zostaną wybrane konkretne zasady poprzez wypełnienie odpowiednio pól obligatoryWarrantyId, voluntaryWarrantyId lub returnTermsId. Rękojmia i zwrot są obowiązkowe, zaś brak gwarancji ma 'magiczny' id 0.

Zamówienia

Informacje o wykonanych zamówieniach, opłacaniu zamówień, anulowaniu zamówień, itd. odkładają się w inbox'ie. Można też "klasycznie" pobierać zamówienia z listy zamówień filtrując po dacie aktualizacji zamówienia i sortując po dacie aktualizacji zamówienia.

Sprzedawca musi aktualizować stan zamówień (przez API lub w panelu sprzedawcy) i wprowadzać informacje o śledzeniu przesyłki.

W przypadku gdy kupujący kupi produkty, które są dostarczane przez różne metody dostawy, to dla każdej metody dostawy tworzy się osobne zamówienie.

Przy aktualizacji zamówienia dla przesyłek Erli sprzedawca nie podaje numeru nadania trackingNumber. Numer nadania zostanie zaktualizowany automatycznie po wygenerowaniu przesyłki.

Stan zamówenia

Zamówienia nieopłacone, czekające na płatość przez PayU mają w polu status wartość pending.

Zamówienia opłacone przez PayU mają w polu status wartość purchased.

Zamówienia COD mają w polu status wartość purchased.

Zamówienia anulowane mają w polu status wartość cancelled.

Zmiany stanów magazynowych

Po dokonaniu zamówienia w marketplace pole stock w produktach jest automatycznie zmniejszane o ilość zakupionych produktów.

W przypadku anulowania zamówienia pole stock nie jest aktualizowane, więc należy dokonać stosownej aktualizacji przez API.

Inbox

Z adresu /svc/shop-api/inbox można pobrać zdarzenia związane ze sklepem sprzedawcy, czyli:

  • nowe zamówienia i zmiany związane z zamówieniami
  • notyfikacje, że produkty wymagają synchronizacji
  • Planujemy implementację:
    • problemy z przypisaniami kategorii/atrybutów/grup wariantowych
    • problemy z zasadami rękojmi/gwarancji/zwrotu
    • problemy z pobieraniem obrazków
    • wiadomości od kupującego / pytania o produkt
    • blokowanie przedmiotów przez moderatorów marketplace
    • faktury za prowizję

Jednokrotnie pobiera się maksymalnie 500 nieprzeczytanych wiadomości, po ich odczytaniu i przetworzeniu należy oznaczyć je jako przeczytane używając id najnowszej (ostatniej) wiadomości.
Osobne żądanie na potwierdzenie przeczytania wiadomości ma ochronić sprzedającego przed utratą wiadomości, gdy przetwarzanie zostanie przerwane ze względu na problemy sprzętowe lub programistyczne.

Użycie inbox sprawia, że podczas używania API nie ma potrzeby pobierania danych z żadnych innych miejsc. Dla przykładu można traktować inbox jako jedyne źródło informacji o zamówieniach i zmianach w nich.

Paginacja

Listy zamówień, produktów itp. mają wspólny interfejs związany z przeglądaniem wyników. Dla przykładu jeżeli chcemy przejrzeć zamówienia utworzone od 1 maja, to wykonujemy zapytanie z następującą treścią: 


        {
            "pagination": {
                "sortField": "created",
                "after": "2019-05-01T00:00:00.000Z"
                // możemy też podać skróconą datę 2019-05-01
                // albo uniknąć pominięcia pierwszej majowej milisekundy i podać 2019-04-30T23:59:59.999Z */

                // domyślnie "order": "ASC"
                // domyślnie "limit": 50
            }
        }

W naszym przykładzie jeżeli chcemy pobrać kolejne 50 zamówień, to zamieniamy wartość w polu after na wartość pola created z ostatniego z pobranych zamówień i ponownie wykonujemy zapytanie.

Pole after pozwala uniknąć używania znienawidzonego przez bazy danych mechanizmu offset/skip.

W momencie tworzenia produktów, zamówień, itp. pole updated ma taką samą wartość jak pole created, nigdy nie jest puste.

Aby zagwarantować brak duplikatów w przypadku remisu w sortowaniu (np. identyczna data i godzina złożenia zamówienia), zamówienie zawiera pole cursor, które można podać jako wartość pagination.after.

Hooki

Istnieje możliwość zarejestrowania własnego hooka. Rejestracja odbywa się poprzez wysłania zapytania POST na endpoint `hooks`. Hooki pozwalają obejść problemy z opóźnieniami w synchronizacji swojej oferty z Erli, które mogą być spowodowane np. oparciem integracji o crona. Na przyład obsłużenie hooka checkBuyability wraz z zaplanowanym hookiem orderCreated powinny wyeliminować przypadki zakupu produktu pomimo wykupienia go przez inny kanał sprzedaży.

productsNeedSync - Produkty wymagają synchronizacji

Hook "productsNeedSync" jest wywoływany, gdy produkty wymagają ponownej synchronizacji (np. ich pola zostaną odmrożone). Zawiera on listę produktów oraz pól, które powinny być zsynchronizowane.

Przy założeniu, że zarejestrowano hook: 


        {
           "hookName": "productsNeedSync",
           "url": "https://moj-sklep.pl/hooks/products-need-sync",
           "accessToken": "very-important-secret"
        }

Podczas odmrożenia system Erli wykona następujące przykładowe żądanie POST:


        curl -X POST 'https://moj-sklep.pl/hooks/products-need-sync' \
-H 'Authorization: Bearer very-important-secret' \
-H 'Content-Type: application/json' \
-d '{"externalProductIds": ["123", "456", "789"], "fields": ["status", "price"]}'

Odpowiedź na powyższe żądanie powinna zwrócić dowolny status 2XX. Nie jest oczekiwana żadna zawartość odpowiedzi.

Brak pól oznacza, że wszystkie pola powinny być zsynchronizowane, na przykład:


        curl -X POST 'https://moj-sklep.pl/hooks/sync-lost' \
-H 'Authorization: Bearer very-important-secret' \
-H 'Content-Type: application/json' \
-d '{"externalProductIds": ["123", "456", "789"]}'

W przypadku błędów połączeń lub odpowiedź zajmie dłużej niż 5 sekund, wykonanie hooka nie zostanie ponowione, natomiast informacja o zdarzeniu pojawi się w inbox.

Testy hooka można przeprowadzać przy użyciu endpoint'a `/hooks/productsNeedSync/run`.

orderCreated / orderStatusChanged - Zostało złożone zamówienie w Erli.pl / zmieniono status zamówienia w Erli.pl

Hooki są wywoływany, gdy zostało złożone zamówienie / zmieniono status zamówienia i zawierają wskazane zamówienie.

Przy założeniu, że zarejestrowano hook: 


        {
           "hookName": "orderCreated",
           "url": "https://moj-sklep.pl/hooks/order-created",
           "accessToken": "very-important-secret"
        }

Gdy powstanie zamówienie Erli.pl wykona następujące przykładowe żądanie POST:


        curl -X POST 'https://moj-sklep.pl/hooks/order-created' \
-H 'Authorization: Bearer very-important-secret' \
-H 'Content-Type: application/json' \
-d '{"id": "1234x5678", "status": "pending"}'

Pełna zawartość żądania znajduje się w dokumentacji: https://erli.pl/svc/shop-api/doc/reference/#/inbox/get_inbox

Odpowiedź na powyższe żądanie powinna zwrócić dowolny status 2XX. Nie jest oczekiwana żadna zawartość odpowiedzi.

W przypadku błędów połączeń lub odpowiedź zajmie dłużej niż 5 sekund, wykonanie hooka nie zostanie ponowione, natomiast informacja o zdarzeniu pojawi się w inbox.
