## Core model, in one paragraph
A BaseLinker bundle ("zestaw", EN "bundle", newer changelogs "Set") is a catalogue product with `is_bundle=true` and `bundle_products` {component_id: pieces}. Its stock is derived (min over components, computed per warehouse and then summed) and its price is its own. The **only** normalisation knob is one global order setting, "rozbijanie zestawów" (Order → Settings → Order processing). With splitting **on**, an incoming bundle line is replaced by its component lines, each carrying `bundle_id`, and the price difference becomes a discount. With splitting **off**, one bundle line stays and the components are still deducted from stock. Gifts are not a concept: they are ordinary order lines, either added by an automatic action "Dodaj produkt do zamówienia (np. gratis)" or flagged per integration into extra fields. Discounts gained a dedicated **discount log** (June 2026) with before/after values and the user who applied each one. Invoices and receipts still carry only a gross unit price per line, with no discount field.

## Integration normalisation
- **One global switch, not per channel.** "Rozbijanie zestawów" lives under Order → Settings → Order processing and applies to all sources, manual orders included. There is no documented per-source override. Splitting from a **shop** additionally requires product links plus stock sync BL→shop, and the docs warn this swaps shop product identity: "Zmieniane są magazyn/katalog, numery ID, waga, EAN, SKU i lokalizacja" while the name stays (https://base.com/pl-PL/pomoc/faq/magazyn-bl/).
- **Catalogue linking is the normalisation layer for bundles.** A bundle is recognised only because the incoming line links (offer link or shop-product link) to a BL bundle product. `bundle_id` "Only applies to bundles from Base inventory". A channel-native bundle with no link stays one opaque line.
- **Connector-specific import of bundle *definitions*.** A stream of per-platform changelog items: Shoper, WooCommerce, Upgates, VTEX, HostGator, Unas, Nexo/SGT "treat as sets". **Source conflict:** changelogs say HostGator/Upgates bundles arrive "in productsList and productsData when include_bundles=true is set", but the public generic shop protocol (developers.baselinker.com/shops_api, ProductsData and ChangeLog) documents no `include_bundles`, `is_bundle` or bundle field. I trust both as true for different layers: the changelog describes BL-built native connectors, and the public file protocol for third-party shop plugins lags behind. Unresolved.
- **Discounts: connector toggles plus a central log.** Each connector decides fold-into-price vs separate line (Shopify, Yampi, Temu, Trendyol SKU mapping, Kaufland types). Since June 2026 a central discount log records what was applied, with before/after values. The line itself still only has the post-discount gross price.
- **Gifts: no neutral concept.** Each connector maps its gift signal its own way: IdoSell → 0.01 PLN technical price with value redistributed; Base Connect/Etsy/Skroutz → order extra fields. Operator-side gifts are plain lines added by an action.
- **Non-goods lines.** Also per connector (MerchantPro wallet → discount line; Allegro deposit → extra field or SKU). The packing assistant handles them with a name-based "default packed" list.

## UX patterns worth copying
1. **Discount log with before/after and actor** (`value_before`, `value_after`, `profile_id`, `details`, per-line breakdown) plus an order-card "Discounts" tab. Copy this, and extend it to gifts (X-06, G-12).
2. **Split as an event.** The June 2026 automatic-action event "Set has been split into components" lets downstream rules react (e.g. add the gift, notify the packer). A neutral "bundle expanded" domain event is cheap and useful.
3. **Reverse lookup "sets containing component EAN X"** and a relations filter "part of a set". Good for impact analysis when a component runs out (B-02, B-12).
4. **Combinatorial bundle generation for variants** (2×3 → 9 bundles) as a pragmatic answer to B-09 when channels cannot express slot choice.
5. **"Default packed" list for non-goods lines** (discount, packaging) so the bench never asks to scan them. Copy it, but keyed by line *kind*, not by name.
6. **Bundle stock per warehouse, then summed.** Avoids overselling when components sit in different warehouses (B-13).

## Anti-patterns
1. **Technical 0.01 PLN price with gift value deducted from other lines** (IdoSell, Jul 2026). It destroys the list-price/rebate information needed for G-10 and typed gift reasons, and silently changes other lines' unit prices on fiscal documents.
2. **Matching non-goods lines by product NAME** ("Rabat" in "Produkty domyślnie zebrane/spakowane"; manual discount = a product line named "Rabat" with a negative price). Fragile, untyped, breaks under translation.
3. **One global split switch.** A shop already decrementing pack components, a marketplace sending parent-only, and an ERP needing the parent all get the same treatment. Enabling it for a shop also rewrites shop product identity (ID/EAN/SKU/warehouse) on incoming orders.
4. **Bundle discount allocation undocumented.** "This difference will be displayed as a discount" gives no allocation rule, which matters for mixed VAT and for partial returns (B-14, B-15).
5. **Gift and is-a-gift semantics stuffed into free-text extra fields** per connector. Not queryable as a fact, not reportable, and the meaning differs per source.

## Confidence and gaps
- **High:** bundle creation/stock/split semantics, the discount-log schema, line fields on invoices/receipts/returns, and the gift-by-automation pattern (official docs plus API spec agree).
- **Low / unverified:** pack bench behaviour for an unsplit bundle; stock formula with pieces > 1 (docs say "lowest stock" only); Allegro bundle and discount import; double decrement with shop/ERP masters; out-of-stock gift behaviour; zero-value lines on KSeF.
- No live account test (the brief forbids sign-up). A trial account would resolve B-05, B-07, B-08, B-11 and G-08.
