# R3 phase 2 / competitor 7: Brightpearl (by Sage) - bundles, free items, Automation, WMS

Round 3, blind replication. Built only from the briefs and `use-cases-v3.md`; no earlier analysis was read.

## How the evidence was gathered (read this first)

- **The live help centre is not machine-readable.** `help.brightpearl.com` now runs on a Salesforce community (`/s/article/<id>`). Fetching an article returns only "Customer Account Portal", "Loading" and a "Sorry to interrupt ... CSS Error" message, and the old Zendesk URLs (`/hc/en-us/articles/...`) answer **HTTP 401**. Tested 2026-11-04.
- **All help-centre quotes come from Wayback Machine snapshots** of the old Zendesk centre, fetched with `curl` from `web.archive.org/web/<timestamp>id_/...`. Each source below names its snapshot date and the article's own "Updated" date. The newest snapshot of any article is from Feb 2023, so **everything here describes Brightpearl as of 2021-2023**. Sage bought Brightpearl in 2022, and the product may have changed since. I could not verify the current state.
- **API facts come from the live `api-docs.brightpearl.com`**, fetched 2026-11-04 (primary source, public).
- Part-way through, the web-search and web-fetch tools hit a spend limit, so the Shopify App Store listing, partner sites (such as the "B Solutions" alternative Shopify connector a reviewer mentions) and community forums were barely covered. Treat "None" ratings as "not documented in the 2021-2023 help centre", not as proof the feature is absent.
- Source types: H = official help article (primary for behaviour, as of the snapshot date); A = official API reference (primary); M = marketplace listing (secondary).

## Brightpearl's model in one paragraph

A Brightpearl **bundle** is a product record with "Bundle = Yes" and a component table (max 40 items). It is **always non-stock tracked**; its availability is computed per warehouse from components; components stay sellable alone. When a bundle is added to a sales order (by hand, by API, or because a channel listing is connected to it by SKU), the order "explodes" on save: one parent row carrying the price, plus one row per component **at zero price**, linked by `composition.bundleParent / bundleChild / parentOrderRowId` (A1). Cost of sales posts from the components (FIFO). WMS and goods-out notes pick and pack components, and the packer can see a rolled-up bundle line. Gifts have **no first-class concept**: a free item is a zero-price row, added by hand or by the Automation action "Add free SKU". POS has proper promotions ("Buy X get Y free", "Spend X and get Y items free"), but they work **only in POS**. Channel discounts arrive as already-reduced row prices, plus a zero-value or negative coupon row depending on the channel.

## Integration normalisation (how Brightpearl copes with each channel encoding things differently)

1. **Catalogue linking by SKU is the only bundle "declaration".** A channel listing or product is connected to a Brightpearl product **or** bundle by identical SKU. Whether an order line expands depends only on what that SKU is in Brightpearl. Connectors never declare "this channel sends parent plus children" (S14, S16, S6, S18).
2. **Per-channel strategy is chosen in the docs, not in settings.** Magento has two documented modes (bundle in Magento with only components connected, or a Brightpearl bundle on a Magento simple product). The duplicate hazard (bundle:bundle) is left to an "IMPORTANT" warning (S19, S38).
3. **Support matrices per connector.** Each channel article carries a table (Inventory sync / Price sync / Order download / Stock allocated / Shipment update / Split shipment of components / Tracking reference). This is the closest thing to adapter-declared capabilities, but it is documentation, not runtime (S6, S14, S16, S17, S41).
4. **Channel price is authoritative.** "Always respect the item price and tax collected", with a **reconciliation line** when unit×qty rounding differs from the channel total. Tax *codes* come from Brightpearl's tax rules; tax *amounts* come from the channel (S15, S37, S38).
5. **Discounts are normalised to row price plus an informational row.** Shopify and BigCommerce: weighted spread over item rows (shipping discounts only reduce shipping), with list price kept as the original. Magento: per-row discounted price, coupon code via customization mapping. The coupon row is negative or zero depending on the channel (S15, S21, S25, S37, S38).
6. **Non-goods lines get mapped SKUs or nominal codes.** Gift certificates get a configured SKU with a liability code; shipping and discount lines get default nominal codes; gift wrap becomes a row; gift messages go to custom fields (S35, S37, S38).
7. **Shipment feedback is degraded to the channel's grain.** With bundle components shipped separately, the channel sees the whole bundle shipped at the first component (Amazon, Shopify), or only on "fully shipped" (BigCommerce, legacy Shopify, ekm). Tracking is at "Simple product level" (S6, S14, S16, S41).
8. **Unknown SKUs degrade to free-text rows** that cannot be shipped. The fix is to create the product, delete the order and re-download ("Single Order Import") (S15, S35).
9. **Returns import is per connector.** Shopify can create sales credits (orders less than 60 days old, "cancel and refund now" only); Amazon returns are not imported at all (S30, S36).

## Conflicts found

- **Nested bundles.** Help says "Brightpearl only allows a single level of bundles and does not support any nested bundles" (S14). The API Product Bundle GET example shows "bundle 391 is itself a component of bundle 488" (A4). I trust the help text for UI behaviour; the API example may be illustrative or allow it only via API (unverified).
- **Cost on the parent row.** The API Order GET example shows the parent row with `"itemCost": {"value": "5.0000"}` and children at 0 (A1), while help says cost of sales posts from components via FIFO (S2) and reports show "all of the cost ... against the bundle components" (S9). I trust the help: the order-row itemCost and the posted journal may be different things.
- **Magento-built bundles.** 2016: the order shows "details of the bundle (which gives the sell price) plus each individual stocked item" (S19). 2022: "An order for the bundle will only show the simple products, or the components" (S38). I trust the newer text.
- **Shopify shipment of bundles.** The same article (S14) says both "the whole bundle on Shopify will be marked as shipped when the first item is shipped" and, in its table, "Shipment update: Yes - when order is marked as fully shipped". Unresolved.
- **Bundle stock sync history.** The legacy Shopify and ekm apps had "Inventory sync: No" (S17, S41). From 2021, S2 notes "we now support bundle inventory across all integrated sales channels". This is an evolution, not a contradiction.

## UX patterns worth copying

1. **Explicit parent-child row linkage on the order** (`bundleParent`, `bundleChild`, `parentOrderRowId`), with the price on the parent, children at 0, and visual "blocks" next to rows in the order UI (S4, A1). Simple, inspectable, and API-visible.
2. **Two independent document toggles.** Invoice: components under the name, or a single line. Goods-out note: omit components for pre-packed bundles to prevent double-picking (S4).
3. **WMS bundle packing controls.** A rolled-up bundle line with an expand arrow; scan either the bundle barcode or the components; **"Bundle validation"** against mixing the two; **"Pack bundled items together"** forces a bundle to be completed before switching parcels (S10, S27).
4. **Per-warehouse "complete bundles only" availability** with a worked example in the docs, conservative by design (S3).
5. **Rule log that shows every condition with the order's value against the expected value and a ✓**, plus "is / is not" and ANY / ALL / NONE row conditions (S13, S31, S33). This is a strong model for a G-16 "why did or didn't the gift fire" view.
6. **A support matrix per connector** (sync, order download, split shipment, tracking grain), stated as a table. This maps directly onto adapter-declared capabilities.

## Anti-patterns

1. **First component shipped = whole bundle shipped** on the channel (Amazon, Shopify), and "split shipment of components not supported" (S6, S14). The buyer is told everything shipped when it has not.
2. **Revenue on the parent, cost on the components**, so reports show a 100% margin and a 100% loss, and the operator is sent to spreadsheets (S9).
3. **A gift is just a zero-price row.** No type, tracked by a custom field or by renaming the row "Sample", with cost moved to marketing by hand-editing journals (S20). Free items cannot be reported or audited.
4. **Duplicate expansion left to a warning.** Connecting a channel bundle to an OMS bundle double-counts, and nothing detects it (S19).
5. **Silent gift failure.** The Add free SKU action waits in the watch list when the gift is out of stock, the rule acts only once per order, and "Pending" log entries are purged after 24 h (S11, S12, S33, S34).
6. **Promotions locked to one surface.** POS promotions and coupons do not apply to e-commerce orders ("can only be applied within POS"), so the same "spend X get Y" deal needs a different mechanism per channel (S23, S24, S37).

## New use cases (not in v3)

- **N-01 Bundle on a purchase order.** A supplier sells a kit, but stock is received as components. The bundle price must be split across component costs (manually, or via a negative non-stock row). (S5: "the bundle price may need to be manually divided among the components.")
- **N-02 Pre-packed virtual bundle.** No own stock, but its own scannable barcode and "omit components" on paperwork, a middle state between B-03's two options. (S4, S10)
- **N-03 Demand planning / replenishment** folds bundle sales into component forecasts. (S7: "The demand for a bundle is accounted for in the replenishment suggestions of its components.")
- **N-04 Free samples from a separate "Sample stock" warehouse**, shipped together with a paid order via split fulfilment, with cost reclassified to a marketing expense account. (S20)
- **N-05 Rounding reconciliation line** when the channel total differs from unit×qty after discount spreading. (S37: "Brightpearl calculates row totals using unit price multiplied by number of units, instead of taking a row total amount directly from BigCommerce.")
- **N-06 Variant-bundle generation.** Create one bundle, add a variant option, get N bundle records each pointing at one variant component (a practical answer to B-09). (S2)
- **N-07 Per-line gift message bound to a SKU** (Amazon prefixes each message with the SKU). (S35)
- **N-08 Unmatched SKU becomes an unshippable free-text line**, with "delete and re-download" as the recovery (relevant when a bundle SKU is not yet defined). (S15)
