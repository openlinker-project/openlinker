## 1. How the product models bundles and gifts (summary)

**Cin7 Core.** A bundle is an ordinary product with an "Assembly BOM". Two run-time modes:
- *Manual assembly* (pre-built kit with own stock): "Manual assembly keeps components in your inventory until you create an assembly order for the finished product." (C-AA)
- *Auto-assembly* (virtual kit): "With auto-assembly, you keep only the component products in stock. When a sale for an auto-assembled product comes in, this triggers an assembly order for the finished product. ... Stock availability for the finished product is calculated as what could be assembled from available components." (C-AA)
- Plus a WMS-only third mode, *Picking for kitting*: pick the assembled unit if in stock, else pick components and the system auto-creates the assembly order (C-PFK).

The **sale line is always the parent**; components move through a separate, system-generated assembly order. There is no parent+children representation on the sale itself. Gifts have no type of their own: the API states "Discount. Value between 0 and 100. For free items discount is 100" (C-SALEAPI). Promotions ("Product Deals") are a Core-side engine for Core/B2B/POS sales; for e-commerce orders "Cin7 Core does not perform any discount calculations, it simply captures the discount amount from Shopify" (C-SHO).

**Cin7 Omni (contrast).** Product "Order Type" decides behaviour: "Kit: for Bill of Materials products. This will show Virtual Stock." / "Made To Order: for Bill of Materials products that are only built when sold." (O-PROD). On a sales order the BOM can be **loaded into the order itself** as a parent row ("Make") plus component rows ("Use") - visible in the import template: "enter Make for the BOM product and Use for each component ... enter Parent for the BOM product" (O-IMP). Per integration: "Automatically Load BOMs for Kits ... Yes: The line item's BOM will expand; each component of the finished product will be shown as a separate line item. To dispatch the finished product, you must dispatch each component separately" (O-SHS). Promotions are a "promotional matrix" with limited reach: "You cannot use promotions with the Cin7 Omni API" and "Buy X and get X free ... promotions can not be used with Sales Orders or Legacy B2B" (O-PROMO).

## 3. Integration normalisation

How Cin7 copes with channels encoding bundles/discounts/gifts differently:

1. **Connector-owned, fixed mapping; few operator knobs.** Each integration has a Setup page with a small, connector-specific set of switches; the core of the mapping is not configurable ("The data mapping between Cin7 Core and Woo is preconfigured and cannot be changed", C-WOOF). There is no generic "channel declares X" layer visible to the operator.
2. **Kit expansion is decided by the PRODUCT, not the channel (Core).** If the parent SKU has auto-assembly, every channel's order for it expands; the only per-channel knob is the *quantity policy* "Process auto-assembly as" (C-AA). **Omni inverts this:** expansion is a per-integration switch "Automatically Load BOMs for Kits", gated by the product's Order Type = Kit, with a documented channel exception: "the 'Automatically Load BOMs...' setting ignores the Amazon Fulfilled Orders (FBA)" (O-AMZ). So Omni already has "channel x product" gating.
3. **Discounts: per-channel shape, not normalised.** Shopify gets two shapes (proportional line price reduction OR per-line discount charge carrying the line's tax rule); Woo/Amazon/eBay/BigCommerce get one unallocated order-level charge; BigCommerce/Woo coupons optionally as named charges or products (C-SHO, C-WOO, C-BC). Tax is always copied, never recomputed ("will bring in the exact tax amount", C-WOOF). Result: the same promotion lands three different ways depending on channel.
4. **Catalogue linking via SKU, with manual link column and a BOM-alias trick.** Products auto-match by SKU + name, else manual link in the Catalog tab (C-AMZF). Where channel SKUs collide or differ, Cin7 uses a **1-component auto-assembled "KitProduct"** as an alias: "Each KitProduct will have an Assembly BOM containing 1 component only, MainProduct ... KitProducts will only be used to accurately update stock levels and fulfillments and will never be used in sales" (C-DUP); users also link differing Woo SKUs "by auto-assembly for stock calculations" (C-WOOF). Pack listings (SKU5 = 5 x SKU1) are the same mechanism with qty N.
5. **Channel bundle types are opaque.** Magento order lines are said to respect "Bundle, family, Configurable" types, but outbound a Core BOM can only become a Magento *simple* product (C-MAG). No documentation for Shopify bundle groups or Woo bundle plugins.
6. **Gift signals from channels are not normalised.** Gift message -> notes, gift wrap -> charge, gift card -> liability account; free item = 100% discount line. Nothing maps a channel's "free item" flag.
7. **Import is one-shot and log-deduplicated.** "If an order already has an entry in the log ... it will not be processed again ... This also means we do not capture changes made to orders after they are downloaded" (C-SHO). Any channel-side bundle/gift edit after import is lost.

## 4. UX patterns worth copying

1. **Per-channel expansion switch gated by a product attribute, with a named exception** (Omni "Automatically Load BOMs for Kits" + Order Type Kit + "ignores ... FBA"). Maps cleanly to "adapter declares capability + operator toggles per connection + product says it is a kit". (O-SHS, O-AMZ)
2. **Buildable availability shown where decisions are made**: virtual stock column in product list, and in the sale-order product picker ("as many units available for sale as you have component quantities"), with the mode difference (built-only vs built+buildable) spelled out. (C-AA, O-VS)
3. **A named, actionable failure bucket for kits that could not be built**: "Out-of-Stock Components for Auto-Assembly Report", organised by location and finished SKU, feeding purchasing. A good template for G-16 / B-12 statuses (though the re-authorize step should not be needed). (C-OOS)
4. **Expanded pick list grouped by kit** (KitSKU / KitName / KitQuantity, non-kits under "Items") - one document serving both levels. (C-MM)
5. **Pick-time kitting fallback**: pick a built unit if available, otherwise explode to components and record the assembly automatically. (C-PFK)
6. **Deal builder with explicit "Buy" vs "Get" criteria and an explicit discount base** ("Order total" vs "Buy collection total"), plus worked examples in the UI help, dates, customer tags, single-use coupons. The "base" choice is exactly what our neutral reduction needs to record. (C-DEAL)

## 5. Anti-patterns

1. **Import-once, never-update orders** with dedupe by log row; fixing a changed order means void + delete log + re-import. Gift/bundle edits after import (X-04) silently diverge. (C-SHO)
2. **Unallocated order-level discount charge** on most channels. Loses per-line net price, makes per-line VAT and partial returns of bundles/gifts wrong or manual. (C-WOO, C-AMZ)
3. **All-or-nothing auto-assembly with no substitution**, plus "Undo ... then Authorize again" as the recovery path; batch-tracked kits cannot even have a line changed without voiding assemblies. Community has asked for BOM flexibility. (C-AA, C-SHF, C-FR1)
4. **Two promotion worlds**: the internal deal engine and free shipping do not apply to channel orders ("it is not applied to orders captured from eCommerce channels such as Shopify"), and Omni's BOGO is POS-only and promos are API-invisible. Operators cannot express one gift rule across channels. (C-DEAL, O-PROMO)
5. **Gift = 100% discount with no type or reason**, and in Omni the promo matrix cannot even reach 100% (99.9999%). No way to report gifts, apply gift-specific VAT/document policy, or handle gift returns. (C-SALEAPI, O-PROMO)
6. **Kit mechanism reused as an SKU-alias hack** (duplicate SKUs, differing channel SKUs): conflates "listing identity" with "bill of materials", with fragile relinking rules (re-download needed, KitProduct disappears if unlinked). (C-DUP)
7. **Multi-level kit behaviour flips with the auto/manual flag per level** (sub-assemblies picked vs exploded), documented with six examples because it surprises users. (C-ML)

## 6. New use cases (not in v3 catalogue)

- **N-1 Channel SKU alias / listing variant that is the same physical product** (duplicate SKUs at different prices, differing channel SKUs) - stock must be shared, sale must show the master item. Source: C-DUP, C-WOOF.
- **N-2 Kit availability policy: count pre-built units, buildable units, or both**, and per-channel which number is published. Source: C-SHF, C-AA.
- **N-3 Auto-build quantity policy**: build exactly the ordered quantity vs build up to a minimum/reorder level vs only the shortage. Source: C-AA ("Quantity required and maintain minimum stock level quantity").
- **N-4 Nested bundles**: whether a sub-bundle is consumed as a pre-built unit or exploded to its components. Source: C-ML.
- **N-5 Pick-time fallback** from pre-built kit to components inside one order line. Source: C-PFK.
- **N-6 Channel-fulfilled orders must not expand bundles** (marketplace warehouse such as FBA ships the parent from its own stock). Source: O-AMZ.
