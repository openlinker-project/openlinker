Which document, from which integration, per country

Second review pass — ADR-041 dec. 5's rule engine, previously deferred, now leads this tab. A rule is conditions → document type → integration, scoped to one country; no rule matched falls through to that country's default integration per document type. Legal responsibility for what a sale requires stays with the operator — OpenLinker executes the configured routing, it doesn't decide tax obligations (see tab 06 for that framing spelled out).

Scope decision, confirmed before implementation starts: the rule-building mechanism (conditions → document type → integration, defaults, the fallback ladder) is fully country-agnostic and available to every country an operator wants to configure by hand — nothing below is Poland-only. The predefined starter template (the "Review & adopt" screen further down) is the one Poland-specific exception, and stays that way for this issue: no other country ships a curated template yet. An operator can still build fully custom rules for Poland too — adopting the template is never mandatory, and a country with no template is not a country that can't be configured, just one nobody has pre-written suggestions for.

Correction, independent architecture review "Receipt with NIP" is a property, not a third document type the earlier pass modeled it as a peer of Invoice/Receipt — this bypasses the router's own capability check for open-world kinds

Why this changed

SalesDocumentKind has exactly two well-known values, 'invoice' and 'fiscal-receipt' — the discriminator that decides which CAPABILITY to dispatch to. A receipt that happens to carry the buyer's tax id (PL art. 106e ust. 5 pkt 3 — a paragon standing in as a simplified invoice, ≤ the PL threshold, through 2026) is still the same document, the same capability, the same adapter — one optional field populated, not a third kind. Modeling it as a peer of 'invoice'/'fiscal-receipt' would also silently skip the router's capability-validation for open-world kinds (it only checks the two known values). Now: the "Document type" choice stays exactly two-valued (composer above), and "include the buyer's tax id" is a checkbox on the Receipt outcome — data the fiscalization command carries, not a routing decision.

Same review pass, one more correction: earlier drafts of ADR-041 decision 5 sketched a priority field with "last match wins, equal priority is a conflict." This design deliberately narrows that: there is no priority field at all — see the conflict guard below, which rejects a same-conditions/different-integration save outright rather than letting a priority number decide it. For a fiscal document, a number quietly picking a winner is the same failure mode this whole epic exists to close.

A dependency this design cannot route around Blocked on: buyer tax-id on the order contract ADR-041 dec. 5's own words — "a blocking prerequisite of the engine, not an assumption it may make"

Every rule below presupposes "buyer has a tax ID" already works. It doesn't yet.

Order carries no buyer tax identifier or buyer-type today — no issuance caller wires one, so every auto-issued document is type: 'private', taxId: null. The rule engine's flagship condition can't evaluate against real data until that field exists on the order contract. This mockup shows the target design; it is not claiming the condition is already computable.

"Customer has no NIP" for Poland already routes to eparagony.pl. Saving this rule would point the identical condition at Subiekt instead — OpenLinker can't pick between them by save order, so it isn't saved as a second, silently-losing rule.

Deliberately no priority field to break this tie. Correction after first review Why there's no separate per-connection checkbox anymore

"Auto-issue invoices on this connection" has nowhere to move to — it asks the wrong question

The first version of this mockup had two independent checkboxes: one per capability, on the connection's own edit screen. That breaks the moment this connection's "Issues" becomes a receipt — a checkbox named "Auto-issue invoices" stops making sense, and adding a SECOND checkbox ("Auto-register fiscal receipts") next to it implies two independent axes, when there's only one: isPrimary (dec. 3a — exactly one originating document, so exactly one primary among ALL candidates, regardless of capability).

A more important reason than naming: primary can only be set correctly by seeing all candidates at once. N independent checkboxes across N separate connection forms is exactly the shape that produces a conflict today — two people, two sessions, two saved connections, neither aware of the other. One radio group in one place structurally eliminates that possibility at the UI level (the write path — dec. 3b — remains the guarantee for configuration that originates outside this screen).

So EditConnectionForm gets a READ-ONLY view only — no duplicated editable control.

The one sentence this whole feature has to keep true OpenLinker executes routing — it doesn't decide what a sale legally needs

Not stated: "OpenLinker knows this order legally needs an invoice."

Stated instead: the operator defines document rules; OpenLinker executes the configured routing. Every rule, default, and threshold on this page is something an operator typed in — OpenLinker never infers a tax obligation, and no copy on this page implies otherwise. That distinction is why this can change country by country, and be wrong by configuration without ever being wrong by design.

Comparing a threshold against an order's own totals.currency needs an explicit mismatch rule — an EUR order against a PLN thresholdRef is NOT convertible via the existing FX stamp (ADR-040: "this stamp is analytics-only and must never supply a fiscal document's rate"). A currency mismatch resolves unresolved with a new reason (tab 04), the same way an exclusive (net) total already does for net-priced-order — never a silent conversion.

All three tables sit in the existing sales-documents context (libs/core/src/sales-documents/) — this epic's own "module now, context later" decision (ADR-041 dec. 1) already reserved that context for exactly this kind of policy data. The conflict guard (tab 02) is one unique index on (country, conditionsHash) plus an application-level check for overlapping effectiveFrom/effectiveTo ranges — a DB constraint alone can't express "overlapping date range," so the guard is a transaction-scoped read-then-reject in the same service that would otherwise INSERT the rule, not a trigger.

Two things this table layout does NOT mean. First: the rule evaluator stays a pure function over an order-fact projection the caller assembles — mirroring how the router itself takes Order as a value parameter (ADR-041 dec. 2), never injecting an orders/customers token. Reading a buyer's tax-id presence off the order happens in the CALLER, before the evaluator runs — the leaf context (no outbound value imports, enforced by barrel-purity.spec.ts) never reaches into a sibling context for it. Second: Poland's specific citation text and threshold VALUES (the seed data behind pl-simplified-invoice-2026, the KSeF source URL, the disclaimer copy) are NOT rows this context writes on its own — they ship from the API/interface layer as seed data, never as literal "KSeF"/"NIP" strings inside libs/core/src/sales-documents/**. The feature (a template exists, is cited, is inert until adopted) is architecturally fine; the country-specific CONTENT still has to stay out of core, the same way KSeF/FA/NIP vocabulary already stays out of libs/core/src/invoicing/ today.
