Epic 3 · New capability

eparagony Issues Invoices

The provider that registers our fiscal receipts can also issue full invoices and relay them to KSeF. This epic gives one connection both roles — and keeps the guarantee that one sale still ends with exactly one document.

Where the line runs, and why it holds itself

The two capabilities do not overlap, and not because we maintain a convention — because they are different request bodies at the provider, with different validation.

One plugin, several capabilities: ordinary PrestaShop already dispatches six from one table. There is no structural obstacle to eparagony exposing two.
And the double-issue fear was overstated I claimed the one-document guard assumed (connection, kind) uniqueness and had to be reviewed before anything else. It does not. Both cross-kind guards are already connection-blind — the invoice side searches by blocksFurtherRegistration with no connection filter, and the fiscal side calls findBlockingInvoiceForOrder(orderId) with no connection argument at all, both under the same per-order lock. A dual-role connection cannot produce both documents for one sale. What survives is a one-hour confirmation and a stale docblock sentence to correct.

on Fiscalization

on Invoicing

Issue invoices and corrections. Where the provider relays a document onward, OpenLinker follows its status.

Enabling a role does not route anything to it This connection becomes eligible to issue invoices. Which orders actually get one is decided under Sales documents, per country.

Two independent switches, not one three-way choice — a connection may hold one role, the other, or both, and turning one off must never imply anything about the other.

The first support question this will generate A connection's enabled roles are stamped at create and never back-filled. An eparagony connection that already exists will not gain Invoicing when the adapter starts advertising it — the operator must switch it on. That is correct behaviour and it will still surprise somebody.

This is the real gate of the epic, and it is not front-end work readSalesDocumentRouting reads documentKind as a single string, and SalesDocumentRoutingCandidate.documentKind is single-valued. "Both" is not expressible in the shipped model. It needs the config key, the coercer, the candidate type, the routing resolver, the auto-issue trigger and the settings view widened together — six sites. Everything else in this epic can proceed while that happens; only the role select and the acceptance test wait on it.
Why "Both" is safe now and was not before "Goes first" used to be the only thing separating two candidates, so a connection offering two kinds was genuinely ambiguous. It is not any more: a routing rule names the kind and the connection, and the country fallback is a single select naming both. There is no decision left for the system to guess at — which is what makes declining to split the connection affordable.
Cost to accept Widening the routing model touches auto-issue. That path decides, unattended, which document a paid order gets — so it needs its own regression tests, not just the acceptance scenario below.
03

Awaiting submission

eparagony relays to KSeF, so a document travels PENDING → OFFLINE → CONFIRMED. The provider's own words for OFFLINE are "invoice issued in Offline mode – awaiting submission to KSeF" — which maps to pending-submission on our neutral axis, not submitted. The document has not left yet.

Deliberately no "Send again" button — seven endpoints in the provider's API, none of which triggers transmission. The hash is shown because it is the one thing proving a document was built, and the value a support ticket gets answered against.

Correction — this is wiring, not new UI An earlier draft called this "the screen that does not exist". Overstated: the order cell already renders the literal label "Awaiting submission", the invoice timeline already draws an active waiting node, and pending-submission is already handled in the lifecycle steps. What is missing is the eparagony adapter mapping into it. Do not build a second ladder beside the shipped one.
The exception that shapes the copy During a total outage at the authority, this state stops being transitional: the visualisation becomes the legally valid document and there will be no further transition. Over the API the two cases are indistinguishable — the provider does not report the outage. Hence "waiting", never "it will clear shortly", and an elapsed measurement rather than a countdown.

What the audit changed here The old plan gated this entire epic on reviewing the one-document guard. Wrong gate, and it cost the adapter its head start. The guard is already connection-blind; the real gate is the single-valued routing model, and it holds up exactly two tasks. E3-3 onwards can start on day one.

Open decisions

  • Whether "Both" or a narrowed role is the default when an operator first enables the second capability. Narrow is conservative; "Both" matches what someone enabling it probably wants.
  • Whether voiding a receipt is in scope. The guard's copy already offers it as the way forward, and no provider in the tree exposes a void today.
  • Whether a role may be disabled once documents exist under it. Disabling leaves those documents without a live issuer for corrections.
