Competitor research — what changed and what didn't

Two research passes (BaseLinker / Apilo / IdoSell / Sellasist — the Polish market this screen actually ships into; and ShipStation / ShipHero / Extensiv / Linnworks / Cin7 — the wider category) converged on a few things worth stealing, and ruled a few things out:

Added: per-scan audio+colour feedback distinct from the end-of-parcel state (universal across every tool checked); a manual "can't scan it" override (Apilo, IdoSell); a pull-based Take next task action (mirrors the reference screenshot, and matches BaseLinker/Apilo's auto-advance toggle); a concurrent-picker collision warning (BaseLinker shows an orange banner, Apilo sums both packers' scans) — a real gap, since two packers CAN pick up the same FulfillmentWork today; courier-cutoff framing on the deadline badge ("must ship by 16:00 — InPost") instead of a bare countdown, since Polish tools frame urgency around the courier's actual pickup schedule, not a generic SLA.

Deliberately NOT added: live scale weight capture — every source describes it as a physical scale built into the desk, never a digital "weigh and confirm" step, which matches the real bench-documents.tsx docblock's own reasoning for keeping box measurements off this screen. And the reference screenshot's per-zone order progress (PIĘTRO/DÓŁ split bars) is NOT a pattern either research pass could find documented anywhere, in either market — it's not "what everyone does," it's a genuinely open product question, and OpenLinker's real docs (fulfillment-work-detail-page.tsx) explicitly say the opposite today: "Everything below belongs in this box only. The other box of this order is being handled somewhere else." I left it out of this build rather than mocking up something the real product's own docs argue against.

Round 2 — foolproofing + hardware reliability

First pass covered feature parity; this pass asked what makes a screen genuinely mistake-proof for a first-day, possibly non-native-language worker, and what a shared kiosk should say about its OWN hardware. Two sourced anti-patterns drove real decisions:

Added: a tri-colour connectivity indicator, ported directly from Shopify POS — green (scanner + network both fine), amber (hardware problem), red (network problem), because the two failure modes have different fixes and a single "offline" banner tells a packer the wrong one to try. An "Undo last scan" action living right next to Confirm rather than in a menu — a real open-source WMS bug thread found in research states the failure mode exactly: "an operator has to leave the scan flow, find the row, open a menu... so in practice they don't, and the data drifts." A pre-lock countdown warning (GOV.UK's session-timeout pattern) instead of an abrupt lock with no warning. The printer/scanner binding made visible ("Printing to Zebra ZD420 · Bench 3") — research found this binding is configured by an admin in every tool checked (ShipHero, BaseLinker) but never shown to the worker at the bench, which is exactly backwards for a shared terminal. And every primary touch target raised to ≥44px, the converged WCAG/iOS/Android floor for gloved hands.

Confirmed as a genuine, unsolved gap, not something I invented a fake fix for: research found NO pick-pack tool — not ShipStation, ShipHero, BaseLinker, Apilo — documents a per-action retry (pressing "Confirm this line" and having it fail server-side); every retry pattern that exists operates one level up, on a batch of labels. And printer-status flags are documented as actively unreliable at the SDK level (both Zebra's and DYMO's own vendor docs admit isConnected lies). So the connectivity indicator here is deliberately named a status summary, not a promise — and a failed "Confirm this line" gets its own visible retry rather than silently vanishing, since that's the one thing research could confirm nobody has solved well.

Round 3 — two tech-lead UX audits, one real bug found

Two independent audits, reading the file cold and clicking through every state, converged on the same top finding — which turned out to be a genuine mistake, not a design disagreement: the earlier draft showed a required-looking Confirm this line button sitting right next to a footnote saying "there is nothing here to press." Checking the real component (bench-parcel.copy.ts) settled it: Confirm this line is real, but it's the manual fallback for a damaged or unreadable barcode — scanning alone confirms a line, no button needed. I'd built the fallback control twice, once as this button and once as a separate tiny "mark manually" link. Fixed to one control, correctly labelled, and the footnote is now actually true.

Also fixed: a table row that quietly contradicted its own quantity and status (a real bug, not a design choice); every tooltip-only hint (connectivity, undo scope) moved onto the screen as visible text, since this is a touch kiosk with no hover; the rail rows were showing the internal work id as the primary label instead of the order reference the real bench-work-row.tsx actually renders; "To pack 12" and "To pack 4" now say what each one counts; a closed-but-unlabelled parcel no longer inflates the "to pack" count; Hold and Packed-no-label now share one structured header and a matching forward-looking reassurance; and signing back in after an idle lock now returns to whatever state was actually on screen, not a hardcoded default — so "nothing has been lost" is true rather than aspirational.

Both "real bugs" named above are mockup-draft defects, not shipped-product defects — mistakes I made building an earlier draft of THIS file, caught by the two audits reading this file cold. Neither was reproduced against the real /pack screen in production, so no separate product issue is being filed for either; this section exists so a reader can tell that apart from the items marked new above, which ARE proposed changes to the shipped product.

Round 5 — a real scan engine, and "line" retired from what the packer reads

Two pieces of direct feedback. First: the scan box did nothing — only the dev "Simulate a scan" pill produced feedback, so nothing here actually demonstrated the product's central claim. Type MUG-WHT-350 (or its EAN, 5901234123457) into the scan field above and press Enter — it's checked against the real active item, the count and table update live, a wrong code shows a named error and records nothing, and the parcel auto-advances through items and closes itself the moment the last one is verified, same as the real product claims.

Second: Confirm this line is the REAL shipped string (bench-parcel.copy.ts) — but "line" is warehouse/ERP jargon a buyer-facing e-commerce team wouldn't write, and there's no reason a packer needs to inherit it. Every packer-facing "line"/"lines" here is now "item"/"items" — a proposed copy fix on top of a verified-real control, not a claim that the shipped product already says this.

Round 4 — assignment: a genuinely new concept, not a shipped one

Checked first: the real schema has no assignedToUserId on a FulfillmentWork today — only packedByUserId, stamped AFTER the fact. Every packer can currently claim any unassigned parcel; there's no way for a supervisor to earmark one for a specific person ahead of time. This round adds that, grounded in a dispatch/task-assignment research pass (ServiceTitan, Onfleet, Cin7 Core WMS, Deputy, Jira).

The one explicit decision you made: show unassigned work greyed-out rather than hiding it, which is Jira's model (a separate visible "Unassigned" swimlane) over Cin7 Core's (assigned work is invisible to everyone except the assignee) — Cin7's stricter model was the other real option research surfaced, and you picked visible-but-muted.

Also decided: claiming is instant and first-click-wins (Deputy's plain "open shift" mode — the dominant pattern; the only documented alternative anywhere in research is routing every claim through a supervisor approval, which is Deputy's OTHER mode, not the default one). The companion operator screen — Assign Packing Work — assigns by dropdown rather than drag-and-drop; ServiceTitan documents both as valid, and dropdown is the one a static HTML mockup can actually demonstrate honestly.

Round 6 — bin-level location, a genuinely new concept, not a shipped one

Checked first: OpenLinker's real inventory_locations table is warehouse-level only — code, name, kind, status — with no shelf/bin/row column anywhere, a deliberate design choice recorded in the docs ("OpenLinker never invents a location the master withheld"). Row 5 had already added a "Location" column but left it honestly disabled for that reason. This round adds real-looking values instead, following the Polish WMS row-rack-shelf-place convention (ARBL: Rząd-Regał-Półka-Miejsce) and BaseLinker's own shipped "Lokalizacja" field, which exists specifically to re-sort the picking/packing assistant's task order.

Every location value here — A1-02-03 and friends — is invented for this mockup, not read from anywhere real; every place it appears carries a spec. tag rather than blending in as a verified field. "Group by location" is no longer disabled — checking it re-sorts the item list by bin code and inserts a zone header per location, the actual mechanism BaseLinker's help docs describe rather than a cosmetic toggle.
