#1965 · Listings redesign

Listings — human-readable rows and lifecycle tabs

Interactive mockup for issue #1965. The tabs, search, channel filter and counts below are live — they compute from one data array, so the behaviour matches what the real page would do. Every colour, radius and spacing value is transcribed from apps/web/src/index.css.

Three claims in the issue are wrong, and they shrink the work. The linkedProductId-missing condition is not computable — an unmatched offer never becomes a row at all (offer-mapping-sync.service.ts:89-119). offer_status_snapshots is not product-keyed — it is unique on (externalOfferId, connectionId), a plain join (offer-status-snapshot.orm-entity.ts:28-30). And .tabs__count already exists (index.css:5578+). The real gap is two columns, not six — see the last section.

Quantity † Channel-side available_quantity; OUT OF STOCK at 0 Deliberately not product.stock — what the channel thinks it has is what decides whether it sells.
Updated lastStatusSyncedAt, via <TimeDisplay> Corrects the issue, which assumed OfferMapping.updatedAt. The snapshot's own timestamp says when the channel state was last read, which is the question the column actually answers — and it is already available. Formatting is the project-wide one: formatDateTime (shared/format/format-date.ts) — dateStyle: 'medium' + timeStyle: 'short', which in pl-PL reads 30 lip 2026, 16:05. The year stays: a listings table spans months, so a year-less date is ambiguous the moment a row crosses into January. Machine-readable value on the datetime attribute, never invented per page.

No status column. The tab already states the lifecycle, so a badge on every row would repeat it. A badge appears only when a row departs from its tab's nominal state — ACTIVATING mid-transition, REJECTED when the marketplace validator refused it.

Four follow-ups this mockup surfaced

Blocking Materialise price + quantity on GET /listings. The single backend change this redesign needs.
Product gap Unmatched offers are invisible in OpenLinker. offer-mapping-sync discards them without writing a row (no_deterministic_match, ambiguous_ean, ambiguous_sku…), so a seller has nowhere to see that an offer on Allegro isn't matching the catalog. This is the real problem the issue was reaching for with its linkedProductId assumption — worth its own issue.
App-wide Numeric columns are not actually right-aligned anywhere shared. The convention is right-aligned mono + tabular — declared 14 times as align: 'right', documented in .claude/rules/ui-components.md:182, and canonical in patterns-section.tsx. But .data-table__cell--right (index.css:2770, specificity 0,1,0) loses to .data-table th, .data-table td { text-align: left } (index.css:2797, 0,1,1) on both specificity and source order, so the class is dead. Orders and Products each wrote their own --end stack class to work around it; Sync jobs, adapters catalog, connection diagnostics and dashboard did not, and render left today. One-line fix: .data-table td.data-table__cell--right. This mockup assumes the fix — its Price column relies on the shared rule.
One line .channel-pill has no selector for Erli or WooCommerce. --channel-erli and --channel-woocommerce are defined (index.css:288-293) but unwired (:9242-9245), so both render a grey dot today. This mockup shows them correct.
