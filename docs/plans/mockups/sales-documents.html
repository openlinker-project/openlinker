Frontend plan · Operations

Sales Documents: from an invoices-only screen to a kind-aware one

/invoices only ever knew about invoices. A fiscal receipt never gets a row there, and opening one by its record id dead-ends. /orders already solved exactly this problem for the per-order view — this plan carries that same solution over to the operational list.

route: /invoices → /sales-documents reuses DocumentKindGlyph + resolveSalesDocumentCellState needs one new backend endpoint (keyset-paged) revised after 3 independent reviews — see §08

01 What's actually broken

Confirmed live on ol-demo-fresh, not guessed. Two facts, and they compound:

TODAY — /invoices
Every row on this screen is an invoice. The subtitle even hardcodes "regulatory (KSeF) status" — a Polish-invoicing detail on a screen meant to cover every connected provider. A fiscal-receipt order simply has no row here at all; it isn't filtered out, it was never queried.
ALREADY WORKS — order detail
A fiscal receipt renders correctly here: kind label, registered timestamp, its own field set.
ALREADY WORKS — order detail
An invoice on the same panel, same shell, its own fields and actions (correction, email, PDF).

The vocabulary for "one sale, one of two possible documents" already exists and already ships — it's on /orders and on the order-detail page. Nobody carried it over to the operational list. That's the actual bug behind "wyskakuje faktura": clicking through from a receipt-routed order towards the invoices screen hits a page that only understands invoices — at best a dead end, at worst a confusing, wrong-labelled flash of "Invoice" for a sale that never had one.

02 One naming collision to resolve first

"Sales documents" is not a free name — it's already the title of /settings/sales-documents, the per-country routing-rules page (which connection issues what, and when). Renaming the Operations list to the same words gives the sidebar two entries that read identically, in two different groups, about two different things.

What actually moved

  • Kind column — the same DocumentKindGlyph silhouette used on /orders: a folded page for an invoice, a torn slip for a receipt, a struck circle for "routing hasn't decided." Colour-free by design — kind is an entity axis, not a health signal. The word beside it is never dropped at any viewport (see "Small screens" below) — the glyph alone isn't a reliable identifier at 14px.
  • One Status word instead of two columns — resolveSalesDocumentCellState already names the most actionable fact per kind ("Authority rejected" outranks "Issued"; "Unconfirmed" for a receipt that failed without a rejection). Moving that logic here means it's reused, not re-derived a second, possibly-drifting way. REVISED A short reason subline now sits under the word for every row that isn't "done" — the actual text SalesDocumentCell already computes as reasonDetail, truncated to one line. This is the fix for losing the popover's "why": the reason lives in the row, not only behind a click.
  • Amount column REVISED — the native order total in the document's own currency (never summed across currencies — see the KPI note below). This didn't exist in the first draft; a screen whose job is "did we bill this correctly" needs a number on every row, not just a status word.
  • KPI strip + duplicate alert banner REVISED — mirrors the `/orders` health-card pattern. The duplicate count gets its own red tile AND a dismissible banner with a direct link to a filtered view, replacing the first draft's small in-row badge as the only surfacing (see §04a).
  • "Clearance ref." → "Regulatory ref." — same column, generalised label; carries a KSeF reference for an invoice. REVISED A receipt row now reads not applicable in italics, not a bare dash — a dash reads as "pending," and a receipt structurally has no regulatory-clearance rung at all (§16 of the architecture doc). The two states must look different.
  • Kind filter replaces nothing — it's additive, sitting first because it's the one axis that decides which other filters even make sense. REVISED See §04b for exactly how Kind narrows Status, and how "Routing not set" became a first-class, filterable value rather than only a row you might scroll past.
  • Free-text search REVISED — order id, regulatory ref, and buyer tax id in one box. Wasn't in the first draft; "find the document for order #X" is the single most common support-agent task on a screen like this.
  • Segment chips REVISED — All / Failed / Routing not set / Duplicates, the same non-partitioning-filter-chip pattern the architecture doc already uses for `salesDocumentBlocked` on `/orders`. Duplicates gets its own chip rather than living only in a badge nobody clicks on.
  • Bulk selection bar REVISED — kept from day one, not deferred (see §04c) — with per-kind action availability so a mixed selection can't fire an invoice-only action against a receipt row.
  • Subtitle drops the hardcoded "(KSeF)" and adds one sentence stating the kind is the operator's own routing decision, not OpenLinker's (§08, legal finding).
  • Top-right link, "Document routing" — one click to the settings page from §2, in the PageLayout actions slot exactly like /connections's "New connection" link. This is the list's own configuration screen, so it belongs on the list.
  • Accessible name construction, reused not reinvented REVISED — the row's trigger/link carries the same spoken-state aria-label SalesDocumentCell already builds (kind + word, plus the dupe sentence when present), rather than a new one hand-written for this list. Flagged by the UX review as unaddressed in the first draft.

§04a — The duplicate signal, promoted

All three reviews flagged the first draft's small badge as disproportionate to what it represents: the architecture doc calls a second document on a different connection "a legal event" (ADR-041) — a double-billing / double-registration risk, not a routine list-scanning nuance. It now gets three surfaces instead of one: a red KPI tile in the header ("Duplicates: 1 order"), a standing banner beneath it that names the count and links straight to a filtered view, and a dedicated segment chip. The in-row badge stays too — clicking any of the three lands on the same filtered/detail view, so there's no fourth, disagreeing surface to keep in sync.

§04b — How Kind and Status interact

Selecting a Kind narrows Status to that kind's own closed vocabulary — an invoice offers Issued / Issuing / Failed / Authority rejected / Cleared, a receipt offers Pending / Registering / Registered / Unconfirmed / Rejected. With "All kinds" selected, Status shows the merged list grouped under two labelled headings in the dropdown (native <optgroup>, same as the app's existing Select primitive already supports) — never one flat 10-item list where "Rejected" could mean either an authority-rejected invoice or a rejected receipt with no way to tell which you're filtering for. "Routing not set" is a first-class Kind value (third option, after Invoice / Fiscal receipt) — the first draft only showed it as a row state with no way to isolate it, and "why didn't this order get a document" is at least as common an investigation as "did this one succeed."

§04c — Bulk actions, kept from day one

The current /invoices page already has bulk retry/issue; the first draft's mockup silently dropped the bulk bar and only mentioned "kind-aware bulk actions" as a Phase 3 stretch, which read — correctly, per two independent reviews — as bulk retry disappearing for the whole of Phase 1–2. It doesn't. The bulk bar ships in Phase 1, unchanged in spirit from today, with one rule added: an action is enabled only when it applies to every row in the current selection. Selecting a mix of invoices and receipts (as in the mock above) disables both "Retry invoices" and "Reconcile receipts" with a tooltip explaining why, rather than firing an invoice-shaped action at a receipt row or vice versa. This needs no new receipt-specific action to exist yet — "Reconcile receipts" can ship disabled-with-a-reason ("not built yet") until it's real, exactly like the style guide's disabled-checkbox-with-a-reason convention for an unavailable capability.

§04d — Empty, loading, and partial-failure states

Not addressed at all in the first draft — flagged by the UX review as a real gap for an implementation-ready plan. Four states, matching the app's own async-UX baseline:

  • First-run empty ("No sales documents yet") — a fresh install or a connection with nothing routed. Copy points at /settings/sales-documents, not a generic "nothing here."
  • No matches for these filters — distinct copy from the above; offers "Clear filters," never implies the install has no data at all.
  • Partial failure (Option B specific) — if the invoice half of the merge succeeds and the receipt half fails (or vice versa), the list renders the half that succeeded plus a standing banner ("Fiscal receipts are temporarily unavailable — showing invoices only"), rather than blanking the whole page or, worse, silently showing an incomplete list with no signal at all. This was raised by two reviews as a correctness question, not just a UX one.
  • Total load failure — the existing `ErrorState` primitive with retry, unchanged from today's `/invoices` page.

§04e — Small screens

Flagged as unaddressed by the UX review, and it shouldn't have needed a flag — /orders already has a mobile card layout, and SalesDocumentCell was already built with a layout: 'row' | 'stack' prop specifically for this. This list reuses the same split: below the existing table breakpoint, each row becomes a card carrying Order, Kind + Status (with its reason subline), Amount, and Connection; Regulatory ref. and the exact issued timestamp move into the card's expanded state, mirroring how the order-row card already prioritises fields today.

§04f — What we're deliberately not building yet

Three items came up across the reviews that are real but out of scope for this pass — named here so they're a decision, not a silence:

  • CSV / accounting export. A finance team will eventually want to hand a period's documents to bookkeeping. Not in Phase 1–2; filed as a follow-up once the merged list itself is stable.
  • A dedicated country filter. Connection already narrows by country indirectly (a connection serves one market); a first-class country facet needs country metadata surfaced on the connection picker itself, which is a connections-feature change, not a list-page one. Revisit once /connections exposes country in its own filters.
  • Buyer-tax-ID filter under PII hash-only mode. Under OL_STORE_PII=false the raw tax id is never stored, so the filter can't do a text match. It degrades to a presence/absence toggle ("has a tax ID" / "asserted none" / "unknown") in that mode — same three-state vocabulary the architecture doc already uses for buyerTaxId, not a new one invented here.

What about the /orders popover? REVERSED

Nothing ever changes on /orders — that popover stays exactly as it is, unchanged, regardless of anything below. This section is only about the new /sales-documents list.

The first draft of this plan dropped it there too, arguing the row itself already carries enough (kind, status, amount, reference, connection, date are columns, not a compressed cell) that a popover's job was redundant. That held up on paper and felt wrong in the actual mockup — a screen an operator scans 50 rows deep needs a place to see identity facts, a duplicate warning, and fire a quick action without committing to a full-page navigation per row, exactly the job the popover already does well on /orders.

So it's back — the identical SalesDocumentCell popover, reused verbatim rather than redesigned, reachable by clicking the status word (the interactive mockup above uses it live). Two things sit alongside it rather than competing with it: the short reason subline (§04) stays, so the "why" is visible while scanning and doesn't require a click at all; and the detail page (§5) still exists, one level deeper, for the identity/regulatory history and any correction action — reached from the popover's own "View document" link, the same way the real component's "Open order" link already reaches its own deeper page. Nothing here is a new interaction pattern; it's the one the app already has, applied to a screen that turned out to need it just as much as /orders does.

05 Detail page

Don't design a third detail layout. The "Sales document" panel already on order-detail (the two screenshots in §1) is the right shape — extract its body as a shared component and give it two thin routes:

/sales-documents/invoice/:recordId→renders <SalesDocumentDetailBody kind="invoice">
/sales-documents/fiscal-receipt/:recordId→renders <SalesDocumentDetailBody kind="fiscal-receipt">

Explicit :kind in the URL means no backend "which table does this id belong to" lookup is ever needed, and a bookmarked or shared link can never point at the wrong kind of page.

A fiscal receipt never renders a correction or edit action — structurally, not just visually

Flagged by the legal review as the sharpest risk in "extract the shared panel and reuse it": the architecture is explicit that a KSeF correction is a new, linked document, never an edit of the original — and a fiscal receipt has no correction path documented anywhere in the fiscalization context (§16). Reusing one component for both kinds is still right, but the action row must be built as a per-kind allowlist inside SalesDocumentDetailBody itself — kind === 'fiscal-receipt' never even evaluates whether a correction action exists, rather than the component receiving a generic actions prop that a future edit "for consistency" could quietly populate for both kinds. This line goes in the component's own header comment, not just in this plan, so the constraint survives the person who wrote it.

06 The real lift: there's no backend endpoint for this today

Checked against the actual code, not assumed. GET /invoices only ever queries invoice_records. GET /fiscal-registrations requires an orderId and returns one order's records — it isn't a pageable, filterable list at all. And ADR-065's shared "sales document" projection is built to answer "for these order ids, what does each one have" — the shape /orders and order-detail need — not "give me page 3 across every order." A merged operational list is new work, not a widening of something that exists.

Two ways to build it

A — one SQL query, unioned. A single projection over invoice_records ∪ fiscal_registration_records, one shared pagination. The most "correct" shape, and the bigger lift.

B — two paginated queries, merged in application code. Fetch each table's page, sort by issue date, cap the combined page size. Cheaper, ships sooner, and matches what the architecture docs already conclude for this data volume (tens of orders a day, not thousands) — a joined read model was explicitly not judged worth it at this scale for the adjacent per-order projection.

REVISED — plain OFFSET pagination is not safe for Option B, and the first draft missed it

Both the UX and e-commerce reviews caught the same bug independently: paging two independently offset-paginated sources and merge-sorting them in application code breaks the moment a new row is inserted into either table between page fetches — which happens continuously on a live install issuing documents in real time. Every OFFSET past that insertion point shifts, so a row can be silently skipped or duplicated across the merged page boundary. For a page whose entire reason to exist is "did we see every document," a silently-skipped row is a materially worse failure than slow pagination — and it gets rarer to notice at low volume, not safer, which means it can go unnoticed until a reconciliation comes up short with no error anywhere to explain why.

The fix, still inside Option B's cost envelope: page each source by keyset (issuedAt, id as the cursor), never by OFFSET. A keyset cursor is stable under concurrent inserts — a new row lands before or after the cursor and never shifts what's already been read — so the two sources can be paged and merged safely without a SQL union. This is strictly an implementation detail inside Option B (same two queries, same application-side merge); it costs nothing extra in scope, only in not reaching for the default LIMIT/OFFSET shape.

Recommendation: ship B — with keyset pagination — first. Revisit A only if real usage shows a pain B can't absorb; building the union query speculatively is the more expensive way to learn we didn't need it.

Audit note (legal review): this merge is presentation-only. invoice_records and fiscal_registration_records stay independently queryable exactly as they are today — nothing about building a merged read changes either table's own history, and an auditor asking "prove we issued this on this date" is answered from the same source table as before, not from the merged view.

07 Rollout, in four steps

Phase 0 — stop the bleeding

no backend change · ~30 min
  • Redirect a receipt's record id at /invoices/:id to its order, instead of a dead end.
  • One honesty line under the current list header: "Fiscal receipts aren't listed here yet — open the order to see one," with a link.
  • Drop the hardcoded "(KSeF)" from the subtitle copy.

Phase 1 — the new list

new backend read (Option B, keyset)
  • GET /sales-documents: merged, filterable across both record types, paginated by keyset (§06 revision) — not OFFSET.
  • Amount column + header KPI strip (documents, amount, failed, duplicates) — §04's "no money on a finance screen" fix.
  • Duplicate segment chip + banner (§04a), not just an in-row badge.
  • The row-level popover — the existing SalesDocumentCell component, reused unchanged, reachable by clicking the status word — for identity facts, the duplicate warning, and a quick action without leaving the list.
  • Kind ↔ Status filter interaction (§04b), free-text search, "Routing not set" as a filterable Kind value.
  • Bulk selection bar ships here, not deferred (§04c) — per-kind action availability from day one.
  • Empty / no-match / partial-failure / error states (§04d), and the mobile card layout (§04e).
  • FE: move resolveSalesDocumentCellState into the shared features/sales-documents barrel so both /orders and this list import the same function — never a second copy that can drift.

Phase 2 — the rename

small, mostly strings + routing
  • /invoices → /sales-documents, with a redirect kept for a release.
  • Nav label, page title, settings page title (§2), the operator-configured-not-OpenLinker-decided subtitle line (§08, legal finding).
  • Detail route split by kind, reusing the extracted panel component, with the correction/edit action allowlisted per kind — a receipt never gets one (§5).
  • Top-right "Document routing" link. /orders' own popover is never touched by any of this — it's a separate instance of the same shared component (§04).

Phase 3 — stretch, explicitly named rather than left silent

once the above is live
  • A real "Reconcile" action for receipts (the bulk bar already reserves the slot, disabled, from Phase 1).
  • CSV / accounting export (§04f).
  • A first-class country filter, once /connections itself exposes country (§04f).
