OpenLinker · Orders · #2081

Where packed goes

Two new signals need a home in the orders list — packed state and marketplace returns. The row already carries six badges. Decided: option A, and the reason turned out to be one the market leader supplied.

The brief changed once I looked

What the inventory found

Issue #2081 was written on the premise that the order row is a pile of competing status badges with no precedence between them. That is partly wrong, and the correction matters more than the original complaint.

A consolidation pass already happened. The code carries the marks: Merged dispatch column (#1713) and Merged money column (#1713). The row is deliberately organised into three semantic groups, each with one primary badge and subordinate detail beneath it.

Counted from orders-list-page.tsx on main. Worst case a single row renders six badges — but grouped, not undifferentiated.

So the honest question is not “fix the crowded row”. It is narrower, and answerable: where do two new signals sit inside a structure that already works — and does the Shipment group survive another one.

Operator-defined statuses live in a left sidebar as collapsible folders, each with a count badge tinted its own colour. The status also repeats as a pill in the row.

Density comes from chips, not stacks

Rather than stacking pills, the row carries a fixed four-slot strip — delivery, payment, shipment, invoice — colour-coded grey / green / orange / red. You scan for red instead of reading labels.

$ F ▣ ✎

Packing is invisible in the list

There is no packed column and no packed icon. Packing state shows only as whatever status an automatic action moved the order into — and there is no board, no drag: transitions are bulk-select, automated, or scanner-driven.

Screenshots may predate the base.com rebrand — patterns are trustworthy, pixel details are not.

The asymmetry that decides this. BaseLinker can omit a packed signal from the row because its status folders already carry it — an operator makes a “Packed” folder and the folder is the signal. OpenLinker deliberately did not build operator-defined stages, so it has no substitute. The upstream omission is not evidence the signal is unwanted; it is evidence their information architecture carries it somewhere else. That is the real argument for putting packed in the row.

Three placements

Dashed outline marks what is new

Packed and returns are different kinds of signal, and giving them the same treatment is the first mistake to avoid. Packed is a position in a workflow — it happens before dispatch. A return is an exception — it happens after delivery, and it means something went wrong.

Option A · recommended

Shipment column reads as time

Packed joins the head of the Shipment stack, so the column reads top-to-bottom in the order things actually happen: packed → shipped → due → delivered by whom. Returns go to the Status group, where exceptions already live, beneath the health badge.

Why it works

Chronology is real information, not decoration. The column becomes scannable as a sequence rather than a list of unrelated facts.

Deliberate

Packed uses a tick, not a pill — it is a binary fact, and badges are already carrying four different vocabularies.

Cost

Shipment goes to five signals on a worst-case row. Carrier and the delivery chip may need to become hover detail.

A, refined · borrowed density

Chips pay for the extra line

Option A’s one real cost is row height — Shipment goes to five signals. The market leader’s answer to exactly this problem is chips instead of stacked pills. Apply it to the Money group: payment and invoice become two compact chips on the total’s line. Money loses two lines, Shipment gains one. Net row height goes down.

Why it works

The height cost that made A arguable disappears. Money is reference data — you glance at it — which is exactly what chips are good at.

Deliberate

Only Money converts. Status and Shipment keep labelled badges, because those are read, not glanced at.

Cost

A chip is less legible than a label until learned, and it needs a legend. Accessibility rests on title plus the mobile card keeping full labels.

Option B

Packed gets its own column

A narrow, sortable Packed column. Treats packing as its own workflow — the operator works a pack queue, sorts by it, and clears it.

Deliberate

Channel is dropped to buy the width — it is the least-consulted column once connections are named on the detail page.

Cost

A whole column for one boolean, on every screen including the many operators who never pack. A filter already does most of this.

Option C

Add nothing to the row

Packed lives on the detail page and as a list filter only. A return shows as a small marker against the order id. The row keeps exactly the density it has now.

Why it works

The null hypothesis, and this project has rewarded it repeatedly. Nothing is added to a row nobody has complained about.

Deliberate

Filter-only still delivers the pack queue — the operator selects “not packed” and works the result.

Cost

Packed state is invisible while scanning. A supervisor cannot see at a glance what the floor has done.

Constraints any option must respect

Two are hard

  • The order-health partition cannot grow a bucket. Its five values must stay exhaustive and mutually exclusive, because the KPI cards must sum to the total — an invariant that exists to fix a real bug where orders fell into no bucket. So packed and returns are never health values. They sit beside health, never inside it.
  • No frontend-only vocabulary. deriveOrderHealth is a deliberate twin of SQL in the repository. A signal the backend cannot also compute can never become a server-side sort or filter.
  • Badges carry text, not colour alone. Both new signals read without colour perception — and a chip, which is colour plus one glyph, must therefore keep its label in the mobile card and a title on desktop.
  • Keep a status pill inside ~17 characters. Borrowed, not derived: BaseLinker reserves a 17-character “short name” for “space-limited areas like order tables”. It is calibrated against a table doing this job at higher volume than ours. Awaiting dispatch is exactly 17.

One thing I could not verify. The premise behind #2081 — that operators find the multi-badge row confusing — is untested. Nobody has been asked. If they read it fine and ignore what they do not need, Option C is correct and the rest of this page is a solution to a problem that does not exist. That question is worth one conversation before any of this is built.

Decision

Option A — recorded in the frontend style guide

Option A, because it adds information rather than surface: ordering the Shipment stack chronologically makes the column easier to read than it is today, before the new signal is even counted. Returns land where exceptions already live.

The chip refinement is the recommended form. It removes A’s only real cost, and it is a pattern proven at higher volume than ours rather than one invented here. If chips prove hard to learn, the fallback is A unrefined plus demoting carrier to hover detail — carrier is reference data, packed is a decision the operator acts on.

Option B becomes right the moment per-line packing ships, or if anyone wants to tick packed in the list — that would be the first in-place mutation in this table, a new interaction pattern, and its own decision. Both wait on the pack-station principal question.
