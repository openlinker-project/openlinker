Two gaps. Nothing carries the recorded match onto this screen — an operator hands over verbally. And the proposal's handoff link points at /invoices/:id, which has no correction action today; the real flow is this panel. That link is drift, not a design choice.

The two things to agree with

1. A grid over the invoice's own lines — not a card per returned line, and no picker. An earlier revision of this sheet asked the operator to choose which of two identical invoice lines a returned item belonged to. That question is unanswerable: the operator holds a parcel, both candidate lines carry the same product name, and InvoiceLine has no id and no SKU. It was also unnecessary. OpenLinker builds the invoice itself from order.items in order (order-to-issue-invoice-command.mapper.ts:113), and GET /invoices/:id/content (#2076) returns those lines index-aligned with the very array a correction addresses — so a row's position is its line number. The grid is therefore honest because it is built from the document, not from whichever lines happened to match by name. Every Polish invoicing tool a seller already uses has this shape: a recessed read-only “as invoiced” column, one editable column holding the quantity that should be there, and a computed credit. BaseLinker advertises the absence of line-picking as a feature. Both the quantity and the unit price are editable, because CorrectionLine carries newQuantity and newUnitPriceGross and the returns path used only the first — so a discount, an agreed reduction or a re-priced line was unexpressible even though the backend and every Polish invoicing tool support it.

2. The screen's subject is the refund that already happened. A marketplace refunds the buyer before the goods are even examined, so by the time this screen opens the money has usually moved. The question worth the operator's attention is therefore not “which line” but “does this credit note match what the buyer actually got back”. OpenLinker holds both figures and compares them nowhere today. That comparison is the loudest thing on the screen here, and the first thing it catches is delivery cost — which the current matcher can never credit, because it joins product names and a delivery line is not a product.

This screen needs backend work that does not exist yet

The grid is built from GET /invoices/:id/content (#2076), whose lines are index-aligned with the array a correction addresses — so a row's position is its line number and nothing has to be guessed. That read is shipped. Four things it depends on are not.

1. The matcher narrowing. The join itself is done — ReturnLine.resolvedOrderLineId is resolved at ingestion (#3171/#3172) and is trustworthy. What is not done is narrowing return-correction-matching.domain-service.ts onto it: the matcher still joins by product name and can still emit status: 'ambiguous' with a candidates list for a line this grid has no row shape for — a 'proposed' outcome can carry one of those today. Until the matcher is narrowed, OpenLinker cannot pre-fill a single quantity, because a name-joined match is not trustworthy enough to act on. The data needed to do it is already in hand at ingestion — the return carries offerId and unitPrice, and the invoice is built from order.items in order.

2. The refund figure. The reconciliation compares this credit against what the channel already refunded. OpenLinker holds both numbers and no read exposes them together.

3. Already-credited quantities. Nothing tracks how much of a line an earlier return already credited, so a second return can over-credit the same line. This is a correctness hole, not a convenience: Business Central and Comarch ERP Optima both gate on it.

4. Shipping. Delivery is a real invoice line, so it appears in this grid — but the current matcher joins product names, so it can never be matched, and delivery is today silently never credited. A buyer who withdrew within 14 days is owed the cheapest delivery option back.

Also unbuilt and out of this epic: a correction in a currency other than PLN cannot be filed (KursWaluty is implemented nowhere), and a line the seller resolved by sending a replacement would still be offered for credit.

State index — cite these names in the sub-issues

Every value below is settable without a click — open the file with ?state=<name> (or #state=<name>, which also responds to a hash change). An E2E baseline loads the state it wants and asserts on the attribute; it must never drive this sheet by synthesising clicks on the switcher, or the baseline ends up testing the switcher instead of the screen. An unrecognised name is ignored rather than silently rendering the default, so a typo in a ticket reads as “nothing happened” and not as a wrong screenshot.

Which attribute holds what. body[data-state] is the state in force — a page state outranks a credit state, because it replaces the panel outright. body[data-credit-state] and body[data-page-state] always hold their own family's current value, which is where page-loaded lives: it is the absence of a page-level override, so it is never the state in force and never appears on body[data-state]. Cite body[data-page-state]="page-loaded" for that one. The per-element data-state attributes stay and say WHERE each state renders, which is a different question from which one is showing. For the implementer. Tokens are verbatim from apps/web/src/index.css. Two drifts are reproduced, not fixed: .text-muted has no rule despite 116 uses, so the app renders those spans in --text-primary; .dialog__head / .dialog__desc do not exist. Classes .returns-credit-note, .credit-grid, .credit-cell--* and .infotip are proposed here, per the #3147 precedent. The shipped copy string RETURN_PROPOSAL_COPY.reviewCta (“Confirm these matches”) is rendered nowhere today and becomes Issue credit note — a rename, not a new string.

Two things the grid leaves for the implementer. The price cells are <input type="number">, which always renders and accepts a dot, while the “as invoiced” column renders a Polish comma — a seller types 189,00. Use a text input with locale parsing (accepting both separators) rather than shipping the mismatch. And the unit price shown here is gross, derived as line.gross / line.quantity, because that is the unit a correction asks for; IssuedDocumentLine.unitNet is the wrong field and its own type says so.
