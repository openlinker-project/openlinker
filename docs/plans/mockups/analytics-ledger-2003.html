#2003 · /analytics v1 „Ledger"

A business page that says what it does not know

OpenLinker can tell an operator whether the plumbing broke. It cannot tell them anything about the business flowing through it. This is the form, the states and the words for the page that can — assembled entirely from primitives that already exist.

Scope. No new shared/ui primitive — an acceptance criterion of #2003. Every token is copied verbatim from apps/web/src/index.css; every component below names the primitive and the line range it was transcribed from. Exactly ten new CSS rules are invented, isolated in section 5 of this file’s stylesheet and listed in frame 13. One thing on this page is a genuine scope addition and says so in frame 13: the period-over-period delta on the KPI strip, which the original scope note ruled out. Cells marked † need data that does not exist in today’s API. The operational dashboard at / is untouched.

Build
An enabled Apply is the only signal that the fields are ahead of the page. Everything below still reports 1 Mar – 15 Apr, so for this one moment the fields are a draft rather than the truth.
Rules
  1. That state needs exactly one carrier. A second badge saying „not applied“ would be a second place to forget to update.
  2. The draft is local and disposable: it never reaches the URL, cannot be linked, and a reload discards it.
InteractionWhat happensURL after
Operator clicks 30d Applies immediately. Writes absolute dates and refreshes every section — no Apply needed, because there is nothing to review. The range includes today: from = today − (N−1), to = today, so 30d on 5 Aug is 7 Jul – 5 Aug — thirty days counted inclusively, not thirty-one. The preset itself is not stored; only the dates are. ?from=2026-07-07&to=2026-08-05
Operator clicks Custom Keeps the dates exactly as they are, lights Custom, moves focus to From and opens its picker. Nothing below reloads — this click states an intention, it does not change a range. unchanged
Operator edits From or To Lights Custom and enables Apply. The fields are editable at all times, including while a preset is lit — typing a date is itself the way into a custom range, so there is no unlock step. unchanged until Apply
Apply — when it is enabled Only for a range that is complete, valid (From ≤ To) and different from the one in force. At rest it is disabled: with nothing to commit, an enabled button would promise an effect it does not have. —
Operator clicks Apply Commits the dates to the URL, refreshes every section, then re-derives which option is lit. If the typed dates happen to equal a preset, that preset lights and Custom goes dark — the operator gets the correct label for the range they built, not a memory of how they built it. ?from=…&to=…
Which option is lit Derived at commit time, never stored. A preset is lit iff from/to equals today − (N−1) … today; otherwise Custom is. Deliberately not recomputed on every keystroke: Custom preserves the dates, so a live comparison would re-light 30d the instant Custom was clicked and the option would be a radio with no effect. Custom therefore holds its selection from the click until Apply. —
Reload, or open a shared link Dates come straight from the URL, so the page renders the same figures it rendered for whoever sent it. Any pending draft is discarded — it was never in the URL. Open yesterday’s link and Custom is lit, correctly: those dates are no longer „the last 30 days”. unchanged
Field cleared An incomplete range cannot be applied — Apply stays disabled, so a half-typed range never reaches the URL. On commit, an empty string removes the param, matching setFilterParam (orders-list-page.tsx:965-976); a missing bound means „unbounded on that side” and lights Custom. ?to=2026-08-05
Day boundaries The URL carries dates only (YYYY-MM-DD) so the native input round-trips; they widen to UTC instants when the query is built — from → T00:00:00.000Z, to → T23:59:59.999Z. To is inclusive of that whole day (orders-list-page.tsx:268-273). —
Build
Absolute dates in the URL, never a relative preset. ?range=30d opened tomorrow shows a different thirty days — fine as a bookmark, wrong as a link. The spec settles it twice: the DoD requires that „a maintainer can reconcile a day’s revenue against the source“, and risk R2 states that a quietly-changed number is worse than no number.
Rules
  1. URL carries from/to only. Keeping range too lets them contradict (?range=7d&from=2026-01-01) and forces a precedence rule nobody will test.
  2. Derive the highlighted preset from the dates — that deletes the state instead of synchronising it.
  3. Apply is a draft buffer: #1986 keeps it in component state and writes the URL only on commit. The draft never reaches the URL and does not survive a reload.
  4. A preset needs no Apply; a typed range does, because From and To are entered one at a time and applying per keystroke would query a half-built range.
  5. Params are plain from/to. Do not reuse createdFrom/createdTo — those mean ingestion time, and this page filters order date (decision 2).
Watch out
No new primitives are needed, so do not build any. SegmentedControl takes four options like three, and Custom as permanent fallback keeps the group out of the „nothing checked“ state its roving tabindex supports (segmented-control.tsx:97). Apply is the existing .button--secondary at default height plus the shipped :disabled treatment (index.css:633).
Build
Three facts per channel, and the third is the one that matters. Freshness answers „is this current“, coverage answers „how far back does this go“, state separates a channel that is caught up from one still backfilling — decision 4’s second meaning of „pending“, a different fact from „ingestion stalled“.
Rules
  1. Freshness from connection_cursors.updatedAt, which only advances on real progress — failing that, MAX(sync_jobs.updatedAt) WHERE status='succeeded'.
  2. Coverage reads „data from“, never „complete since“: the window is not computable, and MIN(placedAt) is the closest honest approximation. The words must not promise more than it delivers.
  3. Channel names from connection.name, never platformType — an open string with no display contract.
  4. Rows stay at full size. This is the list of shops, not a status indicator that happens to list channels.
Watch out
Do not aggregate these rows to save height. An aggregate must be written pessimistically to stay honest — latest start, oldest sync, worst state — which makes it strictly less useful than the rows it replaced.
Build
Two kinds of note, and the difference is what changes. A row note is about one channel and moves with its state, so it stays inline, indented to that channel’s name. The standing caveat is the ⓘ on the section title: true of every row, and it never changes — a permanent full-width line is the most expensive way to say something the operator learns once.
Rules
  1. Row notes are one line. A caveat that needs a paragraph is a banner, not a note.
  2. The marker is a real <button> opening a Popover on click, which also answers hover and Enter. The mockup stands it in with title.
  3. Markers reuse what ships: no icon library exists here, and every inline status marker in the app is a Unicode glyph plus a colour class — .bulk-editor__infotip (index.css:10901) and .bulk-editor__warn-tri. Transcribing both keeps #2003 at eight invented rules.
  4. Each glyph is role="img" with an aria-label, never aria-hidden. Colour is never the only signal.
Watch out
Do not build the marker from shared/ui/tooltip.tsx. It opens from Radix’s onPointerMove, and that handler returns immediately when event.pointerType === 'touch' (@radix-ui/react-tooltip@1.2.8) — on a phone a tooltip is not awkward, it is unreachable.

03 · KPI strip Six pairs: what happened, and what qualifies it feeds #1990 · .status-strip + KpiCard (shared/ui/kpi-card.tsx) Ships partly · 6 of 12 figures blocked, plus all 6 deltas
Build
.status-strip + six KpiCard (shared/ui/kpi-card.tsx). Every card is a pair: a headline figure, and beneath a hairline on the card floor, the qualifier that would change the operator’s mind about it. Under the hairline, never beside the figure — a second number on the same line as a four-figure amount reads as part of it.
Rules
  1. One ⓘ per card, in the eyebrow: term, definition, formula, and the caveat that stops the figure being over-trusted.
  2. Delta on its own line under the figure, arrow after the number, basis stated in words („vs previous period“) — not only for screen readers.
  3. Rates move in points, never percent. Colour follows meaning: a falling return rate is a green down arrow.
  4. GMV and AOV render unconditionally (decision 3, reversed 14 Aug): the rate comes from the master on the order line, so no card waits on what a source declared. What GMV and AOV do inherit is the spec’s split — GMV gross and before discounts, AOV net and after them — which is why the ⓘ on the Revenue card says so outright. Orders and Units are untouched by [G].
  5. Revenue reads net-first (reversed 14 Aug): net sales is the headline, GMV the qualifier, and the ⓘ states them in that order. GMV is the half that renders, so this is the one card whose headline is blocked — ship it showing the qualifier alone rather than promoting GMV back into the big slot, where it would read as money kept.
  6. Sparkline (shared/ui/sparkline.tsx) only where a per-channel series exists. On Revenue that series is GMV’s, so the label says GMV trend — it now describes the qualifier, not the figure above it. Net sales has no daily series at all.
Blocked
Six of twelve figures and all six deltas. Mark each † on the figure, not the card — on four cards the other half ships. Three causes, three fixes:
Cancellation rate, cancelled value Spec A7, needs [C] — cancellation is a string in the order snapshot, never a state
Return rate, refunded value No return entity in the repo; spec §8, out of scope

Build
One reporting currency (the system’s main currency, PLN here), and every money figure stated in it. Counts are untouched: an order is an order in any currency. Decision 11 — the spec leaves the choice open only on condition it is “decided, not defaulted”.
Rules

Share is measured in units, not revenue

Revenue totals across every channel: every order line carries its own VAT rate, supplied by the master for the product and its delivery country rather than inherited from whatever a source reports. Share still counts units, because a unit means the same thing in every market and a converted amount does not.

Build
Decision 1 and 3, together, as settled on 14 Aug. The spec named gross-vs-net [G] the most dangerous item in the epic and it is right about the danger — but the danger is answered by one source for the rate, not by disclosing what each channel guessed: the master supplies a VAT rate code per (product, delivery country) and the order line carries it — OpenLinker never computes one. So every row on this table is already on one basis and the Tax column that used to qualify them is gone. What the adapters report is now a cross-check, not a verdict: Allegro and Erli send tax: 0, PrestaShop sends total_paid_tax_incl and declares nothing, and #2054 carries the rate from the master onto the line instead of asking anyone to reconcile the three. Until it lands: a line with no rate — and an order whose master and channel rates disagree — is excluded from the net aggregate rather than counted at gross, and the count of excluded orders is stated under the figure. A conflicted line shows no net/VAT split at all.
Rules
  1. Never derive Share from revenue. Share (units) is comparable across markets and currencies without a rate or a rate’s date — which is why the column is labelled in the header rather than left to be inferred.
  2. Frame 05 held the degraded twin of this table and is withdrawn; the per-currency twin is in frame 03b.
05 · By channel — state B Withdrawn: the total no longer refuses, because the basis is ours was: the degraded half of decision 3 · reversed 14 Aug 2026 Withdrawn · kept as a record
Build
Nothing. This frame is not to be implemented. It drew the by-channel table refusing to total revenue when one source reported net and the others gross. That state cannot arise under the settled model. The metric spec fixes the axis — „VAT calculated by country of delivery“ — and #2054 fixes who answers it: the master supplies the rate for the product and that country, and the order line carries it. So the tax basis is something every line already states, not something each source declares and the page reconciles. With one basis there is nothing to mix, so the total always renders and the Tax column is gone from frame 04.
Rules
The frame is kept rather than deleted because the argument it settled is still worth reading, and because a reader who finds the mixed-basis reasoning quoted elsewhere should be able to see that it was considered and reversed, not overlooked. What survives it:
  1. Mixed currency and mixed tax basis are still different problems, and the distinction outlives this frame. Two currencies can each be added perfectly well; what is missing is a rate, and a rate can be obtained and disclosed — so currency converts, and the page prints the method under the figure (decision 11, frame 03b). The old symmetry „basis degrades“ is what has gone.
  2. Share stays in units regardless (frame 04, rule 1). That rule was written to survive a mixed basis and it survives its removal too.
  3. Neither condition ever escalated to a page banner, and that line still holds: frame 11 draws it.
Watch out
The problem moved, it did not vanish — and it landed on #2054. Allegro and Erli report tax: 0 and PrestaShop declares no basis at all, so the rate has to reach the line from somewhere. It is not machinery OpenLinker builds: #2054 records the team decision that the master supplies the rate and OpenLinker never computes it. What is left is sequencing — ADR, order contract, master read, mapper fill plus the issuance gate, conflict state, and only then dropping the adapter defaults. Step one of seven has started. Until the rate reaches the order snapshot, a build reading only this file will reinvent the Gross? badge on its own — which is why the reversal is written here and in the handover rather than left as a silent deletion.
