Order-time FX stamping — every surface it touches

What an operator actually sees once each order carries a reporting-currency amount plus an immutable reference to the rate used. Tokens and component CSS transcribed from apps/web/src/index.css; primitives from apps/web/src/shared/ui/ (KpiCard, DataTable, StatusBadge, KeyValueList, Alert, Chip, FormField, Sparkline, PageLayout). No new colour, radius, shadow or spacing value is introduced anywhere in this file.

Read the frames as three different kinds of claim. In #2049's scope — only the settings tile; the plan's Phase 4 ships features/currency-settings/* and nothing else on the frontend. A page that does not exist yet — /analytics has no route, no feature folder and no consumer of GET /analytics/trust; it is #1986 / #1990 / #1991, and the frames below show what those issues have to render once a stamp exists. Not filed anywhere — the orders list and order-detail FX surfaces. The breakdown assigns every frame to one of those. A † marks a design decision taken in this mockup rather than settled by the ADR. All four are signed off and recorded on the relevant issues.

What every screen has to honour

Five constraints out of ADR-040. Each one is why a frame below looks the way it does — and each is a way to build the UI that would produce a plausible wrong number.

#ConstraintWhat it forces on screen
1 The reporting currency is a choice, and its default converts. Resolution is settings row → OL_REPORTING_CURRENCY → 'EUR'. Every reporting figure carries a currency label, and while nothing has been chosen it renders EUR (default) — never a bare EUR. The discriminator is the response's source !== 'setting', never a client-side comparison against 'EUR'.
2 Unstamped rows exist and never sum. Provider outage, missing placedAt, unsupported pair. No money figure ships alone — it is always paired with an unstamped count. A total with nothing beside it is a defect, not a simplification.
3 reportingCurrency IS NULL means unstamped — never exchangeRateId IS NULL. "No conversion needed" (same currency, exchangeRateId = NULL) has to read as a healthy state, visually distinct from "not converted". Conflating them discards the overwhelming majority of orders.
4 The stamp is immutable, so changing the setting splits history into eras. The settings change is a confirm that reports the already-stamped row count. Analytics warns when the selected range spans two reporting currencies.
5 The stamp is analytics-only and must never reach a fiscal document. Nothing in the invoicing UI reads it. On a PLN-reporting deployment both figures come from NBP table A and differ only by date — so each is shown with its own date and source, never as one number.

† Decided. Money is written as 48 210,00 PLN throughout, not 48 210,00 zł. The app's formatAmount uses Intl … style:'currency', which renders a symbol — but on a surface whose subject is which currency, two symbols are harder to tell apart than two ISO codes. An FX-surface-only deviation, not a global change.

1 · Config — the Currency tile on /settings

Named Platform → Currency, not Analytics → Reporting currency. The value is a property of the deployment, not a setting belonging to one module — ADR-040's own words are that the reporting currency is a property of the reporting entity, and analytics is merely its first consumer. The scope is stated in the tile's body copy, where it can be precise, instead of in its name, where it would either under-claim (analytics-only) or over-claim (implying invoices use it).

One system-level setting on the ai_provider_active_setting singleton shape: GET /currency-settings + PUT /currency-settings/reporting-currency, both @Roles('admin'). Structure copies posthog-settings-tile.tsx — an article.panel.panel--dense inside settings-page.tsx's .workspace-grid, with panel__header (eyebrow + section-title + panel__meta), context-chip badges, a definition-list, and an Edit button opening a dialog. The <select> is fed by the response's supportedCurrencies, which is what makes the 400 / 422 paths unreachable from the UI.

1d What the tile deliberately does not offer two absences that a reviewer will ask about

No per-connection currency field

An earlier draft of the ADR put config.fx.reportingCurrency on the connection. It was deleted: per-connection values make a deployment-wide total impossible by construction, which is the problem this feature exists to solve. Connection.config.currency (#362) keeps its single existing meaning and is not consulted.

No lock after the first stamp

Also rejected: the default converts and nobody chose it, so a lock would make an unchosen default permanent — one foreign-currency order and a deployment that never opened this page is stuck in a currency it was never asked about.

6 · Invoicing — the boundary, made visible

ADR-040's sharpest consequence: a stamped figure must never reach a fiscal document. The two differ on all three axes that define a rate — date (placement vs the tax point, which for a prepaid marketplace order is the payment instant no shipped source persists), target (always PLN statutorily), and derivation (a statutory rate must be a directly published quote, never inverted or pivoted). This bites hardest where it looks safest: on a PLN-reporting deployment both come from NBP table A and differ only by date, so the two rows look interchangeable and are not.

A 0,70 PLN difference on one order — small enough to read as a rounding bug and large enough to break a reconciliation. It is neither: they are answers to different questions, and no arithmetic recovers one from the other. Never test exchangeRateId IS NULL for "unstamped"

It is NULL on the same-currency path too — the overwhelming majority of orders. A revenue query written that way silently reports almost nothing and looks like a business collapse. The discriminator is reportingCurrency IS NULL.

fxStampedAt IS NULL does not mean "unstamped" either

It is also NULL on a deferred row, which is legitimately still in flight rather than unstampable. The reconcile sweep deliberately uses both — fxStampedAt IS NULL AND reportingCurrency IS NULL — because it wants exactly the first two states and nothing else.

9 · How the work gets filed

Per the house rule — one issue, one branch, one PR — #2049 stays a single implementation issue and does not get split by phase or by risk. What it got instead is six native sub-issues mirroring the plan's phases, so progress is visible inside one branch. Everything below that is either genuinely separate work or an acceptance-criteria edit on an issue that already exists.

Filed — #2049 is now a mini-epic with six native sub-issues

#2122 Phase 0 shared calendar · #2123 Phase 1 currency context + integrations-fx · #2124 Phase 2 persistence · #2125 Phase 3 stamp, retry, sweep · #2126 Phase 4 settings API + tile + env · #2127 Phase 5 docs. All six linked as GitHub sub-issues; #2049's body carries the ordering, the ECB blocker and the four design decisions taken here. One branch 2049-order-fx-rate-snapshot, one PR closing all seven.

Not filed — the three new issues and the five body edits

Everything in Wave 2 and Wave 3 below, plus the acceptance-criteria edits on #1985 / #1987 / #1988 / #1990 / #1991, is written and ready but not created — it was not part of what was approved. Say the word and it goes up as specified.

No open blocker — an earlier version of this page said otherwise, and was wrong

ECB's historical endpoint was treated here as an unresolved Phase 1b blocker. That came from PR #2050's description, which described an earlier draft rather than what merged: the plan's ECB reference rates subsection in main is verified against the live API, and an independent re-verification reproduced every claim in it. Every phase is unblocked, and the ordering below is pure dependency rather than risk.

The re-verification did surface a latent bug, now recorded on #2123

includeHistory=true combined with lastNObservations=1 injects a phantom row — ACTION=Delete, an empty OBS_VALUE and an unrelated historical date — so an adapter reading "the last row" would get an empty rate and a nonsense date. Alongside seven other additions: a 4xx body may be HTML rather than JSON, the empty-200 response is zero bytes in every format, the maximum non-publication run is 4 days, and ECB publishes no document identifier at all — its header.id is a fresh UUID per request — so the audit reference has to be a re-executable locator OpenLinker constructs, which is a design gap to state rather than paper over.

The two new issues, in full

[TASK] Frontend — surface the FX stamp on the orders list and order detail

enhancement
Problem / Context

#2049 persists six FX columns on order_records and ships exactly one frontend surface — the reporting-currency tile at features/currency-settings/*. Nothing renders a per-order stamp, so the product cannot answer the first question anyone asks of a converted figure: which rate, from when, from where. Today orders-list-page.tsx:846-901 renders only the native total via formatCurrency(parsed.totals.total, parsed.totals.currency, locale), and order-totals-panel.tsx:17-43 renders every row in totals.currency alone. An operator reconciling an analytics figure against a bank statement has psql and nothing else.

Worse, the five persisted states are indistinguishable without UI. "No conversion needed" (same currency, exchangeRateId NULL) and "not convertible" both render as a bare native total, and the first is a healthy fully-counted order while the second is excluded from every money figure on /analytics.

Proposed Solution
  • Orders list — a fourth line in the existing .orders-cell-stack--end of the merged money column, styled like .orders-cell-sub, plus a compact StatusBadge for the stamp state. No new column, no wider table.
  • order-health-summary.tsx — a fourth cell, Reported as, with the rate as its __hint. Drop the ≥768px grid from repeat(3, …) to repeat(4, …).
  • order-totals-panel.tsx — one .order-totals__row--reporting under --total; and the FX disclosure line appended to the existing .order-pricing__note, which already carries the "buyer-paid price, source-authoritative" provenance sentence.
  • New .detail-section — Currency conversion, a KeyValueList carrying native total, reported amount, the multiplication, rate, rate date, rule, source + document reference, stamped-at, and the rate-record id. Derivation legs render as a nested list when the rate was inverted or pivoted.
  • One shared state→label/tone map so the list badge and the detail heading cannot drift; five labels — Converted, Native, In flight, Not convertible, Before FX.
  • Read from the existing order detail response — no new endpoint if #2049's response DTO exposes the six columns. If it does not, that DTO change belongs here.

[TASK] Full-Stack — unstamped-coverage read and its disclosure on /analytics

enhancement
Problem / Context

ADR-040 § Consequences: "any figure must be paired with an unstamped count." Nothing produces one. #1987 returns revenue, order count, AOV, median and units; #1988 returns ranked products. Neither reports how many orders in the range carry no stamp, why, or what their native value was — so the frontend has no way to satisfy the constraint even if it wants to, and the honest reading of a revenue figure is unavailable.

Two second-order traps come with it. Denominator drift: revenue narrows to the stamped set while unit and order counts do not, so AOV computed as revenue / orders under-reports by whatever share is unstamped — a plausible wrong number on the page's headline card. Era split: a range spanning a reporting-currency change has no single figure at all, and ADR-040 forbids re-converting a stamped amount to manufacture one.

Proposed Solution
  • Backend — extend the #1987 aggregates response rather than adding an endpoint: reportingCurrency, the stamped order count used as the money denominator, and a coverage block — total in range, stamped, deferred, terminal-by-reason, and the unstamped rows' native totals grouped by their own currency (never summed).
  • Report an era list when the range spans more than one reportingCurrency, and return no single revenue figure in that case — the response says a single figure cannot be given, matching the shape #1987's acceptance criteria already use for mixed currencies.
  • Frontend — a Not converted KpiCard in the .status-strip when the count is non-zero; an Alert tone="warning" below it breaking the count down by reason with .alert__count numerals; the era-split Alert tone="error" with a narrow-the-range action; a no convertible orders empty state that distinguishes itself from "no sales"; and a · PLN suffix on every money column header and KPI label.
  • Every money figure renders the denominator it used. AOV divides by the stamped count, and says so.
Classification

Type: CORE + Frontend Layer: Application + Interface

  • libs/core/src/orders/… — the aggregates read introduced by #1987
  • apps/api/src/…/analytics — response DTO
  • apps/web/src/features/analytics/* — created by #1986/#1990
Dependencies
  • #2049 — the columns. Hard blocker.
  • #1987 — the aggregates endpoint this extends. Hard blocker.
  • #1986 / #1990 — the page shell and KPI strip this renders into.
Assumptions
  • Extending #1987's response beats a second endpoint: the two reads share a date range, a cancellation filter and a connection scope, and splitting them invites a UI that renders a total before it knows whether the total is honest.
  • If #1987 has already shipped by the time this starts, this becomes an additive response change and the filing stands unmodified.
Acceptance Criteria
  • The aggregates response carries the resolved reporting currency, the stamped denominator, and an unstamped breakdown by reason
  • Unstamped orders' native values are reported grouped by their own currency and never summed into the reporting figure
  • A range spanning two reporting currencies returns no single revenue figure and states why
  • AOV is computed over the stamped denominator, and the UI names that denominator
  • Every money figure on the page carries its currency where it is consumed — a screenshot of one table is unambiguous
  • A range with orders but no stamped orders renders an empty state that distinguishes itself from "no sales" and names the cause
  • Unit and order counts are unaffected by stamping, and any table mixing them with money states which denominator each column uses
  • Integration test: a range with one stamped, one deferred and one terminal order returns exactly one revenue figure and a breakdown of two
  • No architecture boundary violations (CORE ↔ Integration; shared imports nothing upward)

[TASK] Infrastructure — demo seed with foreign-currency PrestaShop orders and matching rates

dx
Problem / Context

#2049 states the consequence rather than fixing it: the demo will show the unstamped path, not a conversion. There is no OL-side order seeder at all — zero INSERT INTO order_records repo-wide — and docker-compose.yml:229 sets PS_DEMO_MODE: 0, so PrestaShop's own fixtures are not installed either. The only order-creating seeder is docker/woocommerce/01-seed-wc-data.sh, whose two orders land in WooCommerce's install-default currency and, with placedAt unmapped, ingest as terminal-unstamped. So the demo's first FX-visible artefact is a non-zero not-convertible count.

Proposed Solution
  • Add PrestaShop order creation to the demo seed. PrestaShop emits placedAt, and the demo shop already has EUR and USD active — docker/prestashop/post-install-lib/20-set-default-currency.php promotes PLN to default and leaves both active — so only order creation is missing.

The rate that matters is the one for the order's own rate date, not today's — so a live provider call at seed time would be both non-deterministic and insufficient.
