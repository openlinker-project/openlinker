Epic 1 · Fiscalization

Tax Number on a Receipt

A receipt carrying the buyer's tax number is, under a threshold, already an invoice. OpenLinker stores that number, routes on it, and then never sends it — so the document the buyer needs is never actually produced. This epic sends it, and shows it.

Why this is not a new document kind

A simplified invoice is not a third thing beside a receipt and an invoice. It is a fiscal receipt — same document, same device, same finality — that happens to carry the buyer's tax number and fall under a threshold. Nothing extra is issued, so nothing extra is built: this epic stays entirely inside the Fiscalization capability.

SaleDocumentCapabilityProvider request
No tax numberFiscal receiptFiscalizationeReceipt, no consumerTIN
Tax number, under thresholdFiscal receipt = simplified invoiceFiscalizationeReceipt + consumerTIN
Tax number, at or overInvoiceInvoicing — Epic 3eInvoice
The separation costs nothing to maintain The two paths are different request bodies at the provider, with different validation. A receipt's number lives in ReceiptMetadata.consumerTIN; an invoice's in CommonInvoiceMetadata.consumerTIN, checksum-verified. Nothing in this epic goes near the second one.
Evidence the gap is real On the demo instance /invoices?taxId=with returns "No invoices found" and ?taxId=without returns 26 of 26. And libs/integrations/eparagony/src contains zero occurrences of consumerTIN.

03

When the provider will not take the number

OpenLinker sends the number and reports what comes back. It does not pre-judge which numbers a provider will accept — it has no basis to, and acquiring one would mean holding a list of countries in code that must never hold one.

So there is one question on this screen, not two: did the provider refuse, and do we know what happened to the sale? That is the existing failureMode split, and it is the only distinction that changes what an operator should do next.

No retry button. A fiscal registration is a legal event, and the one thing worse than not having one is silently having two.

Cut after audit — and the example was wrong too An earlier draft had a state reading "This provider only carries EU tax numbers — 29ABCDE1234F1Z5 looks valid but is outside what e-paragony accepts." Three faults: EU is a regional category as system vocabulary; "looks valid" is a judgement about a foreign tax regime we cannot make; and "route this market elsewhere" is regional routing advice. The value was wrong as well — it begins with digits, so it fails the provider's pattern outright and was never the "valid but unsupported" case the screen claimed.
Why the judgement has no home anywhere The provider's field is a three-branch oneOf whose third branch is a structural pattern with a disclaimer — "no validation guarantee" — not a rejection rule. Telling EU from non-EU would need a member-state list, which exists nowhere in this tree and must not. So neither core nor the adapter can make that call: send it, and report what the provider says.
The shape already exists This follows OfferValidationProblem, whose own docs say a platform's code is its own value, verbatim and untranslated, never invented, and that scope is set by the adapter because "only the adapter knows its own taxonomy, and a core-side code list would put marketplace vocabulary in libs/core". Fiscalization already has the carriers: failureReason and failureMode. Nothing new is needed.

Corrected twice — the second correction was wrong I first said the value travels untagged. An audit told me that was false, because TaxIdentifier { scheme, value } exists and both the inFakt adapter and the FA(3) mapper switch on scheme. So I changed it. That change was the mistake. Those are all true statements about the invoicing command — but every scheme value in the tree is produced by an adapter or by an HTTP caller, never by core, and the type's own documentation says "core never names a country's identifier system". The order stores a bare string, so building a TaxIdentifier from it would force core to invent a scheme. The command carries the value; if an adapter needs it tagged, the adapter tags it, or the operator supplies a default per connection.
A guard that will actually fire libs/core/src/fiscalization has a build-failing vocabulary sweep over every file in the context, banning paragon, kasa, printer, eparagony and ksef — in prose as well as identifiers. Any wording about a specific provider or regime must stay out of that directory entirely, comments included. Invoicing and sales-documents have no such guard; the second claims a grep verification that no longer runs anywhere.

What this epic deliberately does not do

  • No new capability, no manifest change, no new adapter. A receipt carrying a tax number is fiscalisation work, and stays there.
  • No switch to include the tax number. If the order has one it goes to the adapter; the adapter decides what to do with it. A per-rule toggle would let one market's receipt silently drop a number another market's law requires.
  • No threshold logic in core. Which sale qualifies is a routing rule the operator writes — Epic 2 — never a rule OpenLinker knows.
  • No rule naming. Cut after the audit: invented scope, its own migration, and the only coupling between this epic and the next.
