#2823 · /listings variant-centric coverage

Product design mockup

One row per variant, one column per channel

/listings today lists offer-to-variant mappings, so a variant that was never published has no row at all — the page structurally cannot answer “where is this variant not listed yet”. This mockup replaces the mapping table with a variant coverage table: the gap is the loudest thing on the page, and the gap is the button.

† Two acceptance criteria in the issue are not backed by data yet, and this file marks them rather than drawing them as done. A mapping row is written only after createOffer succeeds (offer-creation-execution.service.ts:163), so while a publication is in flight there is no row to show as pending; and the ordering “a product’s variants appear consecutively” has no server-side expression — GET /listings orders createdAt DESC, id DESC with no sort parameter at all. Every † below marks work, not a read.
01 · Desktop The page — try it 1440 × 900 · expand a row, click a gap, filter to gaps only, page through, lock it read-only

Listings

Every variant in the catalogue, and which sales channels carry it.

Pagination counts products, not variants, and the label says so. Paging by variant would split a product’s variants across two pages exactly where the operator is comparing them — so the run stays whole and the page height varies instead. † needs a productId, variantId order key that no listings endpoint has today.

02 · Expanded What a row owes when it opens Connection, price, stock, last updated — and the channel with no offer, which is the whole point

A channel with no listing is not omitted from the drawer — it is the state the operator is hunting, so it gets a field of its own with the action attached. Reuses DataTable’s existing expandable mode (already driving /products), which disables virtualize on the same table and stops linkifying the first cell — so no row-level link here.

03 · Filters Two filters that answer two different questions “Only with missing listings” narrows to gaps · offer state is single-valued and any-match

Offer state stays a select, not multi-select chips, because ListingsFilters.lifecycle is OfferLifecycle — one value, not an array. A variant can hold an Invalid offer on one channel and an Active one on another, so the filter is any-match and the cell that matched carries the state outline. There is no row-level roll-up: no “worst state wins” rule exists in the offer domain, and inventing one would hide the healthy offer next to the broken one.

04 · Publishing Click the gap → the wizard already knows the variant and the channel In flight † · published · failed

Clicking a gap navigates to /listings/bulk-create/wizard?productIds=…&variantIds=…&connectionId=… — the wizard route already parses all three, so the gap needs no new backend and no new prop. The row-level Publish button is the multi-gap fallback and omits connectionId, letting the wizard ask. Note the picker modal is bypassed on purpose: OfferProductPickerModal takes initialProductIds only — there is no initialVariantIds, so preselecting a variant through the modal would be new scope, while the route is free.

† The in-flight state is the one thing here that cannot be read today. Publication dispatches jobs, and the mapping row is persisted only after the marketplace accepts the offer — so between click and confirmation there is no row to mark. Either the mapping is written earlier (backend change), or the table separately reads in-flight OfferCreationRecords and splices them in. The same gap makes “the badge refreshes without a page reload” new work: today’s mutation invalidates the listings cache at the moment the batch is accepted, when none of the offers exist yet. The reusable part is use-bulk-batch-query, which polls every 5 s and stops itself on a terminal status.

05 · States Loading, empty, error, and the two empties that are not the same Every state the issue lists, plus the read-only lock

“No variants match the current filters” and “No channels connected yet” are different failures and get different copy and different actions — the page already refuses a single generic empty state (#2029), and losing the tab strip must not quietly lose that discipline. Read-only follows the shipped pattern: useWriteAccess('listings:write', demoMode) — a demo viewer still sees the action, disabled with the reason; an unauthorised session gets nothing rendered.

06 · Tablet 768 — the matrix survives, scrolled inside its own container 768 × 1024 · the page never scrolls sideways; the table does

Listings

Rendered from the same data array as frame 01, not hand-written markup, so the two frames cannot drift. The identity column keeps a floor wide enough that the name/meta stack never wraps to a third line, which is what forces the horizontal scroll here rather than a squeezed matrix.

07 · Mobile 360 — card view, and the matrix gives way to a pill strip 360 × 812 · one card per variant · a fully-covered card stays quiet, a gap still carries the accent

Listings

    The style guide’s responsive parity matrix puts a table into card view at ≤767 px, so four aligned channel columns cannot survive here — vertical scanning was the matrix’s whole argument and a single card has nothing to align against. The pill strip returns, and the gap keeps its dashed accent so the card still reads gap-first. This is the one place the rejected pill layout is the right answer.

    08 · Many connections Where the matrix breaks, and where the counter finally earns its place Five connections, two of them on the same platform

    With two Allegro accounts the platform name stops identifying a column, and the codebase already has the rule for that: label by platform when it is the only connection of its kind, fall back to the operator-authored connection name when it is not (soleOfPlatform, listings-coverage-pills.tsx). Grouping those two columns into one Allegro 1/2 badge is the only case where the issue’s x/y counter carries information — everywhere else it restates a yes/no. Above roughly five connections the matrix stops fitting and the row falls back to the pill strip.

    09 · Handover What this changes, and what has to exist first Cell vocabulary · corrections to the issue · the style-guide entry to paste · the work

    The cell vocabulary

    Listed An offer exists on this connection. Neutral on purpose — it is not what the operator came to find.
    + Gap — and a button No offer. The only accent in the table. Click it and the wizard opens with this variant on this channel.
    Not applicable † This product is not sold on this channel, so it is not a gap. No such flag exists yet.
    Publishing † Between click and marketplace confirmation. Not readable from today’s data — see the note in frame 04.
    ! Failed The marketplace rejected the offer. Clicking reopens the wizard with the reason carried over.

    Four corrections to the issue

    1. The x/y counter leaves the badge. A variant is listed on a connection binarily, so Allegro 1/1 restates “yes”. The counter survives only on a grouped channel holding several accounts (frame 08). Everything else reads shape, not arithmetic.
    2. A gap has to be rendered, not omitted. /products renders a pill only for connections that have an offer, so a gap there is an absence. Inverted here: the gap is the loudest cell in the row.
    3. “Variants appear consecutively” is not expressible yet. GET /listings orders createdAt DESC, id DESC and takes no sort parameter. This design pages by product so the guarantee is structural rather than cosmetic — which needs a productId, variantId order key on the new read model.
    4. “Available channel” needs a rule, or the gap filter fills with noise. Hence the third cell state. Without an eligibility flag, a product that will never go to WooCommerce reads as a permanent gap and the filter becomes unusable.

    The style-guide entry this row requires

    frontend-ui-style-guide.md:645 is explicit that the #2023 listings carve-out covers the listings identity cell specifically, and that “a new table wanting a tall row needs its own entry here, not a silent reuse”. This row is not that row — it is not an offer, so the offer-ID and the validator line are both gone. Text to paste into the row-height table:

    Variant coverage row | auto, ~64 px | Variant-centric /listings (#2823) — 32 px thumbnail + name/variant line + SKU · EAN meta line. No offer-ID and no validator line: the row is a variant, not an offer. First column carries a min-width floor so the stack never wraps to a third line.

    What has to exist before this can be built

    1. A variant-centric read model. Variants left-joined to offer mappings, per connection, with the coverage state per cell. Neither existing read can produce it: GET /listings enumerates mappings, so a never-published variant has no row; GET /products aggregates coverage at product level and the per-variant pills inside the drawer are assembled one listings query per variant, which does not survive a paginated list.
    2. Product-grouped ordering with a stable tiebreaker. Follow the listings repository’s id DESC discipline rather than the products repository’s plain createdAt, or offset paging will skip and duplicate rows on ties.
    3. Pagination that counts products while the table lists variants. Page size applies to products; the row count per page varies.
    4. A channel-eligibility flag per product to back the not-applicable state.
    5. Run flags recomputed after filtering. The product name prints once per run, so the first surviving row of a run has to carry it. Compute the run boundaries on the rows that survived the filter, never on the unfiltered set — otherwise every filter that hides a product's first variant leaves the next one nameless (see rebaseRuns in this file).
    6. An in-flight publication read — either persist the mapping earlier, or read OfferCreationRecords and splice them into the table. This is also what makes the badge refresh without a reload; use-bulk-batch-query is the reusable poll.

    Out of scope and staying out: product-level parent rows, the listing-creation form, inline price or stock editing, delisting, bulk publish from selected rows, rejection handling and resync.
