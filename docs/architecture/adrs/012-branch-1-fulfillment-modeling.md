# ADR-012: Branch-1 (OMP-fulfilled) fulfillment modeling — delegate-to-OMP, not a degenerate shipping adapter

- **Status**: Accepted
- **Date**: 2026-05-25
- **Authors**: @piotrswierzy

## Context

The #832 fulfillment-routing model (#732) routes each `(orderSource, sourceDeliveryMethod)` to one of three **processor kinds**: *OMP-fulfilled* (the destination shop ships via its own carrier setup), *OL-managed carrier* (OL drives an own-contract carrier — InPost ShipX, #812), *source-brokered* (OL drives the marketplace's own shipping — Allegro Delivery, #833). Branches 2 and 3 map cleanly onto `ShippingProviderManagerPort` (#763) — one capability, different adapters. **Branch 1 is the genuine fork:** the OMP (PrestaShop) ships externally, OL generates no label and holds no provider shipment id. How should branch 1 be modeled?

## Decision

Branch 1 is **not** a `ShippingProviderManagerPort` adapter. It stays on the existing `OrderProcessorManagerPort` + `CarrierMapping` path it uses today — OL sets the destination carrier on the mirrored OMP order; the shop's own workflow ships. Only branches 2/3 implement `ShippingProviderManagerPort`. Branch-1 status read-back becomes a separate, small `FulfillmentStatusReader` capability — **named here, implemented in #834**.

The routing rule carries an explicit, **stored** `processorKind` discriminator (an operator choice — *not* derived from declared capabilities, since one connection may declare several). A single core dispatch orchestrator owns the `switch (processorKind)`; downstream consumers call the orchestrator rather than re-branching. The orchestrator lands with the first executor (#835/#833), not in #832.

**Rule shape & compatibility.** The rule stores only `{ processorKind, processorConnectionId }`. The OMP destination is *derived* (= the processor connection for `omp_fulfilled`; the order's fan-out destination set otherwise) and the branch-1 destination carrier is sourced from the **co-keyed `CarrierMapping`** (same `(source, method)` key) — neither is a stored column. Routing is **operator-configured per `(source, method)`** and validated at save against each processor's **declared capability + topology** (`omp_fulfilled` → declares `OrderProcessorManager`; `ol_managed_carrier` / `source_brokered` → declares `ShippingProviderManager`, with `source_brokered` requiring `processorConnectionId === sourceConnectionId`). **Method-granular auto-detection** — whether an order's `delivery.method.id` is Allegro-Delivery-eligible (the order-method ↔ `/shipment-management/delivery-services` namespace question, OQ-B1) — is a **#833 refinement layered behind the routing-compatibility seam, not a dependency**: the model functions on operator config + capability validation regardless of how OQ-B1 resolves, and a method-incompatible choice surfaces as a readable error at label generation. Compatibility lives behind the service seam so the routing model never reshapes if the compatibility signal's source changes.

## Alternatives considered

- **(i) Degenerate PrestaShop `ShippingProviderManagerPort` adapter** (`generateLabel` = assign-carrier/no-op, `getTracking` = read PS), unifying all targets to "ship-capable connections." **Rejected.** It can't honor the contract: `GenerateLabelResult.providerShipmentId`/`labelPdfRef` are non-nullable and provider-issued (branch 1 has neither), and `getTracking({providerShipmentId})` is keyed on an id branch 1 never gets. Making it fit means widening both — degrading the contract for the adapters that *do* generate labels (#812, #833) — and writing fabricated ids into the partial-unique `providerShipmentId` index. The "uniformity" is illusory: dispatch and status consumers must still branch on "is this the fake adapter?", so (i) hides the fork instead of removing it.
- **(iii) Overload the `Shipment` lifecycle** for branch 1 (`generated` = "carrier assigned"). **Rejected.** Overloads `ShipmentStatus` and conflates shipment status with order/workflow status — against #827's separable-axes requirement.

## Consequences

**Pros:**
- Keeps `ShippingProviderManagerPort` honest for the only adapters that generate labels; models branch 1 as what it is.
- Scales by *adding adapters*: same-mechanic processors are new adapters (zero switch growth); a new arm appears only for a genuinely new mechanic (e.g. a future 3PL/fulfilment-house).
- Branch-1-as-delegate survives even if OL later becomes the system-of-record — dropship/3PL fulfillment OL observes-but-doesn't-perform is permanent.

**Cons / trade-offs:**
- A `switch (processorKind)` exists (dispatch + status acquisition) — contained in one orchestrator.
- `processorKind` is stored config that can drift from a connection's real capabilities; compatibility validation guards rule creation.

**Migration path:**
- Additive — new `fulfillment_routing_rules` table; `connection_carrier_mappings` preserved as the branch-1 carrier detail and the resolution fallback.

## Amendment: source-side read-back

**Context.** The decision above scopes `FulfillmentStatusReader` to branch-1 **destinations**: OL reads how the destination shop shipped the order it mirrored. The order's **source** can ship it too. A merchant packs straight in the Shoper panel, a warehouse works off Allegro, and the tracking number they add there never reached OpenLinker: the source's own read half, `OrderFulfillmentReadback.readFulfillment` (#3365, an `OrderSource` sub-capability implemented by Allegro and Shoper), had one on-demand HTTP caller and nothing persisted or polled what it answered.

**Decision.** A source-side twin of the branch-1 read-back, `SourceFulfillmentStatusSyncService` in the shipping context, driven per source connection by the `marketplace.sourceFulfillment.statusSync` job (`bulk` lane, beside `marketplace.fulfillment.statusSync`; its own scan cursor and sweep lock). It pages the `ready`, not-cancelled orders ingested from the source, reads the source through the readback narrowed off the dispatched `OrderSource` adapter, and acts only on `outcome: 'read'`, `dispatched: true` and a waybill OpenLinker does not already know. It is a sibling service rather than a mode of `FulfillmentStatusSyncService` because nothing in that service's loop carries over: it pages by destination, resolves a routing rule, reads `OrderProcessorManager` and projects four statuses, where this pages by source, needs no routing and records one fact.

1. **It reuses the branch-1 row shape, on the source connection.** `connectionId = source`, `providerShipmentId` NULL, `shippingMethod = omp`, born `dispatched`, tracking = the first unknown waybill. It is the same fact - a platform OL does not drive reports that it shipped, and OL holds no provider id for the parcel - so it gets the same shape rather than a new `ShippingMethod` value. `UQ_shipments_branch_one_per_order_conn` keys on `(orderId, connectionId, direction)`, and an order's source is never one of its destinations, so this row and a destination's branch-1 row for the same order cannot collide; no migration. A source-connection row *with* a provider id is still OL's own `source_brokered` label (Allegro Delivery), which is what makes the NULL the discriminator.
2. **Echo guard (ADR-027).** OpenLinker writes dispatches INTO the source through `OrderStatusWriteback` - its own labels, a destination's branch-1 dispatch, a late carrier waybill (#1947) - so reading the source back would otherwise mint a second shipment and relay the same parcel twice. An order on which OL already holds a live (not failed, not cancelled) shipment with a tracking number is not read at all; a reported waybill equal to a tracking number on ANY outbound shipment of the order (voided ones included, compared trimmed and case-folded) is OL's own and is ignored; a dispatch with no waybill is ignored, because OL relays tracking-less dispatches too and a bare "sent" cannot be told apart from that echo. `waybills: null` ("not reported") and `[]` ("listed none") both carry nothing to record and neither is read as "shipped without one".
3. **Relay, at most once.** The waybill is relayed as `dispatched` to the order's destinations through the role-agnostic lifecycle relay with the source as origin (excluded), under the `Shipment.waybillRelayedAt` claim, the #2073 failure accounting and the #3506 give-up bound - one shared helper, `relayWaybillUnderClaim`, extracted from `ShipmentStatusSyncService` rather than copied. Unlike the carrier poll the waybill is persisted up front (the source already reported it); the retry signal is the free claim alone, so a row whose relay failed is re-driven on a later tick without reading the source again. An order with no synced destination is left owed rather than relayed, since the relay would resolve nobody and count that as a failure every tick.
4. **The reverse loop is closed on the destination side.** Once the waybill reaches a destination, that destination's own branch-1 read-back reports the parcel as shipped. `FulfillmentStatusSyncService` still projects that row but no longer relays it to the source when the order already carries a source-observed row for the same waybill (or the snapshot carries none) - otherwise the source would receive a second parcel. The check fails open: a failed lookup relays exactly as before.
5. **Scheduling.** Shoper registers `shoper-source-fulfillment-status-sync` default ON, every 15 minutes, like its other tasks. Allegro registers `allegro-source-fulfillment-status-sync` default OFF (`OL_ALLEGRO_SOURCE_FULFILLMENT_STATUS_SYNC_SCHEDULER_ENABLED`): every candidate order costs two Allegro requests on every existing connection, and an Allegro seller shipping outside OpenLinker is the exception rather than the rule.

**Consequences.** A parcel shipped outside OpenLinker in the source is recorded, rolls the order up as dispatched, and its tracking number reaches every destination shop. Not covered, deliberately: a third-party dispatch without a tracking number (indistinguishable from OL's own tracking-less relay); later states of a source-observed row (the readback carries no delivered state, so the row stays `dispatched`); the waybill's carrier name (`CreateShipmentInput` has no carrier field, and the relay's carrier hint means a shipping-provider connection, not a marketplace's carrier label). A known race remains: if OL's own waybill relay to the source lands while OL records it as failed (tracking withheld), the source can report that number before OL stores it; the read-back then records it as a source-observed parcel and relays it to the destinations, which receive the same tracking number again once the carrier poll succeeds, and the order carries two rows for one parcel - a duplicate record and notification of one parcel, never a second parcel.
