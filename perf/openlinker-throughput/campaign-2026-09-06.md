# OpenLinker performance campaign - 2026-09-06

Cross-flow report for epic #2840. **Draft: figures land as each flow completes.**
Every number below carries a label - **measured**, **derived** or **extrapolated** -
and the closing section states what the campaign did not establish.

---

## 1. Read this first: what these numbers are, and are not

**The stand is a Docker Compose project on a developer workstation.** It pins no
CPUs, declares no resource limits, and shares a 15 GB host with two other
running OpenLinker stacks whose containers were consuming 3-6% CPU throughout
every measurement. The sampler records the whole host's container CPU column
per sample, so the contention is visible in the raw artifacts rather than
asserted here.

The consequence is specific and worth stating plainly: **these are floors, not
ceilings.** A figure taken under contention understates what the software can
do on dedicated hardware; it does not overstate it. Where a run failed to reach
the system's limit at all, the report says so instead of presenting the highest
rate tried as though it were the maximum.

The stand is **not** the isolated lab environment #2854 specifies. That
environment does not exist yet. The same scenarios re-run there without
modification, and the figures should be retaken when it does.

### What makes these figures trustworthy anyway

Nine pre-flight guards must pass before any load is applied, and each of them
aborts the run rather than annotating it:

| Guard | Refuses to measure when |
|---|---|
| `guard_build` | the running images were not built from the working tree's exact commit |
| `guard_scheduler_off` | a cron could fire into the measurement window |
| `guard_runner_state` | the worker's runner posture differs from what the scenario declares |
| `guard_queue_empty` | work from an earlier run is still queued |
| `guard_demo_mode_off` | demo mode's read-only lock or cleanup tick could land mid-window |
| `guard_connection_budget` | the DB pool budget exceeds Postgres `max_connections` |
| `guard_pool_recorded` | those two figures did not resolve |
| `guard_log_level` | full-body request logging is uncapped |
| `guard_perf_max_attempts` | the retry cap would not actually apply |

Five post-guards then run, and a window that hit its rate limiter, saturated a
lane or drifted mid-run is written `DISCARDED` rather than averaged in. A
discarded run is not a slower measurement of the same thing - it measured
something else.

### Order throughput is not on this page - it has its own

**This page covers webhook ingress, stock propagation, the operator read path,
upstream latency and catalogue replication. It carries no orders-per-hour
figure**, because that flow produced fifteen of them across five runs on three
branches, spanning **182 to 3 356 orders/h**, and several are withdrawn.

They live in one place instead, with the window length, offered rate,
destination rate limit, replica count, scheduler posture and verdict each one
required:

> **[campaign-orders-per-hour-2026-09-08.md](./campaign-orders-per-hour-2026-09-08.md)**
>
> The short version: plan against **598.3 orders/h** - the only figure at which
> the offered rate and the completed rate met over three continuous hours.
> **971.3 orders/h** is a legitimate lower bound from a saturating window.
> Everything above that is a five-minute isolated window or arithmetic, and the
> true ceiling is **unmeasured**.

Asked for 1 000/s, the stand delivered **roughly 600/s**. Read what that does
and does not establish before quoting it:

| Target rate | Achieved | Arm | p50 | p99 | k6 VUs |
|---|---|---|---|---|---|
| 50/s | 43.1/s | unique | 5.3 | 8.6 | 1 |
| 300/s | 239.6/s | unique | 3.4 | 11.1 | 3 |
| **1 000/s** | **601.8/s** | unique | 100.3 | **217.8** | 132 |
| **1 000/s** | **568.0/s** | replay, committed ids | 124.5 | 243.8 | 149 |
| **1 000/s** | **548.7/s** | replay, concurrent id | 135.5 | 268.9 | 143 |

All three arms converge on 549-602/s, which is what makes this a property of
the system rather than of one run. **Zero failed requests at any rate**,
including at saturation.

**But the generator was near its own limit at the same moment, and the two
causes cannot be separated from this run.** k6 reports dropped iterations of
19.6% / 24.1% / 26.7% across the three arms, and it was running at **92-97% of
its configured virtual-user ceiling** (132 of 137, 149 of 154, 143 of 156). An
iteration is dropped when no virtual user is free, so part of the gap between
1 000/s offered and 600/s achieved is k6 running out of VUs rather than the
system refusing work.

Two independent signals point in opposite directions and both are real:

| Evidence | Says |
|---|---|
| `lab-api` CPU at 97.7% during the window | the **system** was saturated |
| k6 at 96% of its VU ceiling, 20-27% iterations dropped | the **generator** was also constrained |

So **~600/s is a measured lower bound on the ceiling.** The API process was
genuinely CPU-bound - a 30x median degradation from 3.4 ms to 100 ms is not a
generator artifact - but whether the system would have absorbed 700/s or 800/s
with a larger VU pool is unanswered. Settling it needs one re-run with the VU
ceiling raised well clear of the observed usage, and that has not been done.

Quoting "the ceiling is 600/s" would overstate what this measured. Quote it as
"at least 600/s, with the API CPU-bound at that point".

**p99 never reached one second.** The scenario's acceptance criterion asks for
the arrival rate at which it does, and the honest answer is that the system
runs out of throughput first: at the ceiling p99 is 218 ms, about a fifth of
the threshold. The criterion assumed a latency cliff; what this system has is a
throughput ceiling with latency degrading gracefully up to it.

### What the ceiling is made of

Sampled live inside the saturating window:

| | 43/s | 240/s | ~600/s |
|---|---|---|---|
| `lab-api` CPU | ~15% | - | **97.7%** |
| `lab-postgres` CPU | ~12% | - | **78.2%** |
| Peak active DB connections | 3 | 3 | **41** |
| Postgres wait events | none | none | **`LWLock:WALWrite`** |

Three limits arrive together: the API process saturates its CPU, the connection
pool reaches its configured ceiling (41 observed against `OL_DB_POOL_MAX` of
40), and Postgres begins waiting on write-ahead-log flushes.

**This contradicts the hypothesis the scenario was designed around, and that is
the most useful thing in this section.** The issue expected contention on the
unique index - waiters serialising on one tuple when the same `eventId` arrives
repeatedly. No index contention was ever observed, at any rate, on any arm. The
binding constraints are **API CPU and WAL write throughput**, which is what a
workload of "two inserts, committed, per request" should be limited by. An
operator scaling this path adds API processes and faster WAL storage; tuning
indexes would buy nothing.

### Two readings that are easy to get backwards

**The replay arms are faster than the unique arm, and that is mechanism, not
noise.** A duplicate event id hits `ON CONFLICT DO NOTHING`, the gate returns
`isNew: false`, and the service short-circuits to the 202 idempotent
acknowledgement - skipping the `sync_jobs` insert and the post-commit Redis
mark. The replay path does strictly less work, so it is strictly faster.

**At 43/s the concurrent-replay arm proved nothing, and its zero lock waiters
must not be read as a result.** k6 used exactly **one** virtual user: at 43
requests per second against a ~5 ms service time, utilisation is about 21% and
the requests ran strictly sequentially. The condition that arm exists to create
- the same event id inserting *simultaneously* - never arose. Zero contention
was observed because zero contention was produced.

At 240/s the executor finally needed 3 VUs, so genuine overlap begins there,
and the arm's figures from that tier are the first that mean anything. Even so,
the right instrument for that specific question is a fixed pool of virtual users
all posting one id, rather than an arrival-rate executor that only creates
overlap as a side effect of saturation. That is named here as a scenario
improvement rather than quietly worked around.

**The pool-exhaustion question the scenario sets itself is likewise still
open.** Peak concurrent connections was 3 of 80. Nothing came close, so nothing
was learned about the behaviour at the pool ceiling.

### Stage breakdown

Four probes stop at four different depths of the request, so the stages are
recovered by difference without instrumenting product code:

| Probe | Response | Reaches |
|---|---|---|
| invalid signature | 401 | connection read + secret resolve + verify |
| valid signature, malformed body | 400 | + envelope decode |
| event the connection lacks capability for | 202 `deadlettered` | + routing, Redis, delivery insert |
| routable event | 202 `job_enqueued` | + the `sync_jobs` insert |

**Correction, and it applies to an earlier claim in this campaign.** All four
probes were seen returning those four distinct outcomes in console output during
stand verification, and that observation stands. **The persisted artifact does
not support it**: `probes.csv` recorded exactly **one** row - `auth-fail` - in
every run taken tonight. The cause was found and fixed: the probe loop calls
`docker exec -i`, which reads standard input, from inside a `while read` fed by
a here-string, so the first call consumed the remaining input and the loop ended
after one iteration. Reproduced in isolation:

```
rows seen with a stdin-reading call in the loop body: 1  (expected 3)
rows seen with </dev/null on that call:               3  (expected 3)
```

A measurement programme's claims have to rest on artifacts, not on a console
line someone read once. **The fix is in and the artifact now supports the
claim** - `run1788653420-probes/probes.csv`:

```
auth-fail,401,auth-fail-1788653421018,<none - never reaches webhook_deliveries>
decode-reject,400,decode-reject-1788653421101,<none - never reaches webhook_deliveries>
routable-product,202,routable-product-1788653421187,deadlettered
routable-order,202,routable-order-1788653421280,job_enqueued
```

Four rows, four distinct depths, and the two 202s are told apart by the
`webhook_deliveries` status rather than by the HTTP code they share - which is
the whole reason the ladder needs a database column and not just a status
code.

**A second gap in the same area is larger and is not fixed.** The probes record
*which* stage each request reaches, never *how long* each stage took - so the
per-stage latency breakdown this section is supposed to carry, and which the
scenario's acceptance criteria require, is **not buildable from the current
implementation at all**. The differential ladder exists; the timing does not.
That is a scenario gap, not a run gap, and no number should be quoted for it
until the probes are instrumented.

## 3. Stock propagation (F2) - in progress

Measures the chain from a stock change at the shop to the quantity the
marketplace shows, **hop by hop rather than end to end**. An end-to-end figure
that is mostly "waiting for the shop's own cron" tells an operator nothing they
can act on; the split is the point.

Two findings already, ahead of any latency figure:

**A direct SQL update to PrestaShop's stock table fires no hook at all.** It
bypasses PHP, so the OpenLinker module writes no outbox row and OpenLinker only
learns the new stock at the next 15-minute inventory sweep. Any tooling that
seeds stock by SQL is silently exercising the sweep path, not the webhook path.

**25 stock writes through the webservice produced only 2 `stock.changed` outbox
rows.** Whether that is a dedup window, a value-did-not-change guard or a real
gap is being established before any figure is quoted for that hop - which of
the three it is matters more than the latency does.

## 4. Operator read path at row count (F5) - measured

Seeded to 10 000, 100 000 and 1 000 000 orders, each read driven through the
HTTP API as an operator hits it, so the figures include serialisation and the
ORM. Zero failed requests at every size. Per-route sample sizes 138-725.

| Route (median) | 10k | 100k | 1M | 10k -> 1M |
|---|---|---|---|---|
| orders list, **needs-attention filter** | 11.4 ms | 47.7 ms | **149.0 ms** | **13x** |
| orders list | 7.9 ms | 14.8 ms | **37.9 ms** | 4.8x |
| whole page load (`page_shell_total`) | 28.0 ms | 35.0 ms | **58.0 ms** | 2.1x |
| order detail | 5.9 ms | 5.9 ms | 6.0 ms | **1.0x** |
| product detail | 6.4 ms | 6.5 ms | 6.5 ms | **1.0x** |
| products list | 10.4 ms | 10.9 ms | 10.8 ms | **1.0x** |
| sync-jobs list | 33.4 ms | 35.1 ms | 34.6 ms | **1.0x** |

**A hundred times the orders moved exactly two routes and left four unchanged.**
Both movers are orders-list variants, and both pay a `COUNT` over
`order_records`; the four flat routes do not. The whole-page figure doubles
because the shell contains one of them.

The tail widens faster than the median: `page_shell_request` p95 goes 12.9 ->
15.5 -> **39.0 ms**, so the worst request on a page load degrades about 3x while
its median barely moves.

### The page is fast; the pagination total is not

The whole degradation is one query. From `pg_stat_statements` at 100k:

```
138 calls  mean 39.636 ms   SELECT COUNT(*) FROM order_records
                            WHERE recordStatus <> $2 AND recordStatus <> $3
                              AND syncStatus @> $4::jsonb
138 calls  mean  0.256 ms   SELECT ... same table, same predicate, LIMIT 20
```

**Same table, same filter, 155x apart.** The paged read stops after 20 matches
on `IDX_order_records_createdAt`; the COUNT has no LIMIT and must evaluate a
non-sargable jsonb containment against every row. 39.6 ms of the route's 47.7 ms
is that one query.

The unfiltered list pays the same shape more cheaply (`SELECT COUNT(*) FROM
order_records`, 6.9 ms mean), which is exactly why it degrades 1.9x while the
two detail routes are flat. **The pattern is "any list that reports an exact
total", not "orders"** - it generalises to every paged read in the product.

### At 1M the growth is sub-linear, and that is not good news

| | 100k | 1M | growth |
|---|---|---|---|
| needs-attention COUNT | 39.6 ms | **141.9 ms** | 3.6x |
| unfiltered COUNT | 6.9 ms | 30.5 ms | 4.4x |

A linear projection from the 100k figure predicted roughly 400 ms; the
measurement is 142 ms, and the end-to-end route lands at 149 ms - so almost the
whole route is still that one query. The plan says why the growth is sub-linear:

```
Finalize Aggregate (actual time=157.838..161.660)
  -> Gather   Workers Planned: 2   Workers Launched: 2
       -> Parallel Seq Scan on order_records (rows=83251 loops=3)
Buffers: shared hit=9281 read=69155        heap size: 613 MB
```

**The sub-linear growth is bought with parallel workers** - three processes
doing one process's work, because the 613 MB heap is far past
`min_parallel_table_scan_size`. Two things follow, and both are worse than the
timing suggests.

**The parallelism is not guaranteed.** `max_parallel_workers_per_gather` is 2 on
this stand. On a server whose worker pool is already busy, the same query falls
back to a single-process scan and the time moves back toward the linear
projection. The 142 ms figure is a best case, not a typical one.

**The real cost is I/O, and it is not confined to this route.** The count reads
**69 155 buffers from disk** per execution - roughly 540 MB pulled through the
buffer pool every time an operator opens that filtered page. That evicts
whatever else was cached, so the effect is application-wide cache thrashing
rather than one slow page. Timing alone would never have shown this.

### One trap for anyone scanning the table above

The **sync-jobs list is the slowest route in absolute terms at every size**
(33-35 ms) and **does not degrade at all** - it scales with `sync_jobs`, not
with orders. A reader picking the biggest number would optimise the wrong thing.

### Remedies, none of them chosen here

An index on the predicate (GIN or expression), an estimated or capped total
("20+"), or a cached count. Which is right depends on whether operators need an
exact number, which is a product decision. This report's job is to establish the
cost.

## 5. Upstream latency (Allegro) - measured

Taken against the Allegro **sandbox**, passively harvested from traffic the
deployment already generates. Production latency is unmeasured.

| Endpoint | n | p50 | p95 | Shape |
|---|---|---|---|---|
| `GET /order/events` | 480 | **276 ms** | 1 194 ms | **bimodal** - two tight clusters, 90-338 ms (51.5%) and 1 059-1 374 ms (48.3%) |
| `GET /order/checkout-forms/{id}` | 118 | **1 106 ms** | 1 217 ms | **unimodal** - 73.7% inside one 1 000-1 199 ms peak |

Three things this establishes that a single averaged number would have hidden:

**The mean is not usable for the events endpoint.** Its two clusters have almost
nothing between them, so the mean (655 ms) describes neither. Anything modelling
this endpoint takes p50 or the two modes, never the average.

**The two endpoints differ by roughly 4x and need separate constants.** A
checkout form hydrates a whole order; an events page returns references.

**The bimodality belongs to the events endpoint, not to the client or the
network** - the checkout-forms endpoint, measured over the same connection in
the same period, is cleanly unimodal. The mechanism behind it remains
unestablished and no explanation is offered here.

### A cost finding that came out of the same sample

19 of 23 marketplace orders in the sample were `source_deleted` - their offers
outlived the catalogue behind them - and each retry of the failing sync
**re-fetches the checkout form**. So an order whose backing variant is stale
costs the upstream one full hydration per retry attempt, for no progress. This
is a cost observation, not a claim that the retry is wrong: a mapping can
legitimately appear later, which is why the job is retryable.

## 7. What this campaign did not establish

- **Any ceiling.** No flow was driven to failure on hardware that could be
  described as representative. Every figure here is a floor.
- **Behaviour on dedicated hardware.** The stand shares a contended workstation
  with two other stacks and pins no CPUs.
- **Multi-replica behaviour.** ~~Nothing here ran more than one.~~ **Superseded by
  F4 (#2851)** - see `results-F4-2026-09-06.md`. At three replicas the same 600
  `bulk` jobs drained **2.77x faster** by hitting the destination at **158.4
  req/min against the 60/min it declares**, because the shared Redis limiter
  timed out at its own 1 s budget and fell back to per-process pacing. What did
  NOT get in the way: the claim (0.087 -> 0.086 ms per call), `sync_jobs` lock
  waits (zero), the pool (no timeouts), and the missing
  `(status, jobType, nextRunAt)` index (0.22-0.37 ms across depth 0 to 591).
  Both arms are `DISCARDED` for the degraded limiter, which is the finding
  rather than a disqualification.
- **Production upstream latency.** The Allegro figures are sandbox figures.
- **Read-path cost at a large history of the OTHER tables.** F5 seeded
  `order_records` and `order_line_items` to 1M and measured them. The other 37
  unbounded tables were not seeded, so a read that joins against a large
  `sync_jobs`, `webhook_deliveries` or `automation_runs` history is still
  unmeasured - and the sync-jobs list, already the slowest route, is the obvious
  next candidate.
- **Cross-lane starvation.** ADR-050's lane model is not validated by any run
  here. F7 (#2852) addresses it and F4 (#2851) exercised the multi-replica
  arm. **F7's original `degraded_mode_entries = 0` is WITHDRAWN and must not
  be quoted**: its post-guard filtered `docker logs` with `--since "@epoch"`, a
  form Docker accepts while matching nothing, so the guard could not see a
  degraded line on ANY scenario in this campaign. Fixed in #2851/#2969.
  **F7 was re-run on 2026-09-07 against the fixed guard** and recorded
  **≥ 38 degraded-mode lines** inside its window - the run is `DISCARDED` for
  that reason. Its structural findings reproduced (claim latency flat across
  arms; realtime execution roughly 5-6x under load while the fiscal control
  stayed flat; occupancy 76.1% at the per-scope cap, still short of the literal
  95% bar), but the original's "32x/35x" queued-depth growth ratio did **not**
  and should not be quoted either - it is dominated by a sub-0.1 ms depth-0
  denominator. **§8 of that report carries an explicit may-travel / may-not
  table**, because a `DISCARDED` verdict stops nothing mechanically here (this
  report's own F4 throughput figure is appended with the verdict as a column) -
  in short, the isolation and depth findings travel, every throughput-shaped
  figure from that window does not. That re-run also found that a peer
  recreating the stack mid-window tripped no guard at all; closed by
  `post_guard_containers_stable`.
- **Erli's 500-unread inbox cliff.** Unreachable without an Erli arm, which does
  not exist; the cap itself is unverified prose rather than an observed
  behaviour.

## 8. Provenance

Every run writes a manifest before any load is applied, recording the git sha of
the images under test, the guard results, the pool budget, the scheduler cadence
row, container digests and the host's resources. Manifests are never
hand-edited. The raw k6 summaries, Postgres lock samples, deadlock deltas and
per-second time series sit beside each manifest under
`perf/openlinker-throughput/results/`.

**Amendment (#3009): what a manifest does not record, and where the artefacts
actually are.** The paragraph above is accurate about the manifest and
optimistic about everything around it. Two corrections.

*The manifest records the PRE-FLIGHT guard values only* - `runnerState`,
`laneCaps`, the pool ceiling and budget, `olLogBodyMaxBytes`, the cadence row.
It contains no post-guard result at all; grep any manifest in this campaign for
`post_guard` and you get zero hits. Until #3009 a passing post-guard left no
trace anywhere - a `VALID` verdict was simply the *absence* of a `reason=` line -
so no artefact could distinguish "passed eight guards" from "passed the four
that existed at the time". Verdicts now carry one
`guard=<name>:<ok|failed>` line per guard that ran, and a withdrawn run reads
`status=SUPERSEDED` rather than `VALID`.

*`results/` is not committed, and never was.* It has been ignored at
`.gitignore:100` since before this issue, with a comment there naming
`perf/prestashop-baseline` as the precedent - so the decision existed; what was
missing was any statement of it a reader of these figures would ever meet. As of
#3009 the ignore is **split by role**: the provenance core (manifest, verdict,
run summary, k6 summary, deadlock delta, and any prose in a run directory) is
committed, and the bulk per-tick samples are not. The README's *Evidence and
artefact retention* section carries the measured numbers behind that split
(130 KB of core against 302 MB of bulk) and the honest state of the back
catalogue: it is fragmented across fifteen worktree-local trees, no one of which
is this campaign, and it is not yet backfilled.

**Five harness defects were found by running it, and every one of them is a
case of the harness reporting something it had not established.** Two were
caught by the harness itself, three by reading its own artifacts:

| Defect | Effect |
|---|---|
| `guard_log_level` verified a value without recording it | manifests said `"unknown"` for a checked value |
| `run_one_arm` returned through captured stdout | its log text polluted a directory path |
| k6 rejects `-` in a Trend metric name | two arms crashed before sending a request |
| k6's default summary carries **no p99** | the headline percentile was unreachable from every export |
| `docker exec -i` inside a `while read` here-string loop | the probe CSV was truncated to one row |

The pattern is worth naming: none of these produced an error an operator would
see. Each produced a *plausible artifact* that was quietly incomplete - which is
the exact failure mode a measurement harness must not have, and the reason the
test suite grew from 63 assertions to 70 tonight rather than the numbers being
patched up.

**One manifest defect is disclosed rather than corrected in place**:
runs before the fix record `"olLogBodyMaxBytes": "unknown"` because
`guard_log_level` verified the value without recording it. The verified value
was 8 192 on both containers. The guard now records what it checks, and the
harness test suite gained an assertion for that shape.
