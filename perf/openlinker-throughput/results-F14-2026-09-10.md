## 1. What this measures, and what it does not

Both sales-document kinds through their real write paths, at a provider whose
latency is a declared constant.

- **arm A** - invoicing issuance, `POST /v1/invoices` against `perf-invoicing`
  (invoicing-stub, #3006).
- **arm B** - fiscal registration, `POST /v1/fiscal-registrations` against
  `perf-eparagony` (the real eparagony.pl adapter, #3043), polled to its
  `registered` terminal.
- **arm C** - the cross-kind one-document-per-order guard (#2047/#2157), raced
  for real: one invoice call and one fiscal call fired at one order at
  (as close as bash gets to) the same instant.
- **arm D** - the `in-doubt` outcome on demand.

**It does not measure a real provider.** Both stub latencies are declared
constants, never distributions. Every figure below is a statement about
OpenLinker's own write path and lock, not about inFakt, KSeF, Subiekt or the
real eparagony.pl.

## 3. Arm A and arm B are NOT two speeds of one thing

An earlier artefact compared them directly and claimed fiscalization costs 114x
more of our own time. **That comparison is withdrawn.** Arm A times a
SYNCHRONOUS HTTP call around the call itself; arm B enqueues and then polls with
`sleep 1` until it observes a terminal state, so its wall-clock includes the
harness's own poll cadence. The scenario says so in its own log line, and that
line was not read before publishing.

The difference is architectural, and the queue proves it rather than the code
reading that way: **the whole measurement window contains exactly 12
`sync_jobs` rows and every one is a `fiscalization.register`.** There is no
`invoicing.issue` row at all, because invoicing never reaches the job runner.

## 4. What a fiscal registration actually costs

Measured the campaign's standard way - `lastAttemptDurationMs`, the job's own
work time:

    fiscalization.register   n=12   mean 8 323 ms   max 9 183 ms

Against the adapter's declared poll ladder (1 000 ms first gap, x1.6 backoff,
5 000 ms cap) and a 2 s stub, the arithmetic lands on the measurement:
`POST 2000 + gap 1000 + GET 2000 + gap 1600 + GET 2000 = 8 600 ms`.

So roughly **three quarters of a fiscal registration is status polling in which
every poll pays the provider's full latency** - not eight seconds of our own
work. The decomposition is a rachunek against declared constants, not a second
measurement: nothing instruments inside the job.

### 4a. A change was made on this reading, measured, and reverted

The obvious lever looked like the first poll gap: the loop issues its first read
IMMEDIATELY after the create, so against a device slower than the hardcoded
1 000 ms that read is premature by construction. An operator-settable
`config.statusPollInitialDelayMs` shipped on that reasoning.

**The measurement contradicted it and the change was reverted the same day.**

| first gap | `lastAttemptDurationMs`, n=11 |
|---|---|
| 1 000 ms (shipped default) | **9 071 ms** |
| 2 000 ms (configured) | **10 087 ms** |

+1 016 ms - exactly the extra wait, with nothing saved. The premise was wrong in
a way the code says plainly once read in the right order: **the loop reads
first and sleeps afterwards, so the gap sits BETWEEN reads and can never remove
the premature first one.** Tuning it only delays the next read.

There is a second reason the knob could not have been validated here even if the
reasoning had held. The stub's readiness is poll-COUNT driven
(`if (doc.pollCount <= doc.pollsUntilOutcome)`), not time driven, so no amount of
waiting makes a document ready sooner against it. That is a limitation of the
STAND, and it is the more useful finding: this harness structurally cannot
measure any change to poll timing. A stub whose readiness is a function of
elapsed time is the prerequisite for revisiting this at all.

What would actually skip the premature read is sleeping BEFORE the first one -
a different change, which would hurt a fast device, and which this stand still
could not measure.

## 5. The defect this run exposed in the scenario itself

An earlier F14 today scored **arm B 0/10 and still wrote `status=VALID`**. Its
verdict rule read "arms A/B are throughput measurements and never gate the
verdict".

The cause was a stand fault - an nginx TLS terminator holding a stale upstream
address after its backing stub was recreated, so every fiscal call 502'd - and
two guards now exist that did not:

- `guard_connection_endpoints` probes every configured base URL from inside the
  worker, through node, before the window opens.
- the verdict discards on an **empty** throughput arm. It still never discards
  on a slow one: a slow number is a result, zero samples is not a number.

`guard_build` was also absent from this scenario entirely, so every earlier F14
manifest recorded `gitSha: unknown`. Added; this run carries `5897057a`.

## 6. Limits

- Declared stub latency, not a real provider (§ 1).
- 350/h is measured WITH the harness's poll cadence, so it is a lower bound on
  the fiscal path rather than a system ceiling.
- The lane was pinned to `fiscal=1/1` on this stand. The shipped default is now
  8/4 (#3006's sweep); this run does not measure that.
- n=10 per throughput arm.
