## Headline: the page is fast, and the total is slow - and it is not about orders

**`GET /orders?health=needs_attention` degrades 13x from 10k to 1M rows (11.4 ms -> 149.0 ms
median), and essentially all of it is one query: the pagination COUNT, not the page.**

```
                                mean, ms          calls
                         10k      100k      1M
filtered COUNT(*)       3.86     39.64    141.89      (WHERE recordStatus NOT IN (...) AND syncStatus @> '[...]'::jsonb)
paged SELECT ... LIMIT 20  ~0.2   ~0.2     ~0.2        (same table, same predicate, LIMIT 20)
```

The **page** query stops after 20 matches by walking `IDX_order_records_createdAt` backwards
and applying the filter row-by-row until 20 pass - confirmed live via `EXPLAIN (ANALYZE,
BUFFERS)` on the exact predicate at 1M rows: `Execution Time: 0.226 ms`. The **count** query has
no `LIMIT`, so it must evaluate the same non-sargable jsonb-containment filter
(`syncStatus @> '[{"status":"failed"}]'::jsonb`, no GIN index -
`order-record.repository.ts:373-375`'s own documented acceptance) against every row in the
table. At 1M rows that is a 150 ms full-table pass; at 10k rows it is 3.9 ms. Same mechanism,
1000x the row count, ~35x the time.

**The pattern is "any list that reports an exact total", not "orders".** The plain
`GET /orders` list pays the identical shape more cheaply, because its `COUNT(*) FROM
order_records` (no predicate) is a plain sequential count with nothing to filter:

```
unfiltered COUNT(*) mean, ms:  1.03 (10k)  ->  6.90 (100k)  ->  30.52 (1M)
route_orders_list median, ms:  7.88 (10k)  -> 14.75 (100k)  -> 37.88 (1M)   (4.8x, 10k->1M)
```

This generalises to every paged read in the product that reports `total` rather than "20 of
many": `GET /products`, `GET /sync/jobs`, `GET /returns`, and any future list, will pay the same
COUNT-vs-page gap in proportion to how selective and how indexed their own filter predicate is.
The remedy is a product decision this report does not make (see "What this did not
establish"), but the three shapes on the table are: a GIN or expression index on the specific
predicate a filter needs (closes the gap for that filter only, and needs one per filter);
an estimated or capped total ("20+" once the first page is known to be non-final, never
computing an exact count past a small cap); or a cached/precomputed count refreshed off the
write path rather than the read path. Which is right depends on whether an operator actually
needs an exact number - a question this report is not positioned to answer.

## The projection did NOT hold, and that is the more interesting result

> **SCOPED, 2026-09-07.** Everything in this section is the original 2026-09-06 text and
> its figures stand as measurements of the **10k to 1M** range. The *conclusion* - that
> the read path scales sub-linearly - is **withdrawn**: it does not hold past 1M, where
> the measured step is 1.84x for 2x the rows. See the correction at the top of this
> report, and `results-reseed-2026-09-07.md` § 0 / § 3.5.

Naive linear extrapolation from the 100k figure (39.64 ms x 10) predicts **~396 ms** at 1M.
The **measured** figure is **141.9 ms** - about 2.8x faster than the linear projection, and the
100k->1M step (10x the rows) cost only 3.6x the time instead of ~10x. **This 3.6x is true of
the 10k-1M range and must not be read as the curve**: at 1M -> 2M the measured step is **1.84x
for 2x the rows** (`results-reseed-2026-09-07.md` § 3.5), so past 1M the honest assumption is
linear. See the correction at the top of this report.

The mechanism is visible directly, captured live via `EXPLAIN (ANALYZE, BUFFERS)` against the
real 1M-row table and the real predicate:

```
Finalize Aggregate (actual time=146.839..150.203 rows=1 loops=1)
  -> Gather (Workers Planned: 2, Workers Launched: 2)
       -> Partial Aggregate (loops=3)
            -> Parallel Seq Scan on order_records
                 Filter: (NOT recordStatus='awaiting_mapping' AND NOT recordStatus='source_deleted'
                          AND syncStatus @> '[{"status": "failed"}]'::jsonb)
                 Rows Removed by Filter: 250083 (per worker)
Execution Time: 150.339 ms
```

At 1M rows Postgres's planner switches this COUNT to a **Parallel Seq Scan with 2 workers**
(`max_parallel_workers_per_gather=2` on this stand), which is what buys back roughly a third of
the naive-linear cost. **This is labelled derived-then-checked, not assumed**: the 100k-scale
plan for this exact query was not directly re-observable once the dataset grew past that point
in this campaign (the additive-seeding trade-off named in "What this did not establish" below),
so whether 100k already ran partially parallel, or not at all, is not established here - only
that the 10x-rows -> 3.6x-time ratio is inconsistent with a single non-parallel scan and
consistent with the parallel plan directly observed at 1M. **This partial self-healing is not a
reason to skip fixing the predicate**: it depends on `max_parallel_workers_per_gather` and on
worker availability, which is exactly what degrades under the concurrent load an operator's
real read path runs under - two workers borrowed by this query are two workers a neighbouring
query does not get, and the harness's own `browse_mix` traffic was competing for that same pool
throughout this window.

## Not every slow-looking route is the interesting one

**`route_sync_jobs_list` is the slowest route in absolute terms at every size (33.4 / 35.1 /
34.6 ms median) and does NOT degrade at all** - it scales with `sync_jobs` (held constant at
~123k rows across all three order-dataset sizes, since #2849's job seeder runs once,
independent of order count), not with `order_records`. A reader scanning this report for "the
biggest number" would land on `sync_jobs_list` at 10k and 100k and conclude, wrongly, that it is
the risk to watch as the catalogue grows - it is flat, and `orders_list_needs_attention` (the
smallest number at 10k) is the one that actually moves.

## Symptom first: what an operator's page load actually costs

**Lead with this, not the per-route split - the per-route figures are the diagnosis, this is
the symptom.** `page_shell_total_duration_ms` times the app shell's own five-request nav-probe
fan-out (`useNavCounts`) as ONE group per page load, separately from the browse-mix routes:

| Size | n | p50 | p95 | p99 |
|---|---|---|---|---|
| 10k | 145 | 28.0 ms | 37.8 ms | 43.8 ms |
| 100k | 145 | 35.0 ms | 46.0 ms | 52.6 ms |
| 1M | 145 | 58.0 ms | 76.8 ms | 86.1 ms |

The shell tax is **several times any single route's own median** (28-58 ms against 5-15 ms for
a typical individual request) because it is five sequential requests, not one - and it degrades
2.1x from 10k to 1M even though four of its five constituent probes
(`connections`, `orders?limit=1`, `listings?limit=1`, `webhook-deliveries?limit=1&status=failed`)
touch tables that do not grow with the order dataset at all. The fifth probe
(`sync/jobs?limit=1&status=dead`) is index-served and cheap (see `explain.txt`:
`Index Scan ... Index Cond: (status = 'dead')`, 0.114 ms at 1M) - so the shell's own growth
is not fully explained by any one of its five constituent calls in isolation, and is more
plausibly connection-pool contention with the concurrently-running `browse_mix` traffic than a
single slow query. `page_shell_request_duration_ms`'s own p95/p99 (12.9/16.1 ms at 10k, rising to
39.0/47.2 ms at 1M) grow far more than its median (3.6 -> 4.0 ms) - the shell is usually fast and
occasionally caught behind whichever route is mid-flight, which is a queueing signature, not a
per-request cost.

## Per-route latency (measured, ms; every figure carries its own n)

**Sample-size honesty (coordinator review): a percentile computed over a handful of requests is
not a percentile - it is an order statistic of a tiny set that happens to look like one.** This
scenario's driver (`drivers/read-path.js`) splits a fixed request budget across six weighted
routes, so a lightly-weighted route can legitimately land with a small `n`. The scenario's
report step (`emit_route_report` in `scenarios/f5-read-path.sh`) enforces two stated
thresholds, applied uniformly, never chosen after the fact:

- **`MIN_N_FOR_PERCENTILE=30`**: below this, the report prints the RAW per-request
  observations instead of a percentile row - demonstrated live on this campaign's own smoke
  run (`results/f5-read-path/smoke/route-report.txt`, `TARGET_RATE=3` for 18s), where
  `route_orders_list_needs_attention` landed at n=3 and the report correctly refused a
  percentile:
  ```
  route_orders_list_needs_attention_duration_ms n=3  BELOW threshold (30) - raw observations (ms): 9.86156 39.57392 9.94334
  ```
  That is exactly the failure mode named in review: three samples, and "p95" would have been
  the second-largest of three numbers dressed up as a percentile.
- **`MIN_N_FOR_STABLE_P99=100`**: above the first threshold but below this one, percentiles
  print but `p99` is flagged `UNSTABLE`.

**Every route in the three real size steps below cleared both thresholds** (n=131-725
throughout), so none of them needed the raw-observation fallback - the fallback code path is
real and demonstrated (above), but this campaign's own load shape did not need it. That is a
property of THIS run's rate/duration/weights, not a general guarantee: `n` here is a function
of `(TARGET_RATE x PLATEAU_SECS x route weight)`, not of dataset row count, which is also why
`sync_jobs_list`'s `n` (131-150) does not shrink as `order_records` grows from 10k to 1M -
the SAME load shape ran at every size.

## Row counts, seed, and the projection's own honesty limit

| Size step | `order_records` | `order_line_items` | `sync_jobs` | RNG seed |
|---|---|---|---|---|
| 10k | 10,000 | 24,995 | 122,869 | 0.271828 |
| 100k | 100,000 | 249,836 | 122,869 | 0.271828 |
| 1M | 1,000,000 | 2,499,313 | 122,869 | 0.271828 |

Catalogue (seeded once, shared by all three steps): 10,006 products, 20,000 variants, 40,000
`inventory_items` (2 connections), 60,428 `identifier_mappings` rows.

Three sizes bracket a curve; they do not locate an exact crossover. What can be said precisely:
the `orders_list_needs_attention` route crossed no round number by design between these three
points, and its degradation is **monotonic and mechanistically explained** (the COUNT), not
merely correlated with row count - which is the strength of this report over a plain
before/after pair.

**Bytes per order** (measured, this synthetic dataset only): `order_records` + `order_line_items`
together occupy 2,334 MB at 1,000,000 orders (`pg_total_relation_size`, includes indexes) -
**~2.4 KB/order**. This is almost certainly a FLOOR for a real deployment: the seeded
`orderSnapshot` is a minimal synthetic document (`totals`, one `shippingAddress` field, an
`items` array of placeholder objects); a real order snapshot carries the full buyer address,
payment details and richer line items, and would be larger per row.

**Rows per day is deliberately NOT reported, and the decline is the answer rather than a gap.**
#2843's criterion 14 asks for bytes per order **and** rows per day, *each qualified by an assumed
arrival rate*. Bytes per order is measured above. Rows per day is not, because **no arrival rate
was set for this scenario** - row count and arrival rate are independent axes by #2849's own
design, and this pass exercises dataset-size only. The criterion asked for the qualifier, so the
qualifier's absence is the honest answer to it: an arrival rate invented here would be a number
with no measurement behind it, and a "days until 1M" figure derived from it would travel and get
quoted exactly as this report's own 3.6x did (see the correction at the top). Nothing further
needs measuring to get it - fix an arrival rate in a scenario that actually drives one, and rows
per day is that rate multiplied by this dataset's **~3.5 rows per order** (1 `order_records` row
plus ~2.5 `order_line_items` rows, from the table above), with the ~2.4 KB/order figure giving
bytes per day on the same multiplication.

## The api's own statement_timeout guard broke the seeder, and the fix generalises

**Found live, not theoretical.** `apply_statement_timeout` (`scenarios/f5-read-path.sh`) sets
`ALTER ROLE "postgres" SET statement_timeout = '30000ms'` to bound the runaway-read risk named
in this issue's own text (the api's pool connection is where an unbounded aggregate would pin a
connection for the whole window). On this lab stand the api and the seed scripts connect as the
SAME Postgres role, so the very first 1M-scale seed attempt after that guard was applied got
**cancelled mid-transaction** by its own statement_timeout (900k-row bulk `INSERT` genuinely
takes ~90s, well over 30s) - `psql:<stdin>:66: ERROR: canceling statement due to statement
timeout`. The transaction rolled back cleanly (no partial rows, confirmed: `order_records` held
exactly 100,000 rows immediately after, matching the prior successful step precisely), so this
was a lost run, not corrupted data - but it is exactly the kind of role-scoped side effect that
would be easy to miss in a production topology too, if a migration or bulk-admin job ever shares
a role with the application pool. The fix is a SESSION-scoped `SET statement_timeout = 0`
prepended to every seed script's own connection (`seed/seed-lib.sh`'s `seed_sql`), which
overrides the role-level default for that session only and leaves the role config - and the
api's own pool - untouched. Recorded in `docs/lessons.md`-shaped detail in `seed-lib.sh`'s own
comment, since it is the kind of interaction a docblock is more likely to survive as than a
one-line changelog entry.

A second, smaller methodological lesson from the same incident: **the additive-sizing contract
means a size step can only be honestly re-measured before the dataset grows past it.** An
attempted resume of this campaign (before the statement_timeout fix was diagnosed) briefly
re-entered the "10k" and "100k" labelled size steps against a table that had already grown to
1,000,000 rows, and wrote a wrong `rowCounts.order_records: 1000000` into the "10k" step's
`manifest.json` before the run was killed (its `k6-summary.json` was untouched - the actual
measured requests happened correctly, before the contamination, against the real 10k-row
table). That manifest field is corrected in the committed artifact; `scenarios/f5-read-path.sh`
now accepts `F5_ONLY_SIZE`/`F5_ONLY_LABEL` to resume or repair exactly one size step without
re-touching the others.

## What this did not establish

- **The exact row count at which `orders_list_needs_attention` crosses any specific latency
  threshold.** Three points bracket a curve (10k: 11.4 ms: 100k: 47.7 ms: 1M: 149.0 ms); they do
  not locate where it crosses, say, 100 ms - only that it is between 100k and 1M.
- **Whether the 100k-scale COUNT plan was parallel or not.** The additive-sizing contract means
  the 100k-row state of `order_records` no longer exists to `EXPLAIN` directly once the dataset
  grew to 1M within this campaign; the sub-linear 100k->1M ratio is established from
  `pg_stat_statements` timing and a live 1M-scale `EXPLAIN`, not from a 100k-scale `EXPLAIN`.
  (The sub-linear ratio itself is withdrawn as a *conclusion* about the curve - it holds for
  10k-1M and not past 1M. See the correction at the top of this report.)
- **Whether the parallel-scan self-healing observed at 1M holds under real production
  concurrency**, where `max_parallel_workers_per_gather` is shared across every concurrently
  running query, not just this scenario's own `browse_mix` traffic.
- **The catalogue-side ILIKE/trigram sites** (`offer_mappings`, `destination_categories`) -
  no `Offer` or `DestinationCategory` rows exist in this seed; a follow-up seeder pass is needed.
- **The real-path validation this issue's own dependency (#2846 stub-diff sampling) calls for.**
  Building #2846 is a separate epic-scale effort; this pass instead asserted the seeded
  distribution against stated targets post-seed (see each `seed-*.sh` script's own
  `distribution gen=...` log lines - all landed within the stated +/-5pp tolerance) and
  confirmed every CHECK constraint held in the real migration-built schema (no insert failed).
- **A production arrival-rate-derived "days until 1M orders" figure.** Row count and arrival
  rate are independent axes by design (#2849); no arrival rate was fixed for this scenario, so
  none is derived here. This is a **deliberate decline against #2843's criterion 14, not an
  oversight** - the criterion asked for the arrival-rate qualifier, and inventing one to produce
  a figure is the failure mode, not the fix. See "Bytes per order" above.
- **Whether the api and the seed path sharing one Postgres role is a lab-stand artifact or a
  real production topology.** This report fixed the resulting failure at the harness level
  (a session-scoped override); whether a real deployment's migration/admin role is genuinely
  separate from its application pool role was not checked.

## Issue candidates (filed as follow-ups, not fixed here - this child measures)

1. **Add a GIN or expression index (or an estimated/capped total) for the `syncStatus`
   jsonb-containment health filter on `order_records`**, or accept the documented cost formally
   with a stated row-count ceiling. This is the report's own headline finding.
2. **Generalise the same question to every OTHER paged list that reports an exact `total`**
   (`GET /products`, `GET /sync/jobs`, `GET /returns`, ...) rather than fixing `orders` alone -
   the mechanism is "any exact COUNT over an unindexed predicate", not an orders-specific defect.
3. **Seed `offer_mappings` and `destination_categories`** so the two remaining #2843-named
   catalogue-side sites (ILIKE search, trigram search) can be measured at row count.
4. **Investigate the `page_shell_total` growth** (2.1x, 10k->1M) given four of its five
   constituent probes touch catalogue-fixed tables - likely connection-pool contention with
   concurrent traffic rather than a single slow query, but not confirmed here.
