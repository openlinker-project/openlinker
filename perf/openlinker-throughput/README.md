# OpenLinker throughput harness (#2841, epic #2840)

Measures how hard the worker can actually drive a real shop, with every
arrange/observe precondition made executable rather than left as prose a
human has to remember at 6pm. This is the successor to
`perf/prestashop-baseline`, whose README records the failure mode that
justifies it:

> `run-a1a-at-offset.sh` … the first version of that script silently failed
> to seed (it wrote a `cursorValue` column that does not exist; the real one
> is `value`) and measured offset 0 while claiming offset 99 000.

Eight new flows would have meant eight more chances at exactly that. So
every guard, the manifest writer, the queue sampler, the verdict writer and
the drain-wait loop live in **one file, `lib.sh`**, and every scenario script
sources it rather than re-implementing any piece of it.

## Files

| File | What it does |
|---|---|
| `lib.sh` | The library. Sourced, never executed directly - `bash lib.sh` loads function definitions and does nothing else. |
| `bootstrap.sh` | Takes a freshly reset stand to a state where every scenario can run (module install, WebService key, tax rules group, WooCommerce REST key, OpenLinker connections, Allegro offer mappings), idempotently, and emits `stand-ids.env`. |
| `lib-test.sh` | Unit tests for `lib.sh` and for `bootstrap.sh`'s argument parsing - everything testable without a live stand. Run with `bash lib-test.sh`. |
| `stand-ids.env` | Generated by `bootstrap.sh`. Sourced automatically by `lib.sh` if present. Never hand-edited. |
| `scenarios/f3-webhook-burst.sh` | First scenario built on `lib.sh` (#2842) - webhook ingress burst throughput. See "F3 - webhook ingress burst throughput" below. |
| `drivers/presign-webhooks.mjs` | Node pre-signer for `f3-webhook-burst.sh` - builds a pool of fully OL-HMAC-signed webhook requests ahead of time, reusing `apps/e2e/src/support/webhooks.ts` rather than restating the scheme. |
| `drivers/webhook-burst.js` | k6 driver for `f3-webhook-burst.sh` - replays the pre-signed pool under `ramping-arrival-rate`. Computes no HMAC. |

Not owned here: `docker-compose.lab.yml` and `preflight.sh` are **#2854's**
(the `lab` stand itself - Postgres's `pg_stat_statements`/`auto_explain`
preload, the credential env vars, the `--scale worker=3` capability). This
child calls `preflight.sh`, it does not define it. `run-all.sh` and
`report/campaign-report.sh` are **#2845's** (the unattended, resumable,
multi-scenario campaign runner built on top of this library).

## Writing a scenario script

```bash
#!/usr/bin/env bash
set -euo pipefail
LIB_LOG_PREFIX="my-scenario"
source "$(dirname "$0")/lib.sh"

CONN_IDS="'${PS_CONNECTION_ID}'"   # single-quoted for SQL IN(...) - see below

# --- pre-flight, fatal, before any load ---
guard_queue_empty "$CONN_IDS"
guard_scheduler_off
guard_demo_mode_off
guard_connection_budget
guard_pool_recorded
guard_build
guard_runner_state enabled
guard_log_level
guard_perf_max_attempts

snapshot_jobs_before "$CONN_IDS"     # required before post_guard_requeues can answer
DIR="$(results_dir_init my-scenario "run$(date +%s)")"
window_start "$DIR" my-scenario "$CONN_IDS" 0 '{"arrivalRatePerSec": 5}'

# --- drive load here ---
enqueue_perf_job master.product.syncAll "$PS_CONNECTION_ID" '{}' "my-scenario:$(date +%s)"
STATE="$(drain_wait "$CONN_IDS")"

window_stop "$DIR"
run_post_guards "$DIR" "$CONN_IDS" "$(date -u -d @$WINDOW_START_EPOCH +%Y-%m-%dT%H:%M:%SZ)" \
  "$WINDOW_START_EPOCH" "$WINDOW_STOP_EPOCH" "$PS_CONNECTION_ID"
```

Connection ids passed to any guard or post-guard are always a **SQL-ready,
comma-separated, single-quoted list** (e.g. `"'id-1','id-2'"`), because every
one of them lands directly inside a `WHERE "connectionId" IN (...)` clause -
`lib.sh` never builds that quoting for you, since a scenario's own set of
connections varies.

## Every guard, and what makes a run invalid

Guards are **fatal and pre-flight** - they abort with `exit 1` and a message
naming the remedy, before any load is applied. A guard that aborts before
the window costs seconds; a post-guard that discards after costs the whole
run, which is why the split exists.

| Guard | Fails when |
|---|---|
| `guard_queue_empty <conn_ids>` | Any `queued`/`running` `sync_jobs` row already exists for the given connections. |
| `guard_scheduler_off` | Any worker container has `OL_SCHEDULER_ENABLED` other than `false`. Also captures the `operational_settings` cadence row into `MANIFEST_SCHEDULER_CADENCE_ROW` - the cadence half of "no cron can fire" is not env-var-only, since an `operational_settings` row overrides `cronEnvVar`/`defaultCron`. |
| `guard_demo_mode_off` | The api container has `OL_DEMO_MODE=true`. |
| `guard_connection_budget` | `OL_DB_POOL_MAX × (1 api + N workers) >= Postgres max_connections`. Records both numbers (`MANIFEST_OL_DB_POOL_MAX`, `MANIFEST_MAX_CONNECTIONS`, `MANIFEST_DB_CONNECTION_BUDGET`) - this is a reported condition as well as a pre-flight, since the pool ceiling is the real ingress concurrency ceiling a throughput number is measured against. |
| `guard_pool_recorded` | Called before `guard_connection_budget` populated the globals it checks. Cheap to call again; exists to catch a call-order regression. |
| `guard_build` | Any of the api/worker containers' `org.opencontainers.image.revision` image label is absent, or does not equal `git rev-parse HEAD`. A digest diff was rejected (see below) - this is a `LABEL`, read via `docker inspect --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'`. |
| `guard_runner_state <enabled\|disabled>` | The running worker's `WORKER_RUNNER_ENABLED` posture does not match what the scenario declares. When `enabled` is expected, an **absent** "Starting sync job runner loop" log line is *also* a failure - never read as "nothing to report", because the field initializer the runner falls back to when disabled (`fan-out: {total:1, perScope:1}`) is stale and must never be silently manifested as though it had been resolved. |
| `guard_log_level` | `OL_LOG_BODY_MAX_BYTES` is unset or `0` on the api or any worker container. Both mean **uncapped** full-body logging, and the log sites that matter run at `error`, so raising the log level does not suppress them. |
| `guard_perf_max_attempts` | `PERF_MAX_ATTEMPTS` is not a positive integer strictly below the `sync_jobs` entity default of 10, or `sync_jobs` cannot be written to. See "Why maxAttempts is capped after enqueue, not at enqueue" below. |

### Why `guard_build` is a LABEL, not a digest diff

There is no version/build-info surface anywhere in `apps/api/src`, and a
plain image-digest comparison against a fresh rebuild is not
content-reproducible: a clean rebuild of identical source can land a
different digest, and a layer-cache hit can reproduce a **stale** digest
without rebuilding anything. Either failure mode is worse than the one this
guard exists to catch. The Dockerfile's `production` and `worker` stages
each declare `ARG OL_GIT_SHA=unknown` / `LABEL
org.opencontainers.image.revision=$OL_GIT_SHA` - pass `--build-arg
OL_GIT_SHA=$(git rev-parse HEAD)` when building (#2854's job); an image built
without it defaults to `unknown`, which correctly fails the guard rather
than silently passing.

### Why `maxAttempts` is capped after enqueue, not at enqueue

`POST /v1/sync/jobs` (`EnqueueSyncJobDto`) has no `maxAttempts` field, so
every perf job starts at the `sync_jobs` entity default of 10, with backoff
capped at 6h - roughly 30.25h to reach `dead`. `enqueue_perf_job` enqueues
through the ordinary API, then downgrades that one row's `maxAttempts` to
`PERF_MAX_ATTEMPTS` (default 3) with a direct `UPDATE` against the harness's
own database access - an operational action against our own data, not a
product-code change or a new config surface. `guard_perf_max_attempts`
verifies the mechanism (a sane cap value, a working write path) before any
job is enqueued. Belt-and-suspenders: `drain_wait`'s own max-wait timeout
(below) marks a stalled row `dead` regardless of whether a scenario used
`enqueue_perf_job` for a given job.

## Post-guards - run AFTER the window, mark the run `DISCARDED`

| Post-guard | Discards when |
|---|---|
| `post_guard_attempts <conn_ids> <window_start_iso>` | Any job created in the window shows `attempts > 1`. |
| `post_guard_deferrals <conn_ids> <window_start_iso>` | Any job in the window carries `deferredTotalMs > 0`, or `drain_wait` itself observed a deferred row (`DRAIN_DEFERRED_SEEN=1`). A penalty-free deferral (`requeueWithoutPenalty`) deliberately never touches `attempts`, so the attempts guard alone cannot see it. |
| `post_guard_requeues <conn_ids>` | `StuckJobRecoveryService`'s `requeueStuckJobs` touched a row in the window - detected by comparing a BEFORE snapshot (`snapshot_jobs_before`, **must be called before `window_start`**) against the current state: same `attempts`, was `running` with a `lockedAt`, now `lockedAt IS NULL`. Neither `attempts` nor `deferredTotalMs` moves on this path, so it is invisible to both guards above. |
| `post_guard_destination_creates <window_start_iso> [destination_conn_id]` | Any `order_records` row created in the window carries a `syncStatus` entry with `status:'failed'`, or (when a destination is named) lacks `syncedAt` for that destination. The only guard that can see `OrderSyncService.dispatchToDestinations`'s `Promise.allSettled` swallowing a per-destination failure while the job itself still reports `outcome:'ok'`. |
| `post_guard_limiter_degraded <window_start_epoch> <window_stop_epoch>` | Any worker's log, in the window, contains the Redis rate limiter's degraded-mode message ("falling back to per-process in-memory limiting"). At three replicas a degraded episode silently turns a configured 60/min into ~180/min. |

`run_post_guards <dir> <conn_ids> <window_start_iso> <window_start_epoch> <window_stop_epoch> [destination_conn_id]`
runs every one of these and writes `verdict.txt`: `VALID` if every post-guard
answered `ok`, `DISCARDED` with every non-`ok` reason listed otherwise.

## `drain_wait` - a timeout, not just a loop

Three states can each stall a naive "wait until the queue is empty" loop
forever: a penalty-free deferral (`nextRunAt` up to 1h out), a stuck-job
requeue (`StuckJobRecoveryService`, `maintenance` role, 15-minute lock
timeout), and a genuinely stuck job. `drain_wait <conn_ids>` polls every
`DRAIN_POLL_SECS` until `DRAIN_IDLE_TICKS` consecutive quiet polls, or until
`DRAIN_MAX_WAIT_SECS` elapses - at which point it marks every remaining
`queued`/`running` row for those connections `dead`, records their ids
(`DRAIN_DEAD_IDS`), and echoes `timed_out` instead of `drained`. One hung
scenario can therefore cost at most `DRAIN_MAX_WAIT_SECS`, never the rest of
an overnight campaign.

## `reset_between_repeats` - more than a cursor delete

`perf/prestashop-baseline/run-a1a.sh` already deleted the `connection_cursors`
row between repeats, but never touched Redis - `#2590` measured 37,500+
`jobdedup:*` keys standing on the shared `redis-data` volume, each carrying a
**7-day TTL**. An 8h campaign sits entirely inside that window, so a
cursor-only reset lets repeats 2 and 3 silently dedupe every enqueue to
`{isExisting:true}` while the cursor still commits and every other guard
still passes - the run reports `n=0` and reads as `VALID`.
`reset_between_repeats <conn_ids> <cursor_keys_csv>` deletes both: the named
`connection_cursors` rows, and every `jobdedup:*:{connectionId}:*` Redis key
for each connection (SCAN, never KEYS - this runs against the shared volume
and must never block).

## The results contract

One directory per scenario **run** (not per scenario - a scenario repeated 3
times produces 3 of these), created by `results_dir_init <scenario> <label>`
under `$RESULTS_ROOT/<scenario>/<label>/`:

| File | Written by | Contents |
|---|---|---|
| `manifest.json` | `window_start` (via `manifest_write`), before any load | git sha, connection ids, `quick` flag, runner state + lane caps, pool ceiling + budget, the `operational_settings` cadence row, `OL_LOG_BODY_MAX_BYTES`, `sync_jobs` row count at start (and at end, filled in by `window_stop`), postgres/node/image versions, host CPU/RAM/load, container resource limits (or the literal string `"none"`), and the sampler's own excluded-query list. **Never hand-edited.** |
| `summary.json` | The scenario script itself (not `lib.sh` - the summary shape is scenario-specific: throughput, latencies, whatever that flow measures) | Must carry the within-run sample size `n` beside every published statistic - a percentile's validity depends on `n`, not on how many repeats produced it (#2845). |
| `timeseries.csv` | `sample_queue` / `sampler_start` | One row per observer tick: `ts,dt,queued,running,dead,deferred,pg_database_size_bytes,docker_stats_json`. `dt` is the ACTUAL interval since the previous tick, never assumed to be `SAMPLE_INTERVAL_SECS` - `docker stats --no-stream` alone costs ~1s for eleven containers, so a nominal 1Hz tick drifts under load. |
| `verdict.txt` | `verdict_write` (directly, or via `run_post_guards`) | See schema below. |
| the raw k6 JSON output | the scenario script, if it drives load via k6 | Not produced by `lib.sh` - a scenario that doesn't use k6 doesn't have one. |
| a dump of the window's `sync_jobs` rows | the scenario script (e.g. `pg_sql "SELECT * FROM sync_jobs WHERE ..." > "$dir/sync_jobs.tsv"`) | Not produced by `lib.sh` directly - the exact WHERE clause is scenario-specific. |

### `verdict.txt` schema

One `key=value` per line, LF-terminated. `--resume` (#2845) parses this as a
machine contract, so the schema is fixed:

```
status=VALID|DISCARDED
generatedAt=<ISO8601>
reason=<free text>            # zero or more, DISCARDED only, one per line
```

`verdict_read <dir>` echoes `status` on its own first line, followed by every
`reason` line, in file order (`verdict_read "$dir" | tail -n +2` for just the
reasons). A directory with no `verdict.txt` echoes `MISSING` and returns
non-zero - never silently treated as either verdict.

### The sampler excludes itself from `pg_stat_statements`

`sample_queue`'s call to `GET /v1/connections/:id/sync-status` runs the
connection-sync-status aggregate over a 7-day window against the very system
under test, and every statement it issues lands in `pg_stat_statements`
(#2843's instrument). `manifest.json`'s `excludedPgStatStatementsQueries`
records that fact explicitly rather than silently, so a "top queries by
total time" report built from `pg_stat_statements` knows to exclude it.

## Agreement arithmetic (`compute_agreement`)

`compute_agreement <r2> <r3>` returns `|r2 - r3| / median` as a decimal -
the arithmetic #2845's `publish_if_agreed` compares against a per-flow
threshold before publishing either value. This library owns only the
arithmetic; the threshold and the fourth-repeat retry are #2845's policy.
**Two runs that both measure zero agree perfectly under this formula alone**
(numerator and denominator both zero) - `compute_agreement` does not guard
against that on its own, because refusing an all-zero comparison needs a
stated minimum sample size `n`, which is a policy decision #2845 owns
(`publish_if_agreed`), not an arithmetic one this library can make for it.

## `jq` vs `python3`

`perf/prestashop-baseline`'s scripts parsed JSON with `python3 -c ...`.
`lib.sh` and `bootstrap.sh` use `jq` instead - `jq` is added to
`bootstrap.sh`'s own tool preflight check. `python3` is still required (and
checked) because two bootstrap-specific, non-duplicated pieces still use it
(a random WebService key via `secrets.token_hex`, and the `connection_test`
success/message parse) - converting those was out of scope for this pass, to
avoid touching working code with no shared-library reason to change it.
`#2854`'s own `preflight.sh` must also check for `jq`, or a missing `jq`
surfaces mid-run rather than as a named message at the start.

## Testing

`bash lib-test.sh` exercises everything that does not need a live stand:
guard argument handling (every guard, both directions), the verdict schema
round-trip, manifest assembly (via `jq`), the agreement-rule arithmetic, and
`--dry-run`/`--verify-only`/`--help` argument parsing on `bootstrap.sh`.
`docker`, `pg_sql`, `pg_sql_write` and `git` are redefined as fake bash
functions after sourcing the real ones - bash resolves a function call by its
definition at call time, so every guard's real code runs unmodified against
canned answers, with zero real containers touched. `bootstrap.sh` guards its
own `main` behind `if [ "${BASH_SOURCE[0]}" = "${0}" ]`, specifically so the
test file can `source` it (to reach `would()` and the argument-parsing loop)
without ever invoking `main` against a stand that may not exist.

## F3 - webhook ingress burst throughput (#2842)

Measures what `POST /webhooks/:provider/:connectionId` can absorb under a
sustained arrival-rate burst, and what happens at the durability gate
(ADR-005 / ADR-049 decision 1) when the same `eventId` arrives many times at
once. Full design: `docs/plans/implementation-plan-f3-webhook-burst.md`.

### Why it needs its own connection

`bootstrap.sh`'s `perf-prestashop` connection has no `OrderSource`
capability, so an `order.*` webhook event addressed to it is `ungated` and
lands `deadlettered` with no `sync_jobs` row - measuring against it would
silently report a one-insert transaction instead of the real two-insert
gate. `bootstrap.sh` therefore also seeds `perf-webhook-ingress`
(`platformType: prestashop`, `enabledCapabilities: ["OrderSource"]` alone),
exported as `WEBHOOK_CONNECTION_ID` in `stand-ids.env` - which also keeps
this scenario's traffic off the connection an operator's other scenarios use.

### Running it

Both modes need the usual `lib.sh` container-name overrides (see
"Environment variables" above) plus `WEBHOOK_CONNECTION_ID` (from
`stand-ids.env`, or exported by hand if the connection was created outside
`bootstrap.sh`):

```bash
export PS_CONTAINER=<your-prestashop-container>
export PG_CONTAINER=<your-postgres-container>
export OL_API_CONTAINER=<your-api-container>
export WORKER_CONTAINERS=<your-worker-container(s)>
export WEBHOOK_CONNECTION_ID=<connection id>

# The driver self-test - proves the moving parts, writes nothing under results/:
bash perf/openlinker-throughput/scenarios/f3-webhook-burst.sh --smoke

# The real measurement - every #2841 guard runs, no skip flag exists:
bash perf/openlinker-throughput/scenarios/f3-webhook-burst.sh
```

`--smoke` runs the differential probes (P1-P4, below), builds a small
pre-signed pool, and fires a short low-rate k6 burst against the live API -
useful on any stand (including a shared workstation one) to prove the rig
works, never to produce a number. The strict (no-flag) path is the real
measurement: every `lib.sh` guard, `guard_runner_state disabled` specifically
(the gate commits real, executable `sync_jobs` rows - with the runner on,
a burst of routable webhooks becomes that many jobs executing inside the
measurement window), the three arms, the pg-side sampler, `run_post_guards`,
and a dated report under `results/results-F3-<date>.md`.

### The differential probes (P1-P4)

Four small sequential requests - never part of the k6 burst - that reach
four different depths of `WebhookService.processWebhook`:

| Probe | What it sends | Stops after | HTTP | `webhook_deliveries.status` |
|---|---|---|---|---|
| P1 `auth-fail` | valid envelope, wrong signature | connection-read + secret-resolve + verify | 401 | (never reaches the table - ADR-005) |
| P2 `decode-reject` | valid signature over a non-envelope body | decode/validate | 400 | (never reaches the table) |
| P3 `routable-product` | valid `product.updated` envelope (connection has no `ProductMaster`) | routing decides `ungated` | 202 | `deadlettered` |
| P4 `routable-order` | valid `order.created` envelope (connection has `OrderSource`) | full path | 202 | `job_enqueued` |

Verified live against the shared demo stack (2026-09-05/06, connection
`a28e768e-72d5-4315-bbf6-dc58e13fb6f4`, driver self-test only - see the
epic's own tracking issue for the caveat this is not a lab-stand figure):
`401` / `400` / `202` (`deadlettered`) / `202` (`job_enqueued`), exactly as
the table above states.

### The three arms

| Arm | `eventId` supply | What it isolates |
|---|---|---|
| `unique` | fresh id per request | headline ingress throughput, no index contention |
| `replay-committed` | ids already committed by the `unique` arm's own pool | pure unique-index probe, lock-free duplicate path |
| `replay-concurrent` | a small pool of ids (default 5) replayed at the full rate | every waiter serializes on ONE index tuple |

Reported separately, never averaged (one is lock-free, the other fully
serialized) - see the plan's §3.3 for the reasoning, including the
`OL_DB_POOL_MAX` pool-exhaustion failure mode `replay-concurrent` watches for.

### Reusing the real signer, and computing zero HMACs inside the window

`drivers/presign-webhooks.mjs` runs on the HOST with
`node --experimental-strip-types` and imports `signWebhook` /
`computeOlHmacSignature` straight out of `apps/e2e/src/support/webhooks.ts` -
it does not restate the OL-HMAC scheme. That import works because the e2e
file uses only erasable TypeScript syntax and imports nothing but
`node:crypto` (verified live; host Node here is v22.14.0, the demo stack's
containers run 22.23.1 - both accept the flag). If that file ever gains
non-erasable syntax (an enum, a decorator, a parameter property), the import
breaks LOUDLY at the `import` line - the point of importing rather than
copying. The pre-signer writes a pool of fully-signed requests (`pool.json`);
`drivers/webhook-burst.js` (a k6 script, run inside the `grafana/k6:1.0.0`
container) replays those bytes verbatim under `ramping-arrival-rate` and
computes no HMAC of its own - the stand pins no CPUs, so k6 signing
thousands of requests would contend with the api for the exact CPU the api
needs to answer them.

### k6: the image, the network, and a Docker Desktop credential-store quirk

`grafana/k6:1.0.0` must be pulled once per host:

```bash
docker pull grafana/k6:1.0.0
```

On a machine where `~/.docker/config.json` points `credsStore` at a helper
that fails (seen live: `credsStore: desktop.exe` under WSL, whose helper
errors with `error getting credentials`), route around it with an empty,
throwaway Docker config directory:

```bash
DOCKER_CONFIG=/tmp/docker-anon docker pull grafana/k6:1.0.0
```

This is a workstation quirk, not a stand requirement - a Linux host with a
working credential store needs no workaround. `f3-webhook-burst.sh` runs the
k6 container with `--user "$(id -u):$(id -g)"` (not a `chmod` on the results
directory) so it can write `--summary-export` into a bind-mounted, host-owned
directory - verified live: the image's default user (uid 12345) otherwise
gets a `permission denied` writing into the mount.

### Why the strict path cannot run on a shared workstation stand

`#2854`, the isolated lab stand, does not exist yet. The only stand
available while building this was the shared local demo stack, which
declares no `cpuset`/`cpus`/`deploy.resources` limit and currently shares a
host with a second full OpenLinker stack. Worse, it fails the guard chain
outright - verified live, in this order:

```
$ docker exec <worker> printenv OL_SCHEDULER_ENABLED
true                          -> guard_scheduler_off dies (a cron could fire
                                  into the measurement window)
$ docker inspect <api> --format '{{index .Config.Labels "org.opencontainers.image.revision"}}'
(no label)                    -> guard_build would die too: the image predates
                                  the LABEL this programme's Dockerfile change adds
$ docker exec <worker> printenv WORKER_RUNNER_ENABLED
(unset -> defaults enabled)   -> guard_runner_state disabled would die too
```

The scenario's own guard ORDER means `guard_scheduler_off` is the one that
actually aborts a run on this stand (the scheduler happened to be on); the
other two were confirmed independently, by direct inspection, since the
script never reaches them in that state. All three failures are the guard
chain working correctly - not a scenario bug - and none has an override
flag. Making them pass would mean rebuilding a shop-scale stand's images
from this branch and disabling its scheduler/runner, mutating a stack in
active use, for a number that still could not be published (the host is
contended and pins no CPUs). The publishable figure is taken on #2854's
stand by re-running this same, unmodified scenario.
