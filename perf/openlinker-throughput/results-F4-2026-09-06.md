# F4 - claim contention at N replicas (#2851)

Cross-flow report for epic #2840. Every number carries a label - **measured**,
**derived** or **extrapolated** - and the closing section states what this run
did not establish.

**Read this first, as with every report in this campaign.** The stand is a
Docker Compose project on a contended developer workstation, not an isolated
lab. 28 logical CPUs and 15.9 GB of RAM shared with two other running
OpenLinker stacks (`openlinker-*`, `ol-demo-fresh-*`) and, through the evening,
with other agents running other scenarios against the same `lab` project. Host
load average was 0.56 entering the 1-replica arm and 1.21 entering the
3-replica arm - **the two arms did not run under identical host load**, and the
busier one is the arm that looks better. Every figure here is a floor.

Both arms are **`DISCARDED`** by the campaign's own post-guards, for the same
reason, and that reason is this report's most important finding rather than a
disqualification. See § 4.

Run group `run1788736132`, image `37520b8b9`, lane caps in force
`realtime=4/2 bulk=12/8 fiscal=2/1 fan-out=8/4`, single connection
`perf-prestashop`.

## 0. What was blocking this, and what had to be built

Every performance figure OpenLinker has published is single-replica.
`results-D` states the limitation plainly - *"Lane caps bound one worker
PROCESS. Every cap figure is per process; N replicas multiply each effective
cap by N"* - and #2302 has carried it as a caveat since. It could not be tested,
for a two-line reason: `docker-compose.lab.yml` pinned
`container_name: lab-worker`, and `docker compose up --scale worker=N` refuses
to scale a service with a fixed container name.

Four things had to change before an arm could run at all.

1. **The fixed `container_name` is gone.** Compose now names the replicas, and
   it does so at scale 1 too, so the single-replica container is
   `lab-worker-1`, not `lab-worker`.
2. **`WORKER_CONTAINERS` is discovered**, from compose's own service label,
   rather than hardcoded. An explicitly-exported value that names a container
   which does not exist is refused with the rename named - because
   `WORKER_CONTAINERS=lab-worker` was the documented export until this change,
   so a stale one is the single most likely way a scenario meets this code.
3. **`WORKER_ID` carries the hostname.** It was `worker-${process.pid}-…`, and
   `process.pid` is `1` in every container, so `sync_jobs.lockedBy` held one
   value fleet-wide and could not answer *"which replica claimed this job"* -
   the question this whole flow is about. It now reads
   `worker-c6c731116d20-1788733907162`. The `Date.now()` suffix stays:
   `refreshJobLock` guards its heartbeat on `lockedBy`, so a restarted replica
   must not present the identity of the incarnation whose rows it no longer
   owns.
4. **`enqueue_perf_job`'s attempt cap was repaired** (the defect F7 filed). It
   read `.id` off the enqueue response; `EnqueueSyncJobResponseDto` has no such
   field, so the `maxAttempts` cap had never applied to a single job on any
   run. Reading `.jobId` would not have fixed it either - that is the Redis
   stream entry id, not a `sync_jobs` key, and the durable row is written
   asynchronously by the intake consumer. This run is the first on which the
   cap actually applied (`600 row(s) capped at maxAttempts=3`).

## 2. Throughput and occupancy - **measured**

600 identical `master.product.syncFromSweep` / `master.inventory.syncFromSweep`
jobs (both `bulk`) against the real PrestaShop catalogue, per arm. F7's
aggressor verbatim, so the 1-replica arm is comparable with
`results-F7-2026-09-06.md`.

| | 1 replica | 3 replicas |
|---|---:|---:|
| Jobs | 600 | 600 |
| Drain wall time | **1054 s** | **381 s** |
| Throughput | **0.569 jobs/s** | **1.575 jobs/s** |
| Mean concurrent `running` | 7.44 | 21.01 |
| Peak concurrent `running` | 12 | 32 |
| Samples ≥ 8 concurrent | 66.4% | 91.3% |
| Samples ≥ 24 concurrent | 0.0% | 44.4% |
| Distinct `lockedBy` | 1 | 3 |
| Peak queued (due) | 591 | 576 |
| Peak Postgres backends | 11 | 30 |
| `sync_jobs` lock waits | **0** | **0** |
| Pool acquire timeouts | 0 | 0 |
| Rate-limit slot timeouts | 0 | 0 |
| Max deferred queue depth | 0 | 0 |
| Jobs dead / `attempts > 1` | 0 / 0 | 0 / 0 |

**Throughput ratio 3/1 = 2.77x** - **measured**, n=1 run per arm. A direction
and a magnitude, not a bounded figure: one run per arm cannot separate 2.77
from, say, 2.4 or 3.0, and the 3-replica arm ran under the higher host load of
the two.

**Work was shared almost perfectly evenly across the three replicas** -
33.4% / 33.3% / 33.3% of running-samples by `lockedBy` - with no coordination
beyond `FOR UPDATE SKIP LOCKED`. That is the claim doing its job.

### The occupancy figures over-read, and the reason matters

Per-scope `bulk` is 8, so one replica should hold at most 8 and three at most
24. The samples peak at 12 and 32. **This is an instrument artefact, not a cap
violation**, and the mechanism is worth stating because F7 used the same proxy:
lane slots are accounted **in process** and released when a handler resolves,
while the `sync_jobs` row stays `running` until a *separate* terminal write
commits. A row in that gap is counted by a `SELECT … WHERE status='running'`
and is not holding a slot. The over-read is proportional to in-flight terminal
writes, which is what the numbers show - r1 sits at 8 with rare excursions
(only 0.1% of samples reached 12), r3 sits around 21 with a longer tail.
Without #2850's `ol_lane_slots_in_use` the true in-process occupancy is not
directly observable, and this run does not claim it.

## 3. Where the scaling went - the five candidates, and a sixth

#2851 asks that a sub-linear result be *attributed from metrics*, not inferred,
and that the three DB-side shapes be told apart. Scaling here was close to
linear, so the question inverts: what did **not** get in the way.

| Candidate | Reading | Verdict |
|---|---|---|
| The claim query itself | mean 0.087 ms (r1, 5651 calls) vs **0.086 ms** (r3, 6444 calls) | **not the constraint** - per-call cost flat while replicas tripled |
| Index / heap cost at depth | `EXPLAIN (ANALYZE, BUFFERS)` on the real claim: 0.22-0.37 ms across depth 0, 1000 and each arm's own observed peak (591 / 576) | **exonerated at this scale** - see below |
| Pool saturation | 11 → 30 backends, budget 80 → 160 against 200; **0** acquire timeouts | **not the constraint** |
| Lock waits on `sync_jobs` | **0** in both arms, every sample | as `SKIP LOCKED` predicts |
| The shared Redis limiter | **degraded in both arms** | **this is the finding** - § 4 |
| The destination | 56.0 → 158.4 req/min | **§ 4** |

**The missing `(status, jobType, nextRunAt)` index is a measured "no" at this
scale.** #2851 names it as a channel invisible to both slot accounting and pool
metrics, and predicts claim cost growing with queued depth. It does not, here:
at a real observed depth of 591 queued rows the claim executes in 0.305 ms,
against 0.265 ms at depth 0. F7 saw the same shape more steeply (32x from depth
0 to 10 000) and reached the same conclusion about magnitude - under 2 ms even
at 10 000. **Not established**: whether the index would help at a depth an order
of magnitude beyond this, and what it would cost writes. Adding it was not
attempted, and on the evidence here there is nothing for it to fix.

Three DB-side shapes, told apart as #2851 requires: **pool exhaustion** would
show `connectionTimeoutMillis` errors plus acquire-wait - zero of both;
**lock waits** would show `pg_stat_activity.wait_event_type = 'Lock'` - zero,
every sample, in both arms; **claim cost** would show in the query's own mean
duration - flat. None of the three moved.

## 4. What actually happened: the destination saw 2.6x its declared rate limit

This is the #2302 harm, measured.

| | 1 replica | 3 replicas |
|---|---:|---:|
| PrestaShop webservice requests | 983 | 1006 |
| **Rate at the shop** | **56.0 / min** | **158.4 / min** |
| Connection's declared limit | 60 / min, maxConcurrent 4 | same |
| Degraded-limiter log lines in window | **2** | **2** |

The **same work** (983 vs 1006 requests - a 1.02x ratio, i.e. identical within
noise) was delivered **2.77x faster** by hitting the shop at **2.6x the rate it
declares it can take**. `perf-prestashop` carries no `config.rateLimit`, so the
effective limit is `prestashopAdapterManifest.defaultRateLimit`
(`requestsPerMinute: 60, maxConcurrent: 4`) - and at one replica the measured
56.0/min sits just under it, which is the limiter working.

**Why it did not hold at three.** The per-connection limiter is Redis-backed
and therefore global across replicas - which is exactly why the naive
expectation is that the outbound rate stays at 60/min however many replicas
run. It did not, because the limiter **degraded**. The log line names the
mechanism:

```
Redis rate limiter unavailable for connection c4710417-… - falling back to
per-process in-memory limiting (degraded, not unthrottled).
Redis rate-limiter call "claimConcurrency" timed out after 1000ms
```

Note what that says: **not that Redis was down - that a call to it exceeded the
limiter's own 1 s budget under load.** The adapter then paces per process, so
the fleet-wide ceiling becomes N x 60/min = 180/min at three replicas, and
158.4/min is squarely inside that. This is the hazard `results-C` measured at
one replica and `results-D` explicitly recorded as **unexercised**: *"With N
replicas a degraded episode would pace per process, so shop-side rate could
approach N x the declared limit. Not exercised - this run used one replica."*
It is exercised now.

Two honest qualifications. The degradation is a **timeout under load on a
contended workstation**, and a production Redis on dedicated hardware may not
time out at all - this stand is not evidence about frequency. And **degradation
was present in the 1-replica arm too** (2 lines), where it is harmless because
one process's fallback ≈ the declared limit; the replica count is what converts
a harmless fallback into an exceeded limit.

### Why both arms are `DISCARDED`, and why that is the finding

`post_guard_limiter_degraded` discards a window containing a degraded-limiter
line, which is the right call for a throughput measurement - the pacing changed
mid-window. Both arms tripped it. The throughput and rate figures above are
therefore **measurements of a degraded system**, and are reported as such.

**That guard could not fire before this run.** It filtered its log window with
`docker logs --since "@$epoch"`, and Docker accepts the `@`-prefixed form
without complaint while matching **nothing** - verified on Docker 29.5.2
against one container and one window: bare epoch 180 lines, RFC3339 180,
relative `25m` 180, `@epoch` **0**. The `@` is GNU `date` syntax, not Docker's.
So a *counting* guard whose count was structurally always zero read exactly
like a clean run, on every scenario of this campaign.

The consequence must be stated rather than left implicit:
**`results-F7-2026-09-06.md`'s claim that there were "zero
`post_guard_limiter_degraded` log lines (i.e. `degraded_mode_entries = 0` -
measured…)" is not supported by evidence.** The guard that produced it could
not see a degraded line. Whether F7's window actually contained one is unknown
and not recoverable from here. The guard is fixed, and `lib-test.sh` now
asserts on the arguments handed to `docker logs` - not on a count, because a
fake that answers regardless of the window would pass however the window was
spelled, which is how the defect survived in the first place.

## 5. What this means for the lane caps (#2867)

**No cap default changes on this evidence, and the reason is in § 4.** At three
replicas the effective `bulk` per-scope concurrency is 24 and the lane
behaved - the claim, the pool and the locks were all uninvolved. What broke was
the *outbound* pacing, one layer below the lane model. Lowering
`OL_LANE_BULK_SCOPE_CAP` would reduce the pressure that provoked the limiter
timeout, but it is the wrong instrument: the correct ceiling on outbound rate
is the limiter, and the limiter's problem is that it fails **open** (per-process
fallback) rather than closed.

It also sharpens what per-process enforcement costs. Making lane caps globally
enforced would **not** have prevented what this run measured - the limiter is
*already* globally enforced and it still degraded. A global lane cap would have
throttled the queue while leaving the failure mode untouched. That is an
argument for keeping enforcement per-process and fixing the limiter's
degradation path, and it is recorded as such in ADR-050's #2851/#2867
amendment.

## 6. What fought this run

Four defects, all in the harness rather than the measured system, all fixed
with regression tests (`lib-test.sh` 96 → 113 assertions). Three are the same
family and are now in `docs/lessons.md`.

1. **`docker logs --since "@epoch"` matches nothing** - § 4. The one with
   consequences beyond this scenario.
2. **`grep -q` under `pipefail` reports failure on a successful match.** `grep -q`
   exits at the first match, the upstream takes `SIGPIPE` (141), and `pipefail`
   takes the pipeline's status from it. Length-dependent: it passed once, then
   spun a boot-wait to its 60-try ceiling against a container whose log plainly
   carried the line.
3. **`| head -1` is the same trap** - it killed the first full run *after* a
   completed 17-minute arm had drained, at `verdict_read | head -1`. Replaced
   with `awk NR==1`, which reads to EOF.
4. **`tee /dev/stderr` truncates the log.** With stderr redirected to a file,
   `/dev/stderr` is `/proc/self/fd/2` and `tee` opens it `O_TRUNC` - erasing
   everything logged so far and restarting at offset 0.

A fifth, non-defect friction: the stand was contended by three other agents'
scenarios through the evening, and one earlier run of this scenario was killed
by a process restart, leaving its lock held. `guard_stand_exclusive`'s TTL is a
crash bound and the documented remedy (one `redis-cli DEL`) was used after
confirming the holder pid was gone.

## 7. What this did not establish

- **A clean (non-`DISCARDED`) throughput measurement.** Both arms ran with the
  limiter in degraded mode. A clean run needs either a Redis that does not time
  out under this load or a raised limiter call budget, and neither was
  attempted.
- **Frequency of limiter degradation.** Observed on a contended workstation
  with a 1 s call budget. This says the failure mode is reachable, not how
  often it occurs on real hardware.
- **Whether F7's window contained a degraded line.** Its guard could not see
  one; the run is over and the answer is not recoverable.
- **True in-process lane occupancy.** The `sync_jobs`-row proxy over-reads by
  the number of in-flight terminal writes (§ 2). #2850's
  `ol_lane_slots_in_use` is the instrument that would settle it.
- **Claim-loop tick rate** (`ol_claim_loop_ticks_total`). Not measured, not
  inferred. `pg_stat_statements` gives claim *calls* (5651 vs 6444) which is a
  different quantity - one tick may claim for four lanes.
- **Event-loop lag.** #2850 absent; not measured.
- **Anything at 4+ replicas.** `guard_connection_budget` would refuse a fourth
  at `OL_DB_POOL_MAX=40` against `max_connections=200`.
- **Anything about a second connection.** One `bulk`-capable connection exists
  on this stand, so the lane's TOTAL cap (12) was never the binding constraint
  and cross-scope fairness (ADR-050 decision 4) was not exercised at all.
- **Whether the missing index matters at greater depth.** Measured to ~591
  queued rows here and ~10 000 by F7; both trivial. No counterfactual with the
  index added was run, and #2964 separately measured and *rejected* an index on
  a related predicate.
- **Equal host load between arms.** Load average was 0.56 entering r1 and 1.21
  entering r3. The busier arm is the faster one, so this does not undercut the
  direction of the result, but the 2.77x is not a controlled figure.

## Issue candidates

- **The rate limiter fails open under its own call timeout.** A 1 s
  `claimConcurrency` timeout on a loaded Redis drops the fleet to per-process
  pacing, and at N replicas that is N x the operator's declared limit. Options
  worth weighing: a longer or adaptive call budget, failing *closed* to a
  conservative local rate rather than the full per-process allowance, or
  surfacing degraded episodes on the connection health surface where an
  operator would see them (today they are an `error` log line and nothing else).
- ~~**Re-run F7's cross-lane starvation scenario now that its degraded-mode
  post-guard works.**~~ **DONE, 2026-09-07** (#2852) - and the headline claim
  about lane isolation did stand: claim latency stayed flat across arms while
  the `bulk` lane held 7-8 concurrent jobs. The control that did not stand is
  now quantified - **>= 38 degraded-mode lines inside the re-run's window**,
  so that run is `DISCARDED` too, exactly as both arms of this one are. See
  `results-F7-2026-09-06.md` §8.
- **A second `ProductMaster`/`InventoryMaster` connection on the stand** would
  let a future run reach the `bulk` lane's TOTAL cap and exercise cross-scope
  fairness - the same gap F7 named.
