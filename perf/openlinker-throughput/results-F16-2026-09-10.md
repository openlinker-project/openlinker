## 1. What this measures

The bulk shop-publish path (`POST /listings/bulk-shop-publish`) against the real
WooCommerce connection, split the way the issue requires: a simple product and a
variable product are DIFFERENT units of work (a variable product is one parent
PLUS N variations, #1836) and are never averaged together.

- **arm A** - simple-product publish.
- **arm B** - variable-product publish, all sibling variants submitted together.
- **arm C** - a batch mixing real variant ids with one syntactically-valid but
  nonexistent id, exercising #1845's `totalCount` reconciliation.
- **arm D** - arm A resubmitted with `generateDescription: true`, reported
  separately and never blended into the baseline.

adapter; what is not available is throughput.

## 3. Arm D is reported beside arm A, never inside it

Same three products, same connection, `generateDescription: true` - 4 s against
arm A's 4 s. Read as "AI description generation did not visibly cost anything at
this size", and no further: three products is not a sample, and the arm exists
to keep the AI path OUT of the baseline rather than to price it.

## 4. Re-runnability, and the verdict defect it exposed

A second run of this scenario on the same stand **fails**, and before 2026-09-10
it failed while still reporting `status=VALID`.

WooCommerce refuses a duplicate SKU. The first run publishes the catalogue; the
second run's variations collide with the products the first one left behind:

    failed  product_invalid_sku  WooCommerce returned HTTP 400:
            https://wc-tls/wp-json/wc/v3/products/532/variations

Observed as **3 of 8 published in arm B**, with the run still VALID, because the
verdict keyed on arm C alone. Arms A and B are the CLEAN-publish arms and arm C
is the one that owns a partial failure by design; reading a failure in A or B as
a result made the two indistinguishable. The verdict now discards on any failure
in A or B (`arm-a-or-b-publish-failed`), and that was verified in both
directions on the day: a colliding re-run discards, and a run against a cleaned
catalogue is the VALID one reported above.

**To re-run**, delete this connection's `ShopProduct`-mapped products from
WooCommerce (`DELETE /wp-json/wc/v3/products/{id}?force=true`) and then the
`identifier_mappings` rows for `entityType='ShopProduct'`. The stand was left in
that state after this run. Automating that teardown inside the scenario is named
follow-up work; it is not done, so the manual step above is the contract today.
