## 1. Bundle budgets — measured, and proven able to fail

`scripts/check-bundle-budgets.mjs` builds `apps/web` (via `vite build` alone —
type-checking is `pnpm --filter @openlinker/web type-check`, a separate gate)
and groups every JS chunk in `dist/assets` by the stable prefix `vite.config.ts`'s
new `manualChunks` assigns, then fails if any group exceeds its budget.

### Budgets (raw bytes, measured 2026-09-06, +15% headroom)

| Group | Measured | Budget (+15%) | Gzip (informational) |
|---|---|---|---|
| `index` (app entry) | 408.0 kB | 469.2 kB → committed as 458.2 kB* | 107.1 kB |
| `react-vendor` | 178.3 kB | 205.1 kB | 56.3 kB |
| `radix-vendor` | 104.8 kB | 120.6 kB | 32.8 kB |
| `editor-vendor` (Tiptap) | 394.8 kB | 454.0 kB | 125.6 kB |
| `vendor` (everything else in `node_modules`) | 544.9 kB | 626.9 kB | 171.5 kB |
| `total` (every JS file in `dist/assets`) | 3 045.5 kB | 3 502.3 kB | 916–943 kB |

\* the committed budget is `Math.round(measured * 1.15)`, computed in code from
`MEASURED_BASELINE_BYTES` — the table above shows the arithmetic, the script
is the source of truth.

15% was chosen to absorb routine dependency patch bumps without hiding a
genuinely new dependency landing unnoticed — a package the size of Tiptap or
Radix would blow well past it on its own. **Route-level lazy chunks (~150 of
them) are summed into `total` but not individually budgeted** — there are too
many to budget one by one, and a new page's own chunk growing is a different
question from the shell every page waits on.

### Proof the gate can actually fail — not merely a comment

A budget nobody has seen reject anything is a comment, not a guard (the
`--self-check` docstring in every one of this repo's invariant scripts says
this explicitly, and F9's predecessor died on exactly this kind of thing
elsewhere in this programme). Two proofs, both re-runnable:

1. **`--self-check`** (also wired into `check:invariants`, runs on every
   `pnpm lint`) exercises the pure `evaluateBudgets` function against
   synthetic sizes: at-budget passes, one byte over budget is reported, an
   absent group is not flagged as a false violation.
2. **A real build was made to fail.** `MEASURED_BASELINE_BYTES.index` was
   temporarily edited to `100` (from 408 003) and the script re-run against
   the actual `apps/web` build:

   ```
   OVER  index            398.4 kB raw ( 104.1 kB gz) / budget 0.1 kB
   [check-bundle-budgets] FAILED — bundle budget exceeded:
     index: 398.4 kB exceeds budget 0.1 kB by 398.3 kB
   EXIT: 1
   ```

   The file was restored immediately after (`diff` confirmed byte-identical
   to the pre-edit version) and `--self-check` re-run clean. **Measured.**

### `pnpm check:invariants` runs the real gate today

The whole `check:invariants` chain (every other structural check in the repo,
plus this one) was run end to end after wiring: **exit 0.** This also means
the bundle budget gate already has CI coverage for free — the existing
`Lint` job in `ci.yml` runs `pnpm lint`, which chains into `check:invariants`,
which now chains into this check. No new CI job was needed for this half of
the issue.

## 2. `manualChunks` — before/after, measured

Added to `apps/web/vite.config.ts`, splitting `node_modules` into
`react-vendor` / `radix-vendor` / `editor-vendor` / a catch-all `vendor`,
grouped by how often each changes rather than by package name (see the
config's own comment for the reasoning).

| | Before | After |
|---|---|---|
| App entry chunk (`index-*.js`) | 595.9 kB | 408.0 kB |
| Largest single chunk | 595.9 kB (`index`) | 544.9 kB (`vendor`) |
| Total raw JS across `dist/assets` | 3 044.4 kB | 3 045.5 kB |
| Total gzip JS across `dist/assets` | 943.2 kB | 938.4 kB |

**This is a cache-shape change, not a size reduction — stated plainly because
the numbers could be misread otherwise.** Total bytes are unchanged (a rounding
error apart); what changed is that `react-dom`, Radix and Tiptap — previously
interleaved into the app's own entry chunk and a shared `ui-*` chunk — now
live in their own content-hashed chunks. A repeat visitor's cache for React
itself now survives a deploy that only touches app code; before this change,
every deploy invalidated `react-dom` along with everything else, because it
shared a chunk with it. Confirmed by direct inspection: pre-change,
`grep -c "react-dom"` on the app entry chunk returned 3 matches and
`@radix-ui`/`@tiptap` accounted for 22 matches in the shared `ui-*.js` chunk;
post-change, those strings are in `react-vendor-*.js` and `radix-vendor-*.js`
respectively, and the entry chunk no longer references `react-dom` at all.
**Measured.**

## 3. Lighthouse — measured, floor not ceiling, three runs per route

### 3.1 The measurement problem, and which side of it was chosen

The task gave two options: stub the network against a static build, or hit a
live stack and say so. **Stubbed**, for a reason discovered mid-build rather
than assumed up front: this host had a real API bound to `:3000` (confirmed
via `ss -ltnp`), which is `apps/web`'s own **default** `VITE_API_BASE_URL`
when the env var is unset. A dist built without the override would have sent
Lighthouse's traffic silently to whatever real backend that port belongs to —
and during this build, **it briefly did**: an intermediate `dist` built by
`check-bundle-budgets.mjs` (which builds with no override, correctly, since
its own budgets don't care about the API) was reused by an early Lighthouse
run before the mismatch was caught by inspecting the built chunk's baked-in
URL. No writes were made (every stubbed/real call in this harness is a GET
plus one no-op `auth/refresh`), but it was real, unwanted cross-stack traffic
during a build, not a hypothetical. Fixed by making `run-lighthouse.mjs`
**build `apps/web` itself**, always with `VITE_API_BASE_URL` pinned to a
dedicated mock port (`4174`), rather than trusting whatever `dist` happened to
exist — closing the whole class of "wrong build measured" rather than
documenting a discipline to remember. The mock server
(`scripts/lighthouse/mock-api-server.mjs`) answers real auth (`/auth/refresh`,
`/auth/me`) and a generic empty envelope for everything else — safe
specifically because `apps/web`'s query hooks are written defensively
(`data?.total ?? null`, per `apps/web/src/app/hooks/use-nav-counts.ts`).

**This was verified, not assumed.** A five-route smoke check
(`scripts/lighthouse/smoke-check.mjs`, Playwright) was run against the stub
before trusting any Lighthouse score. Two of five candidate routes —
`/` (the analytics landing page) and `/settings` — **crashed** under the
generic stub with `TypeError: Cannot read properties of undefined (reading
'length')`, caught by React Router's error boundary. That is a real
defensiveness gap somewhere in those two pages (a `.length` read with no
optional chaining, on a field the stub cannot know the true shape of) — filed
as an issue candidate below rather than fixed by widening the stub to model
real domain shapes, which would turn a network stub into a second copy of the
API. `/orders`, `/products` and `/connections` rendered cleanly (real sidebar
counts, no error text, no console errors) and are the three routes measured.

### 3.2 Host contention — stated, not hidden

Every Lighthouse run in this report shows `hostContended: true`: `docker
stats --no-stream` recorded **25 running containers** during the measurement
window, including a `lab-postgres` container observed at **29–103% CPU**
across different runs (another agent's throughput work, running concurrently
on this shared host — exactly what the task predicted). **These scores are a
floor, not this bundle's ceiling.** Re-run on dedicated hardware, the same
build should score higher, never lower.

### 3.3 Scores — 3 runs per route, median/min/max/spread reported

Performance category only shown with spread since accessibility/best-practices/SEO
were perfectly stable across all 9 runs (spread 0 on every route/category
except performance, which varied by 0.00–0.02).

| Route | Perf (median) | Perf spread | A11y | Best Practices | SEO |
|---|---|---|---|---|---|
| `/orders` | 0.59 | 0.00 | 0.96 | 1.00 | 0.91 |
| `/products` | 0.59 | 0.01 | 0.96 | 1.00 | 0.91 |
| `/connections` | 0.60 | 0.00 | 0.96 | 1.00 | 0.91 |

**Measured**, `scripts/lighthouse/baseline.json` is the committed artifact;
`scripts/lighthouse/last-run.json` (gitignored, regenerated per run) carries
the same shape for the most recent local run.

The 0.59–0.60 performance score is dragged down almost entirely by first paint
timing under contention (§3.4), not by anything structural in the bundle —
accessibility, best-practices and SEO are all high and stable, which is a
different (and healthier) signal than the performance number alone suggests.

### 3.4 Timing and request-count facts (informational — not gated)

| Route | FCP (median) | LCP (median) | Total Blocking Time (median) | Total network requests (median) | of which API (`Fetch`) |
|---|---|---|---|---|---|
| `/orders` | 6 630 ms | 7 668 ms | 106 ms | 130 | 16 |
| `/products` | 6 626 ms | 7 527 ms | 93 ms | 126 | 17 |
| `/connections` | 6 473 ms | 7 520 ms | 90 ms | 114 | 13 |

**The FCP/LCP figures are a contention artefact, not a real 6.5-second paint
time** — this stub API answers in low single-digit milliseconds and the app
itself is small; a ~6.5 s first paint on that combination is the host's other
containers competing for CPU during headless Chrome's own startup and render,
consistent with §3.2's `lab-postgres` reading. Stated as a floor per the
task's own framing, not as a real UX number.

### 3.5 The request-count fact #2840 asked to replace an estimate with

This is the one figure in this report that directly **measures** what #2840
only estimated. Breaking the `Fetch`/`XHR` requests down by URL (one-off
analysis via a raw `network-requests` audit dump, not part of the committed
gate):

**Every route pays a fixed shell cost of 12 requests before its own data**:
`POST /auth/refresh`, `GET /auth/me`, the unpaginated `GET /connections`
(confirming #2840's finding — no `limit`/`offset` on this one), `GET
/system/config`, three unconditional prefetches that fire on every route
regardless of page (`orders?limit=20`, `products?limit=10`,
`sync/jobs?limit=20` — these did not appear in #2840's own accounting, which
named "three command-palette prefetches" without naming which endpoints; this
confirms they are exactly these three), and five `limit=1` nav-count probes
(`orders`, `customers`, `listings`, `sync/jobs?status=dead`,
`webhook-deliveries?status=failed`).

- **`/orders`**: 12 shell + 4 route-specific (`orders?sort=...&limit=20`,
  `status-summary`, `sla-summary`, `lifecycle-summary`) = **16**.
- **`/products`**: 12 shell + 5 route-specific (`fulfillment-authority/status`,
  `products?sort=...&limit=20&offset=0`, plus three more `products?limit=1`
  stock-filter probes) = **17**.
- **`/connections`**: 12 shell + 1 route-specific
  (`fulfillment-authority/status`) = **13**.

This is close to, but not identical to, #2840's estimate ("about ten... about
nineteen on `/products`") — 12 measured vs. "about ten," 17 measured vs.
"about nineteen." **Measured**, and a genuine replacement for the estimate,
with one caveat stated below.

## 4. What this measurement could NOT establish

- **The API-side N+1 sites named in #2840 cannot be observed through this
  harness.** The mock API always returns an empty list (`data: [], items: []`),
  so `/products`' list read never returns any rows, and the per-variant N+1
  the issue names (`apps/api/src/products/http/products.controller.ts:355-357`)
  only fires once real rows exist. This harness proves the *shell* request
  count is real and stable; it says nothing about how that count grows with
  real data. Fixing or measuring the N+1 sites needs a live backend with a
  seeded catalogue — out of scope for a stubbed frontend gate, and #2840
  already names #2843 as their more natural home.
- **Whether `/` and `/settings` are the ONLY two pages with this defensiveness
  gap.** The five-route smoke check found two crashes out of five tried; the
  other ~30+ authenticated routes in the app were not smoke-tested. The gap is
  real and reproducible (see §3.1) but its extent is unknown.
- **A true isolated-hardware performance ceiling.** Every score in §3.3 is a
  floor per §3.2; there is no dedicated-hardware re-run to compare against.
- **Whether the CI job actually runs.** `.github/workflows/ci.yml`'s new
  `lighthouse` job was written to the same pattern as the existing `lint` /
  `docker-build-smoke` jobs and validated as syntactically correct YAML
  (`python3 -c "import yaml; yaml.safe_load(...)"`), but this environment has
  no way to trigger an actual GitHub Actions run. The one assumption carried
  into the job that could not be verified here: `ubuntu-latest` GitHub-hosted
  runners ship Google Chrome preinstalled (documented behaviour of that image,
  not verified against this repo's actual CI account).
- **Whether the nav-count/N+1/virtualization work items in the original AC
  list are safe to make blind.** Given the budget for this task, and given
  that 19 pages use `DataTable` with only one (`sync-jobs-page`) opting into
  `virtualize`, flipping that flag broadly without running each page's own
  test suite (`pnpm test` is off-limits on this machine per instructions) was
  judged too risky to do speculatively. See issue candidates below.

## 5. Issue candidates (not filed — listed per instructions)

1. **Two authenticated routes crash under a network-stub / degraded-response
   condition.** `/` (analytics landing page) and `/settings` both throw
   `Cannot read properties of undefined (reading 'length')` when a data
   dependency returns a shape other than the expected populated array —
   caught live by this task's smoke-check, reproducible with
   `scripts/lighthouse/smoke-check.mjs`. Every other page tried (`/orders`,
   `/products`, `/connections`, `/customers`, `/listings`, `/shipments`)
   degrades gracefully. Worth a defensive-coding pass on those two
   specifically, and worth asking whether more pages share the gap.
2. **Consolidate the three unconditional prefetches and the five nav-count
   probes** (`apps/web/src/app/hooks/use-nav-counts.ts`,
   `apps/web/src/app/command-palette-provider.tsx`) into fewer requests —
   confirmed present and unconditional on every one of the three routes
   measured here, exactly as #2840 described, now with an exact endpoint list
   instead of an estimate (§3.5).
3. **Page the connections read** (`useConnectionsQuery` takes no
   pagination) — confirmed unpaginated in this measurement too.
4. **Audit `DataTable` virtualization thresholds across the 18 pages that
   don't use it** (`sync-jobs-page` is the only current adopter) — deferred
   here specifically because flipping it blindly, with per-page test suites
   this task could not run, risked a regression nobody would catch until
   review.
5. **The two API-side N+1 sites** named in #2840
   (`apps/api/src/products/http/products.controller.ts:229-231` and `:355-357`)
   — unreachable from this frontend-only harness (see §4); #2840 already
   suggests #2843 as their home.
