## 0. What this scenario actually tested, and why it differs from #2852's own design

#2852 proposed saturating the `bulk` lane with ~1000 real `bulk-create`
offer-publish children and firing an order + an invoice into `realtime` /
`fiscal` while it drained. That design is not reachable on this worktree:

- **#2846** (the Allegro upstream stub the bulk children need as a
  destination) and **#2849** (multi-variant seed data, the other route to
  ~1000 children) do not exist here.
- `bootstrap.sh` deliberately ships both Allegro connections with
  `OfferManager` **disabled** ("Adding OfferManager would arm
  `marketplace.offers.sync` ... turning a clean 404 into a retryable
  `CapabilityNotEnabledException`") — so even a raw enqueue against
  `marketplace.offer.create` would fail the connection's capability gate
  before doing any real work.
- **#2850** (the metrics exporter) does not exist — no
  `ol_lane_slots_in_use`, no `ol_event_loop_lag_seconds`, no
  `ol_claim_loop_ticks_total`, no `degraded_mode_entries` beyond the log-grep
  `post_guard_limiter_degraded` already provides.
- **#2851** (the compose overlay that lets `lab-worker` scale) does not
  exist — `docker-compose.lab.yml`'s worker service pins a fixed
  `container_name: lab-worker`, and `docker compose up --scale worker=3`
  refuses to scale a service with a fixed container name.

The substitute built here (`perf/openlinker-throughput/scenarios/f7-lane-starvation.sh`,
new) keeps the property under test — **does the `bulk` lane's own slot
accounting delay a `realtime`/`fiscal` job beyond its own lane's
availability** — while using only what is real and already provisioned on
this stand:

- **The aggressor** is 600 real `master.product.syncFromSweep` /
  `master.inventory.syncFromSweep` jobs (both registered `bulk`,
  `handler-registration.service.ts`) against the real `perf-prestashop`
  connection's six catalogue products (ids 20-25). Each one is a genuine
  PrestaShop webservice round trip through `MasterProductSyncService` /
  `MasterInventorySyncService` — production code, not a synthetic sleep.
- **The realtime probe** is `master.product.syncByExternalId` — the *same*
  handler class, same connection, registered `realtime` instead of `bulk`.
  This makes the lane the only variable between aggressor and probe, which
  is exactly what ADR-050 decision 2 makes a claim about — and it means the
  probe shares the aggressor's connection scope, so it is **not** protected
  by cross-connection isolation; if it is slow, the lane's own per-connection
  slot accounting cannot be the reason (see §3).
- **The fiscal probe** is `invoicing.issue` with a deliberately-invalid
  payload. `InvoicingIssueHandler` F5-validates before doing anything else
  and returns `{outcome:'business_failure'}` on the first bad field — no
  invoicing connection needed, no external call, no retry. What is measured
  is purely claim latency.
- **The queued-depth-vs-claim-latency test** (#2852's "Channel 2" — the
  missing `(status, jobType, nextRunAt)` index) is run as an isolated SQL
  experiment against the real `sync_jobs` table, runner disabled, wrapped in
  `BEGIN … ROLLBACK` so nothing persists.
- **The 3-replica arm is not run** (blocked by the fixed container name /
  missing #2851, above) and is reported as such, not silently skipped.

Every one of these substitutions is recorded in the script's own header
comment, alongside two real bugs found and fixed while building it (see §6).

## 2. Channel 2 — queued depth vs. claim latency — **measured**

`EXPLAIN (ANALYZE, BUFFERS)` on `claimDueJobs`'s exact claim query
(`sync-job.repository.ts:155-183`), reproduced byte-for-byte, against 0 / 1
000 / 10 000 synthetic `queued` `bulk`-lane rows ahead of one `realtime` and
one `fiscal` candidate, each inside its own rolled-back transaction:

| Depth | Lane | Execution time | Planning time |
|---|---|---|---|
| 0 | realtime | 0.044 ms | 0.683 ms |
| 0 | fiscal | 0.052 ms | 0.656 ms |
| 1 000 | realtime | 0.171 ms | 0.594 ms |
| 1 000 | fiscal | 0.253 ms | 0.717 ms |
| 10 000 | realtime | 1.409 ms | 0.668 ms |
| 10 000 | fiscal | 1.838 ms | 0.624 ms |

**Execution time grows with depth — roughly 32× (realtime) and 35× (fiscal)
from 0 to 10 000 — while planning time stays flat (~0.6-0.7 ms) throughout.**
That shape is exactly what a missing `(status, jobType, nextRunAt)` covering
index predicts: the planner still uses `(status, nextRunAt)` and has to
walk/heap-fetch past every queued `bulk` row with a lower `nextRunAt` before
it finds one matching the requested `jobType`s.

**But the absolute magnitude at these depths is not operationally
significant** — even at 10 000 queued rows, the claim itself costs under 2
ms. This channel is real and measurably present, but on this stand, at these
depths, it is not what explains the slowdown reported in §3. **Not
established**: whether adding the covering index changes this number — this
run measured only the current (indexless) schema, never a counterfactual
with the index added.

## 3. The live-load comparison, 1 replica — **measured**

600-job aggressor, drained over **1 032 s** (10:46:01–11:03:13 UTC) —
**≈0.58 jobs/s effective aggregate throughput**, i.e. **≈13.7 s per job at
the connection's own 8-slot `bulk` per-scope cap** — considerably slower
than the architecture doc's ~2-5 s/job design estimate for this job family,
attributable to a contended workstation (this run shared the host with the
prior F2/F3/F5/F9 scenarios' leftover load and 122 763 pre-existing
`sync_jobs` rows), not a code discrepancy.

### Bulk lane occupancy — **measured**

`SELECT COUNT(*) FROM sync_jobs WHERE connectionId=… AND status='running' AND
jobType=ANY(bulk types)`, sampled at ~1 Hz throughout the loaded window (the
`#2841`/`#2852`-documented fallback for lane occupancy, valid at 1 replica):

| Occupancy | Samples | Fraction |
|---|---|---|
| Exactly at per-scope cap (8) | 634 / 954 | 66.4% |
| Within 1 of per-scope cap (7 or 8) | 921 / 954 | **96.5%** |

The AC asks for "at cap for ≥95% of samples." Read literally (exactly 8),
this run is at 66.4% and would be a hard abort. The 96.5% figure is offered
as context, not a substitute pass: for ~35% of samples the lane held 7
concurrent jobs rather than 8, which is the natural boundary effect of a
per-second sampler watching a queue drain right at its cap — one slot
briefly empties between a job finishing and the next being claimed. The
queued backlog stood in the hundreds for the entire window (never ran dry),
so the gap is a sampling/scheduling artifact, not an undersupply of work.
**Stated plainly: this run's occupancy evidence is short of the AC's
literal 95% bar**, and — the one honest caveat that matters most here —
**this aggressor, using this stand's only real `ProductMaster`/
`InventoryMaster` connection, can never reach the lane's TOTAL cap (12),
only its per-scope cap (8)**. A second real bulk-capable connection would be
needed for that; none exists here without inventing state.

### Realtime probe (n=12 each arm) — **measured**

| | Control (paced trickle) | Loaded (saturated bulk) |
|---|---|---|
| Claim/queue-wait ms (median) | 777 | 392 |
| Claim/queue-wait ms (p95) | 1 682 | 1 226 |
| **Total job duration ms (median)** | **3 272** | **18 094** |
| Total job duration ms (p95) | 5 089 | 27 127 |

### Fiscal probe (n=12 each arm) — **measured**

| | Control | Loaded |
|---|---|---|
| Claim/queue-wait ms (median) | 788 | 380 |
| Claim/queue-wait ms (p95) | 1 670 | 1 219 |
| Total job duration ms (median) | 650 | 516 |
| Total job duration ms (p95) | 1 067 | 977 |

**The two probes tell two different, and jointly conclusive, stories.**

- **Claim latency — the thing ADR-050's slot accounting actually
  governs — shows no starvation signal on either probe.** If anything the
  loaded arm's median claim latency is *lower* than control's for both
  probes. Both arms' claim-latency numbers sit in the same 0-1.7 s band,
  which is the runner's own `POLL_INTERVAL_MS = 1000` ms claim-loop cadence
  (`sync-job.runner.ts:49`) plus this scenario's own ~1 s poller resolution
  (see §6) — i.e. **the measured "signal" is dominated by measurement
  granularity, not by lane contention.** A real, sub-second difference
  between arms cannot be resolved by this instrument. What CAN be said: no
  multi-second, lane-shaped delay was observed on either probe while the
  bulk lane held 6-8 concurrent real jobs for 17 minutes straight.
- **Total job duration tells a completely different story for the realtime
  probe, and the difference between the two probes is the point.** The
  realtime probe's own execution ballooned **5.5×** under load (median 3.3 s
  → 18.1 s) while the fiscal probe's execution was essentially **unchanged**
  (650 ms → 516 ms — if anything faster). The realtime probe is a real
  PrestaShop webservice round trip through the SAME connection the 600-job
  aggressor is hammering; the fiscal probe validates its payload and returns
  before touching any adapter, connection, or external call at all. The
  fiscal probe's flat total time is exactly the control this scenario needs:
  it proves the slowdown is not an artifact of "something is generally
  slow right now" (CPU, scheduler, GC) — it is **specific to sharing one
  destination's webservice/DB capacity with the aggressor**, a form of
  contention ADR-050's lane model was never designed to isolate (lane
  accounting caps how many *worker slots* run per lane; it says nothing
  about a shared downstream destination's own capacity). This scenario's own
  design (§0, "the probe is not protected by cross-connection isolation")
  predicted exactly this outcome in advance.

## 4. Control-arm bias check — **measured**

Both arms fired the same 12+12 probes at the same 15 s cadence; the control
arm additionally ran a paced trickle (one bulk job every 3 s) specifically
so the runner's claim loop kept spinning rather than sleeping a full
`POLL_INTERVAL_MS` on every idle tick (#2852's own "the idle control is
biased toward the wrong answer"). The claim-latency numbers in §3 (0-1.7 s
band, both arms) are consistent with that intent — neither arm shows the
"up to 1 s of pure idle-sleep bias" pattern a fully-idle control would
carry. **Not established**: a direct `ol_claim_loop_ticks_total` count per
arm — #2850 (the metrics exporter) does not exist, so this is inferred from
the claim-latency distribution rather than measured directly.

## 5. What the report answers, in one sentence each

- **ADR-050 decision 2's claim** ("per-lane concurrency caps, never strict
  priority — every lane can always pull") — **holds, on the one axis this
  run could measure (claim latency)**: a `realtime` and a `fiscal` probe
  were both claimed within roughly the runner's own 1-second poll cadence
  regardless of whether the `bulk` lane held 0 or 6-8 concurrent real jobs.
- **Slots or the loop?** Neither, on the evidence gathered: claim latency
  did not visibly move between arms, so this run found no sign of the
  shared-event-loop starvation channel (#2852's "Channel 1") at the load
  level exercised here — **but see §6**, this run also could not measure
  event-loop lag directly (no #2850), so absence of a signal in claim
  latency is not proof the loop was never blocked, only that if it was,
  the effect was too small or too brief for this instrument to catch.
- **A third channel this scenario's own design surfaced, unprompted**: a
  probe sharing its destination connection with the aggressor pays for that
  destination's own contention in its EXECUTION time (5.5×), even though its
  CLAIM time is unaffected. This is not a lane-isolation failure — it is a
  fact about shared destination capacity that no lane model addresses, and
  it is exactly why ADR-050's own operator-facing framing ("does my
  customer's order wait behind it") needs a second, connection-scoped
  answer alongside the lane-scoped one this ADR provides.

## 6. What fought this run, and two bugs found and fixed

1. **`enqueue_perf_job` (`lib.sh`) silently no-ops its own maxAttempts cap.**
   `EnqueueSyncJobResponseDto` returns `jobId` (a Redis stream entry id, e.g.
   `"1788690321451-0"`), not `id` — the function reads `.id`, gets nothing,
   and every single call in this run's first attempt logged `"response
   carried no id"`. This scenario routes around it (tracks its own
   `idempotencyKey` and resolves the real `sync_jobs` row by that unique
   column instead, applying `maxAttempts` in one bulk `UPDATE … LIKE
   'f7:%'` before each drain) rather than patching the shared library under
   this task's time budget. **Filed as a candidate issue** — every future
   scenario reaching OpenLinker through `POST /v1/sync/jobs` inherits this
   gap until `lib.sh` itself is fixed.
2. **`sync_jobs.lockedAt` is cleared to `NULL` on every terminal
   transition**, so "queue wait = lockedAt − createdAt", read back after the
   fact, is `NA` for every completed job — discovered when the first full
   run of this analysis reported `n=0`/`NA` everywhere. Fixed with a live
   ~1 Hz poller that records the first tick a probe's row is observed to
   have left `queued`, run for the whole live-load phase.
3. **A `while read` loop piping a CSV into a body that also calls
   `pg_sql` (→ `docker exec -i`) silently processes exactly one row** — the
   inner `docker exec -i` competes with the loop's `read` for the same
   piped stdin and drains the rest of the file out from under it. Fixed by
   reading the CSV on a dedicated file descriptor (`3< <(tail …)`, `read …
   <&3`) instead of the loop's own stdin.
4. **A ~2-hour (exactly 7 200 000 ms) artifact in every early queue-wait
   number** — `date -d` on a bare Postgres `to_char(...)` string (no
   timezone marker) is interpreted in the HOST's local zone
   (`Europe/Warsaw`, CEST, +2h that week), not UTC, even though the
   `postgres` session itself is UTC. Fixed by appending `" UTC"` to every
   Postgres-sourced timestamp string before parsing.
5. **A `trap ... EXIT` set after `guard_stand_exclusive`'s own `trap
   release_stand_exclusive EXIT` replaced it** (bash's EXIT trap is a single
   slot, not a stack), leaving the stand locked for the full TTL after any
   `die`. Fixed by combining both cleanups into one trap function,
   `f7_on_exit`.

None of these were pre-existing scenario files' bugs (`f2`/`f3`/`f5` were
untouched); all were found building and running this new scenario, and (1)
strongly suggests no prior scenario had exercised `enqueue_perf_job` at
scale against a live worker before this run.

## 7. What this did not establish

- **3-replica arm**: not run. Blocked by `docker-compose.lab.yml`'s fixed
  `container_name: lab-worker` and the absent #2851 compose overlay. ADR-050's
  own documented limitation (#2302, "the caps bound one worker PROCESS, not
  the deployment") remains a stated caveat, not a measured number, on this
  worktree.
- **Event-loop lag (Channel 1) directly**: not measured. #2850 does not
  exist; `ol_event_loop_lag_seconds` was never sampled. This run's finding
  ("no starvation signal in claim latency") is consistent with, but does not
  positively rule out, a blocked loop too brief for the ~1 s poller used
  here to see.
- **Lane TOTAL cap saturation**: only the `bulk` lane's PER-SCOPE cap (8 of
  12) was reachable with this stand's single real bulk-capable connection.
  Whether a second connection saturating the lane's remaining 4 slots would
  change the realtime/fiscal probe outcome is untested.
- **The literal 95%-of-samples "at cap" bar**: this run measured 66.4%
  exactly-at-cap / 96.5% within one slot of cap. Read literally against the
  AC, this is a partial miss; read against the intent (a lane genuinely
  under sustained pressure, never idle, backlog never dry), it was met.
  Both readings are reported; neither is picked for the reader.
- **Whether the missing `(status, jobType, nextRunAt)` index would change
  anything**: only the indexless schema was measured (§2). No counterfactual
  run with the index added was attempted.
- **A burst of realtime work** (#2852's own scale-honesty note): 12 probes
  spread across 3 minutes is a distribution, not a burst. This run did not
  attempt to fire many realtime/fiscal jobs *simultaneously* against a
  saturated bulk lane; it fired them spaced 15 s apart. A true burst case
  remains unmeasured.
- **`ol_claim_loop_ticks_total` per arm**: inferred from the claim-latency
  distribution's shape, never directly counted (#2850 absent).

## Issue candidates

- `enqueue_perf_job` (`perf/openlinker-throughput/lib.sh`) reads the wrong
  field from `POST /v1/sync/jobs`'s response (`.id` vs. the actual `jobId`)
  and its maxAttempts cap has therefore never applied to a single job
  enqueued through it, on any scenario, until this run's workaround.
- A second real `ProductMaster`/`InventoryMaster`-capable connection on the
  `lab` stand (or #2846/#2849 themselves) would let a future re-run of this
  scenario saturate the `bulk` lane's TOTAL cap rather than only its
  per-scope cap, closing the literal-95%-bar gap in §3/§7 honestly rather
  than by argument.
- #2850 (metrics exporter) remains the single biggest gap in this whole
  campaign's ability to answer "slots or the loop?" with direct evidence
  instead of inference.

## 8.1 The fixed guard was proved able to FAIL before it was believed

A guard that had answered zero on every run of this campaign was not taken on
trust a second time. Against **real Docker** - not the stub `lib-test.sh`
uses - with a throwaway container emitting one degraded-mode line at a known
instant:

| Check | Result |
|---|---|
| Fixed guard, window CONTAINING the line | `DISCARDED … 1 degraded-mode log line(s)` |
| Fixed guard, window BEFORE the line | `ok` - window bounding is real, not match-everything |
| OLD `@epoch` form, same container, same window | **0** |
| Fixed bare-epoch form, same container, same window | **1** |

The last two rows differ only in the `@`. `lib-test.sh` asserts the *arguments*
handed to `docker logs` against a stub, and a stub answers regardless of how
the window is spelled - which is exactly how the original defect survived its
own test suite. Only an end-to-end check against real Docker closes that gap.

| 00:41:26Z – 00:41:31Z (worker boot, §8.3) | **2** |
| **Total observed inside the window** | **≥ 38** |

Every line is the condition F4 (#2851) reports: *"Redis rate limiter
unavailable for connection `c4710417-…` - falling back to per-process in-memory
limiting (degraded, not unthrottled). Redis rate-limiter call
`claimConcurrency` timed out after 1000ms"*. Not Redis down - a call to it
exceeding the limiter's own 1 s budget on a contended host.

Two qualifications, both load-bearing:

- **The 36 is a direct observation, not a guard reading.** The worker container
  was recreated mid-window (§8.3), which reset `docker logs`, so
  `post_guard_limiter_degraded` could only ever see the 2 lines after that
  point - and `verdict.txt` accordingly records *"2 degraded-mode log line(s)
  inside the window"*. The 36 were counted from the live log before the reset.
  **The guard's own number for this window is an undercount, and `≥ 38` is the
  honest total.**
- **Degradation clustered in the CONTROL arm and at worker boot - not at
  saturation.** The heaviest run of lines came while the lane carried only the
  control arm's one-job-every-3-s trickle, and the loaded arm's sustained 7–8
  concurrent jobs produced none. That is the opposite of the intuitive reading
  and is worth stating plainly: on this stand the limiter's 1 s Redis budget is
  breached during connection establishment and early load, not by sustained
  concurrency.

**Consequence for the original report.** Its §3 numbers were gathered under
conditions that reproduce degradation readily, so they must be read - exactly
as F4 reads its own - as **measurements of a possibly-degraded system**.
Whether that particular 2026-09-06 window contained a degraded line remains
unrecoverable; what is now established is that the condition is common here,
not absent.

## 8.3 The run was contaminated mid-window, and nothing in the harness said so

At **00:41:21Z**, 7.5 minutes into a window whose stand lock this run held,
`lab-api` and `lab-worker-1` were **both recreated** by a peer who had just
finished rebuilding images. `guard_stand_exclusive` arbitrates *scenarios*; it
cannot stop `docker compose up -d` typed by hand, which on a shared
multi-worktree checkout is a routine thing to do.

No guard fired. It was noticed only because a `docker logs | grep -c` happened
to be read twice and the count went **down**, 36 → 2. The damage is quantified
rather than asserted, and the lane-occupancy proxy - a `COUNT(*)` of
`sync_jobs` rows in `status='running'` - shows it most clearly:

| Loaded-arm samples | occ=6 | occ=7 | occ=8 | occ=15 | occ=16 |
|---|---|---|---|---|---|
| **Before** 00:41:21Z (n=197) | 0.5% | 23.4% | **76.1%** | - | - |
| **After** 00:41:21Z (n=649) | - | - | 0.5% | 29.3% | **70.3%** |

The per-scope cap is **8**. An occupancy of 15–16 is not merely high, it is
**impossible**: it is the 8 rows the killed container stranded in `running`
forever, plus the 8 the replacement is really executing. Had the restart gone
unnoticed, this run would have published an apparent lane-cap violation - and
plausibly an ADR-050 bug report against code that was behaving correctly.

**Closed, with the failing case proved first.** `post_guard_containers_stable`
(`lib.sh`) records every measured container's `.State.StartedAt` at
`window_start` and re-checks it in the post-guards; any change is a restart or
a recreate, and the window is void. A **missing** baseline discards too - it
means the run cannot answer the question, and "stable" would be the same
confident-but-blind pass the `@epoch` defect taught us to distrust. Verified
against real Docker on the actual incident: a baseline carrying the
pre-incident worker start discards and names
`lab-worker-1(was=…00:33:01Z now=…00:41:21Z)`, while an untouched stand passes.
Covered by 9 new `lib-test.sh` assertions - **125 passing, up from 116**.

One of those assertions exists because the real-Docker check found a bug in the
new guard *on its first run*: `measured_containers` was capturing
`_ensure_worker_containers`' log line into its own return value, so every word
of that line became a "container" to watch. The stubbed tests could not have
caught it, because discovery is already memoised there. Same lesson as the one
this whole re-run is about, one level down.

## 8.4 What reproduced anyway

The probe dataset is **uncontaminated**: all 48 probe jobs across both arms were
enqueued between 00:33:53Z and 00:40:34Z (the last 47 s before the incident),
all succeeded on **attempt 0**, and **none** completed after 00:41:21Z. The
occupancy figures above are split at the incident for the same reason. So the
following stands.

Figures below are computed from the run's own artifacts (`realtime-probes.csv`,
`fiscal-probes.csv`, `probe-claims.csv`, `sync_jobs`). The scenario's own
`analyze_probes` step did not produce its CSVs: the process was killed by
SIGPIPE from the wrapper driving it, after `window_stop` and after the verdict
was written, so nothing measured was lost - but that is a harness-side
annoyance worth naming rather than hiding.

### Claim latency - no starvation signal, as before - **measured**

| | realtime control | realtime loaded | fiscal control | fiscal loaded |
|---|---|---|---|---|
| Claim wait, median | 1 000 ms | 1 000 ms | 1 000 ms | 1 000 ms |
| Claim wait, p95 | 3 000 ms | 2 000 ms | 3 000 ms | 2 000 ms |

n=12 per cell. **Resolution caveat, and it matters more than the numbers**: the
claim-wait instrument is a ~1 Hz poller, so every value is
1-second-quantised and a sub-second difference between arms cannot be resolved
by it at all. The original's "0–1.7 s band" and this "0–3 s at 1 s resolution"
are the same finding taken with the same blunt instrument. What can honestly be
said is what the original said: **no multi-second, lane-shaped delay appeared
on either probe while the bulk lane held 7–8 concurrent real jobs**, and the
loaded arm was not slower to be claimed than the control arm. Neither run
supports a claim finer than "no starvation was visible".

**So: the isolation band survives the degraded limiter being visible.** The
degradation documented in §8.2 did not move claim latency.

### Execution time - the destination-contention finding reproduces - **measured**

| | control median | loaded median | ratio | control p95 | loaded p95 |
|---|---|---|---|---|---|
| **realtime** probe (real PrestaShop round trip) | 3 335 ms | 19 008 ms | **5.70×** | 8 703 ms | 29 033 ms |
| **fiscal** probe (validates payload, no external call) | 436 ms | 560 ms | flat | 939 ms | 996 ms |

Original: realtime 3 272 → 18 094 ms (5.5×), fiscal 650 → 516 ms (flat). **The
reproduction is close on both probes**, and the fiscal probe again does the job
the scenario needs of it: it is the control proving the realtime slowdown is
not "everything is slow right now" but specifically *sharing one destination's
capacity with the aggressor* - contention ADR-050's lane model does not address
and was never designed to.

**Quote the direction, not the sharp multiple.** The degradation of §8.2 fell
in the CONTROL arm and not in the loaded one, so the two arms were not equally
paced: a degraded limiter permits more outbound throughput, which would make
the control arm artificially fast and the ratio correspondingly generous. At
one replica that effect is small (per-process fallback is approximately the
declared limit), so **"roughly 5-6x, agreeing with the original's 5.5x" is
supportable and 5.70x as a sharp figure is not**. The qualitative finding is
unaffected, because the fiscal control inflated by nothing at all.

### Channel 2 (queued depth vs claim latency) - shape reproduces, **the ratio does not** - **measured**

Phase 1 ran at 00:32, before the contamination, runner disabled, each point in
its own rolled-back transaction:

| Depth | Lane | Execution (ms) | Planning (ms) |
|---|---|---|---|
| 0 | realtime | 0.218 | 0.749 |
| 0 | fiscal | 0.259 | 0.633 |
| 1 000 | realtime | 0.366 | 0.600 |
| 1 000 | fiscal | 0.400 | 0.627 |
| 10 000 | realtime | 0.963 | 0.500 |
| 10 000 | fiscal | 1.708 | 0.490 |

Execution grows with depth, planning stays flat, absolute cost still **under
2 ms at 10 000 queued rows** - all three as originally reported. But **the
original's "roughly 32× / 35×" growth figure does not reproduce and should not
be quoted**: the same span here is 4.4× (realtime) and 6.6× (fiscal). That
ratio is dominated by its depth-0 denominator, a sub-0.1 ms measurement on a
contended workstation which moved 5× between runs (0.044 → 0.218 ms), while the
absolute values at depth agree closely (1.409 vs 0.963; 1.838 vs 1.708). **The
reproducible claim is the shape and the magnitude, not the multiple.**

### Occupancy - the literal-95% partial miss REPRODUCES - **measured**

Restricted to the uncontaminated pre-incident portion (n=197): **76.1% exactly
at the per-scope cap of 8**, 99.5% within one slot of it. The original measured
66.4% / 96.5%. So this run sits at cap more often and **still misses the AC's
literal "at cap for ≥95% of samples" bar**. Read against the intent - a lane
genuinely under sustained pressure, backlog never dry - it is met. Both
readings are reported and neither is chosen for the reader, as before. The
original's structural caveat is unchanged and remains the honest cause: with
one real bulk-capable connection this aggressor can only ever reach the lane's
**per-scope** cap (8), never its **total** (12).

## 8.5 Verdict, and what this re-run did NOT establish

**`DISCARDED` - and that is the finding, not a failed run.**
`verdict.txt` records the reason: *degraded-mode log lines inside the window*.
A second, independent condition would also have discarded it had the guard
existed when the window opened: the stand was recreated mid-window (§8.3).
Both are precisely what a post-guard is for. The original run reported neither,
because it could detect neither.

Not established here:

- **A clean, uncontaminated full-window measurement.** Probe and Phase-1 data
  are clean, and occupancy is clean to 00:41:21Z, but no arm of this run covers
  a whole window on an undisturbed stand. A repeat is owed - and is now
  self-certifying, because `post_guard_containers_stable` makes a recurrence
  loud instead of invisible. The stand passed to a peer's F8 run at 00:58:31Z,
  so the repeat was not attempted here.
- **Whether the ORIGINAL 2026-09-06 window was degraded.** Unrecoverable, as F4
  already recorded. This section replaces the claim; it cannot answer the
  original question.
- **A true degraded-line count for the whole window.** The container reset
  destroyed the first 7.5 minutes of log. `≥ 38` is a floor, not a total.
- **Event-loop lag (Channel 1) directly** - #2850 still does not exist, so
  "no starvation signal in claim latency" remains consistent with, but not
  proof against, a loop blocked too briefly for a 1 Hz poller to see.
- **Lane TOTAL cap saturation** - still one real bulk-capable connection on
  this stand.
- **The 3-replica arm** - deliberately out of scope. The occupancy proxy is
  only valid at one replica (slot accounting is per process, ADR-050/#2302), so
  measuring it at N replicas needs #2850's exporter rather than a bigger stand.
  Note the reason recorded in the original §7 has expired: #2969 removed the
  fixed `container_name` that used to block `--scale`, and F4 (#2851) runs the
  multi-replica arm.
- **A realtime BURST against a saturated lane** - probes were 15 s apart, a
  distribution rather than a burst. Unchanged from the original.
