---

## 1. What this scenario measures

Per the issue's own framing: does OpenLinker's post-sale surface (returns,
refunds, cancellation stock-restore, invoice issuance) behave correctly under
**genuine concurrency** — multiple callers racing the same resource, not
sequential retries — and what do the named locks (`return:line:{lineId}`,
`invoice:issue:{orderId}`) and DB-level idempotency constraints
(`UQ_refund_records_order_idempotency`) actually do when raced for real.

Four arms, run against a stand seeded with real ingested Allegro orders (not
hand-crafted DB rows):

- **arm_cancellation** — `marketplace.offer.stockRestore` jobs, including one
  genuinely concurrent double-enqueue for a single order.
- **arm_returns** — a `restock` race (15 concurrent same-line dispose calls)
  against the lock-contention/blocked path, a `scrap` race (15 concurrent
  same-line dispose calls) against the path with **no master boundary** —
  the real double-apply check per the scenario's own header comment — plus a
  pool pass across 18 distinct orders for throughput/error-rate.
- **arm_refunds** — a genuinely-concurrent **same-idempotencyKey** race (15
  callers, one order) directly exercising the AC's own "genuinely concurrent
  same-key calls" requirement, plus a pool pass across 19 distinct orders.
- **arm_invoice_lock_diagnostic** — 20 concurrent `POST /invoices` across two
  connections for one order, explicitly labelled diagnostic (no
  `Invoicing`-capable connection exists on this stand).

Concurrency is driven by `drivers/post-sale-flows.mjs`: `race` mode issues
every request inside one synchronous loop before any is awaited
(`Promise.all`), so "concurrent" means every request was in flight before any
prior one returned — not staggered, not sequential-with-retry.

## 3. Results

### 3.1 arm_cancellation — concurrent stock-restore

22/22 jobs `succeeded`, 0 dead, error rate 0%. Included a genuinely
concurrent double-enqueue (two distinct idempotency keys, `dup-a`/`dup-b`)
for `ol_order_f61063b44a8e42bd9607b51d69b6c420`. Both jobs executed and both
reported:

```
outcome=skipped-no-restorer released=0 alreadyTerminal=0 offersRestored=0
```

**No double-apply observed — but see § 4 for why this arm cannot certify the
thing the issue actually asks about.** The Allegro connection on this stand
declares no `OfferStockRestorer` capability (Allegro restores its own stock
internally, per the architecture docs), so both concurrent jobs are
structural no-ops. This is the *second* time this exact finding has been
produced on this stand under this exact condition (a discarded earlier run
hit it on a different order, `ol_order_63a927c3bbb348f2b0b2a363af8310ed`,
also two distinct keys, also `skipped-no-restorer` both times) — consistent
across two independent runs, but consistent about a no-op, not about a real
restorer's idempotency guard.

### 3.2 arm_returns

**Restock race** (lock-contention/blocked path, 15 concurrent
`dispose(restock, qty:1)` calls on one line): 1×`201`, 14×`409
ReturnCustodyContendedError` ("Another custody write is in progress for
return line ...; nothing was changed — retry"). p50=122ms, p95=375ms. The
successful call's own response carries `restockBlocked: {reason:
"unresolved-product", ...}` — the line has no sku, so the restock write
itself is refused downstream of the lock, which is expected on synthetic
return lines with no product resolution and orthogonal to what this race is
measuring (lock behaviour, not restock success). **Final line state**:
`quantityReceived: 15`, `quantityRestocked: 0` (blocked), `custodyState:
received` — exactly one write got past the lock, the other 14 were correctly
refused before touching anything.

**Scrap race** (`return:line:{lineId}` lock, **no master boundary** — the
real double-apply check): 15 concurrent `dispose(scrap, qty:1)` calls on one
line, **all 15 succeeded (201)**. The response bodies' running
`quantityScrapped` values, read in completion order, are exactly the
permutation `{1,2,4,6,7,8,9,10,11,12,13,14,3,15,5}` — a scrambled completion
order (expected under genuine concurrency) that nonetheless lands on every
integer 1..15 exactly once. **Final line state**: `quantityScrapped: 15`,
`custodyState: disposed`, `disposition: scrap`. `doubleApplyFinding: "none"`
— 15 successful calls, final count 15, not exceeding `quantityAdvised: 15`.

This is the strongest evidence this run produced for the issue's core
question. Unlike the restock race (serialized by the lock into 1 winner + 14
immediate refusals) and unlike the cancellation arm (no-op'd before touching
anything), the scrap path has **no** master-inventory call to slow it down —
every one of the 15 requests had a real chance to interleave inside the
counter-check-then-write sequence. A missing or broken guard here would show
up as either a final count below 15 (a lost update — two writers reading the
same pre-increment value) or above 15 (an actual over-application past
`quantityAdvised`). Neither happened. The counter landed exactly on the
value 15 concurrent, non-serialized-by-a-slow-downstream-call writers should
produce if and only if the write path is genuinely safe under concurrency
(the per-line `SyncLockPort` lock plus the `SELECT ... FOR UPDATE` the
architecture doc describes for this exact path).

**Pool** (18 distinct orders, concurrency 8): 18/18 ok, error rate 0%,
p50=55ms, p95=77ms.

### 3.3 arm_refunds

**Race** (genuinely-concurrent SAME idempotencyKey, 15 callers, 1 order,
backed by `UQ_refund_records_order_idempotency`): 1×`201`, 14×`409 Conflict`
("A refund with this idempotencyKey already exists for this order").
**`persistedRowsOnOrder: 1`** — read directly from the database after the
race, not inferred from response codes. `doubleApplyFinding: "none"`.

This is a direct, clean answer to the issue's own headline AC ("genuinely
concurrent same-key calls, not sequential retries") for the one flow in this
scenario where that AC is reachable over HTTP with no scope cut: 15 requests
issued before any of them returned, sharing one idempotency key, against one
order — and the database shows exactly one row. The unique constraint did
its job under real concurrent contention, not merely under a sequential
retry that a weaker mechanism could also have survived.

**Pool** (19 distinct orders, concurrency 10): 19/19 ok, error rate 0%,
p50=43ms, p95=64ms.

### 3.4 arm_invoice_lock_diagnostic

Explicitly diagnostic (per the scenario's own note): no `Invoicing`-capable
connection exists on this stand, so this measures the **lock's scope**
(`invoice:issue:{orderId}`, per-order across connections), never a realistic
hold duration under a live provider round-trip. 20 concurrent
`POST /invoices` for one order, split across the PrestaShop and WooCommerce
connection ids: 18 contended, 2 non-contended.

The 18 "contended" responses are not one uniform outcome — reading them
individually shows **two distinct guards both firing correctly**:
- Most (14) answer `409 InvoiceIssueContendedException` — the per-order
  `SyncLockPort` lock (`invoice:issue:{orderId}`) refusing a caller that
  arrived while another held it, explicitly `retryable: true`.
- Three answer `409 OrderAlreadyInvoicedException`, naming the specific
  blocking connection/invoice/status
  (`connection 4c9a936b-..., invoice a700d18f-..., status issuing`) —
  the separate, cross-connection "one originating document per order"
  write-path guard (ADR-041 §3a) firing for a caller on the *other*
  connection once the first connection's row already exists, independent of
  lock timing.
- One is the generic `409 Conflict` ("Invoice issuance already in progress
  for order").

The 2 non-contended responses are both `400 CapabilityNotSupportedException`
("Adapter prestashop.webservice.v1 does not support capability: Invoicing")
— the two calls that happened to land on the PrestaShop connection, which
(correctly) has no `Invoicing` capability at all and is refused before the
lock is even reached.

Net: the lock scope is confirmed per-order-across-connections as designed,
and the cross-connection duplicate-document guard is confirmed to fire
independently of the lock. No document was created (expected — no
`Invoicing` adapter is wired), so this arm cannot say anything about what
happens once a real provider round-trip is in the critical section; it can
only say the two guards it *can* reach on this stand both behaved.

### 3.5 Background ingestion

15 orders ingested via the ordinary poll path concurrently with all four
arms above running against the same connection. No degradation reported;
this only confirms ordinary ingestion did not stall or error out under the
contention the arms created on the same connection.

## 4. What this did not establish

- **Cancellation-arm double-apply, for a REAL stock-restorer.** The only
  connection this scenario can mutate (Allegro) declares no
  `OfferStockRestorer`, so both concurrent stock-restore attempts — in this
  run and in the earlier discarded one — were structural no-ops
  (`skipped-no-restorer`). Two consistent results across two runs rule out a
  crash or corruption from concurrent no-ops; they say nothing about whether
  a connection that *does* implement `OfferStockRestorer` dedupes correctly
  under the same genuine-concurrency shape. That would need a stand carrying
  a connection with that capability, which this stand does not have.
- **Invoice issuance under a live provider round-trip.** The diagnostic arm
  confirms lock scope and the cross-connection guard, but with no
  `Invoicing`-capable connection wired, no call ever reaches the part of
  `issueLocked()` that actually holds the lock across a slow outbound call —
  which is the realistic contention window the lock exists to cover. This
  stand cannot produce that evidence without adding an `Invoicing`-capable
  connection (e.g. a fake/stub adapter).
- **Restock success under genuine concurrency** — the restock race's single
  successful write was itself refused downstream (`unresolved-product`, no
  sku on the synthetic line), so this run has no evidence of what happens
  when 15 concurrent restock calls race AND the winning write is one the
  master would actually accept. The lock behaviour (1 winner, 14 immediate
  409s) is confirmed regardless of that downstream refusal.
- **Sustained throughput** — every pool pass here is a small, short burst
  (18-19 requests) meant to sanity-check the happy path alongside the races,
  not a throughput or error-rate claim under load; that is out of scope for
  this issue.

## 5. Harness bugs found and fixed this session (scope note, not a product finding)

Two attempts on this stand this session died on **harness** bugs before
producing a verdict — recorded here for the record, not as OpenLinker
defects:

1. A missing `/v1` URI-version prefix on every bare-path HTTP call the
   scenario itself makes (`ol_api()` calls in `lib.sh` and the
   NDJSON `path` fields fed to the Node concurrency driver both — the driver
   builds `${baseUrl}${path}` verbatim with zero prefixing of its own).
   `apps/api/src/main.ts` enables URI versioning with a default version, so
   every route lives under `/v1` except the explicitly `VERSION_NEUTRAL`
   ones; `lib.sh`'s `ol_api()` never added it, and only `ol_login()`
   (hardcoded `/v1/auth/login`) already had it. Every bare-path call site in
   the scenario was grepped and fixed in one pass (15 sites: 8 `ol_api()`
   calls, 6 driver-fed NDJSON `path` fields, 1 smoke-test probe path) —
   committed as `cfb1c4e40e2f49a4ec02c41d78d21738434b43d5`. This run's own
   `guard_build` line confirms the running image matched that commit, and no
   fourth instance of the bug surfaced.
2. Two `marketplace.order.sync` jobs left `queued` on the Allegro connection
   by an earlier, incomplete run (deferred by an ADR-050 lane-cap re-queue,
   `attempts: 0` — a benign, no-penalty deferral, not a failure) blocked
   `guard_queue_empty` on the next attempt. Drained by briefly re-enabling
   the worker runner and letting the runner process them for real (both
   completed `succeeded`/`outcome: ok`, 0 attempts consumed) rather than
   hand-mutating their status — preserving real job history instead of
   fabricating it.
