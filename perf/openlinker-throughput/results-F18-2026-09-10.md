## 1. What this measures

- **arm A** - three real triggers fired concurrently (an Allegro orders poll, a
  PrestaShop-source order push, a burst of Erli category resolves), each
  channel's own completion time reported.
- **arm B** - whether an Allegro resolve degrades while Erli's borrowed-catalogue
  burst runs on the SAME peer credentials (#2210).
- **arm C** - the Erli seller-frozen stock skip on `updateOfferQuantity`,
  asserted in both directions: the not-frozen write must reach the marketplace,
  the frozen write must not.

## 2. Results

| arm | result |
|---|---|
| A three channels concurrent | Allegro poll **1 315 ms**, PrestaShop webservice read **44 ms**, Erli resolve burst (5) **57 ms** |
| B peer contention | Allegro solo **40 ms**, under a concurrent Erli burst of 10 **55 ms** (burst itself 60 ms) |
| C frozen-stock skip | stub quantity writes `before=0 -> afterNotFrozen=1 -> afterFrozen=1` |

## 3. Arm B found nothing, and that is a result

Allegro's own resolve latency did not measurably degrade under a concurrent
Erli borrowed-catalogue burst of ten. 40 ms against 55 ms is within this
stand's noise for a call of that size.

Stated as a finding rather than omitted, per the issue's own framing: no
cross-connection cost was observed **at this burst size**. That is not the same
claim as "there is no cross-connection cost", and a burst sized to the peer's
real rate-limit budget is the measurement that would settle it.

## 4. The retracted finding, and the three faults behind it

Arm C reported `before=0 afterNotFrozen=0 afterFrozen=0` across repeated runs:
the offer mapping existed, both jobs reported `succeeded|ok`, and the Erli stub
recorded zero requests. That was published as a stock write reporting success
without writing. **It was wrong.** Three harness faults stacked:

1. **Arm C's own `trap ... EXIT` silently replaced the scenario's.** Bash keeps
   one handler per signal, so `f18_cleanup` was discarded wholesale. The
   frozen-stock cache key it deletes carries a **26-hour TTL**, so the flag arm
   C wrote on its FIRST run was still set on every run after it - and every
   later "not frozen" write was correctly skipped as frozen. The same line is
   why `release_stand_exclusive` never ran and a stale stand lock blocked the
   next scenario.
2. **The Erli TLS terminator was answering 502 to everything.** nginx resolves a
   `proxy_pass` upstream once at startup and caches it without a `resolver`
   directive; the backing stub had been recreated with a new address.
3. **Arm C's mapping insert was not idempotent**, so the second run died on a
   duplicate-key violation before reaching the measurement.

All three are fixed, and each produced a guard rather than a note:
`guard_connection_endpoints` (probing from inside the worker, through node,
because only node reads `NODE_EXTRA_CA_CERTS`), one EXIT handler, and
`ON CONFLICT DO NOTHING`.

**What arm C actually shows now** is the documented behaviour working: the
not-frozen write reaches the marketplace, the frozen write does not, and the
adapter warn-logs the skip every time. The architecture's own note stands
unchanged - the skip surfaces **no operator-facing warning** outside the log -
and that gap is real, but it is a known follow-up, not something this run found.

## 5. Limits

- Stubbed Erli and Allegro. Neither vendor's real rate limit is exercised.
- Arm A reports three concurrent completion times, NOT an ingestion-throughput
  comparison; a full three-channel F11 extension is named follow-up work.
- Arm B's burst size is 10. A negative result at one burst size bounds nothing
  above it.
- `guard_build` was absent before today; this run carries `5897057a`.
