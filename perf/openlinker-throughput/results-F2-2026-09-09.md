### The leading candidate was tested, and REFUTED

Hop F is the one the campaign had already attributed to a mechanism:
`JobIntakeConsumer`'s `xReadGroup` blocks for `BLOCK_MS = 5000`, and a command
queued behind an in-flight block pays the residual - which is why hop F sat at
~5 s in both prior runs. **`BLOCK_MS = 5000` is UNCHANGED in the tree under
test** (`apps/worker/src/sync/job-intake.consumer.ts:46`), so this report does
not claim that mechanism was removed.

The candidate this report originally named was the merged lane work: before
#2609, `fan-out` was `total 1 / perScope 1` **and**
`inventory.propagateToMarketplaces` was enqueued under an all-zero placeholder
connection id, so every stock propagation in the installation shared one scope
with a per-scope cap of one - which is precisely hop F's path. This run's
worker reports `fan-out=8/4`.

**That candidate was tested by a controlled A/B and does not survive it.**

The scenario was re-run unchanged with `OL_LANE_FANOUT_CAP=1` and
`OL_LANE_FANOUT_SCOPE_CAP=1` - the pre-#2609 values - with the applied caps
read back out of the worker's own startup line before the arm began
(`fan-out=1/1`), the F8 discipline, because a cap that silently did not apply
produces a clean curve of the same cap measured twice.

| | `fan-out=8/4` (`run1788936630`) | `fan-out=1/1` (`run1788939164`) | delta |
|---|---|---|---|
| hop D: OL commit -> `inventory_items` | 989.2 ms | 687.8 ms | -30% |
| **hop F: propagate -> child enqueued** | **981.7 ms** | **987.7 ms** | **+0.6%** |
| TOTAL: write -> child enqueued | 2 210.1 ms | 1 930.0 ms | -13% |

Both arms `status=VALID`, n=24 each, all eight guards `ok`.

**Hop F is flat across a 4x change in the per-scope cap.** Reverting the cap
did not restore the ~5 s, so #2609's cap raise is **not** the cause of hop F's
drop. Recorded as withdrawn rather than left standing as a plausible story.

**The experiment's design is one-sided, and saying so is part of the result.**
F2 is a *serial* scenario - one stock write, one propagate job at a time - so
a per-scope cap of 1 versus 4 has no queue to act on. The A/B could therefore
refute the hypothesis but could never have confirmed it. The refutation is
still informative: if the old ~5 s had been cap-induced queueing, running at
cap 1 would have reproduced it, and it did not.

**The surviving candidate is environmental, and it is shared with F1.** F1's
four prior arms were all discarded for 34-52 Redis-limiter degradation entries
per window and this run's show zero; a limiter degrades when Redis is
unavailable *to it*. The stand shares one developer workstation with two other
OpenLinker docker stacks, with no CPU pinning - a caveat the harness's own
generated report prints against every figure. The earlier runs were taken
while several agents and image builds contended for that host; both of this
run's arms at `load_average` 1.4-3.0.

That is a correlation across two independent flows, not an isolation. The
experiment that would settle it is to re-run this scenario **while deliberately
loading the host** and see whether hop F returns to ~5 s. It was not run:
saturating this host is what OOM-killed the previous measurement session and
its `lab-mysql` earlier the same night, and the owner asked for the
re-measurement to avoid exactly that. Named here as the next step rather than
attempted.

## The run was structurally unmeasurable until two stale-state blockers were cleared

This is a harness finding, not an incident: **F2 is not idempotent across runs
without an outbox reset.** Two independent blockers, both left by the crashed
campaign of 2026-09-09T00:2xZ, and the first attempt of this run hit both.

**1. Stale `pending` rows hold the dedup key.** `dedup_key` carries a UNIQUE
index and `OutboxRepository::enqueueEvent` derives it from
`(provider, connectionId, eventType, objectType, externalId)` - no timestamp,
no quantity - with `INSERT IGNORE`. The key is released when the drainer
*claims* a row, not when it is delivered, which the table shows directly:
`delivered` rows carry `dedup_key = NULL`, `pending` rows do not. 110 `pending`
`stock.changed` rows from 2026-09-07 therefore swallowed every write this run
made, and the first attempt logged `NO OUTBOX ROW` on every product.

The scenario's own defence - drain after every single write, so each cycle
claims its own row - works only from a clean slate. It cannot rescue the first
write for a product whose key a two-day-old row already holds.

**2. A `pending` backlog starves the fresh row.** 8 535 `pending`
`order.created` rows sat ahead of the new row in drain order, which is oldest
first. The second attempt created its outbox rows correctly and then timed out
waiting for `delivered_at`, because the drain was still working through the
backlog. Those rows were undeliverable on this connection by construction -
OL answered every one of them
`deadlettered: ungated: order requires OrderSource`.

Both sets were backed up (`outbox-stock-pending-backup.tsv`,
`outbox-order-pending-backup.tsv`) and deleted, restricted to
`status = 'pending'`; `delivered` rows were left untouched. The stand was not
reseeded and no catalogue row was touched.

## Two artefacts of the instrument, recorded rather than passed over

**The scenario's own generated report now carries a false sentence.** It
writes a hardcoded section headed *"`drain_http_status` reads 500 on every
cycle"*, which was true of earlier runs and is false of this one - the data in
the same file records 200 on all 24 cycles. That prose is a fixed `printf` in
the scenario, not derived from the run, so it cannot notice that the condition
it explains has gone. The generated file is therefore **not** the artefact
committed for this flow; this report is. Filed as a follow-up rather than
edited mid-run.

**Hop B is uninterpretable as printed.** The generated table gives hop B
(outbox created -> outbox delivered) a p50 of **-294 ms**, minimum -804 ms.
The negative sign is not a measurement: `outbox_created_local` is PrestaShop's
**local** clock (the CSV shows `2026-09-09 08:51:33`) while
`outbox_delivered_utc` is UTC (`06:51:33`) - a two-hour offset subtracted in
the wrong direction. No figure in this report depends on hop B, and the
scenario's headline already excludes that hop by design for a different
reason, so this is a reporting defect and not a corrupted result.

## Supporting evidence

Every cycle, all 24: `drain_http = 200`, `inv_job = succeeded/ok`,
`propagate_job = succeeded/ok`, `offer_children = 2`,
`offer_child_status = succeeded`, **no `offer_child_last_error` on any cycle**.

## What this run did not establish

- **Hop t1->t2, the shop's own cron cadence, is EXCLUDED by design.** This
  scenario force-drains after every write. The figures above are OpenLinker's
  own work, not what a deployment on a one-minute shop cron experiences.
- **Why the chain got 4x faster.** Three unattributed changes (hops E and F,
  and the drain status). One named mechanism, not isolated.
- **That the 5 s `BLOCK_MS` residual is gone.** The constant is unchanged; only
  the observed residual moved, and a residual depends on arrival phase.
- **Anything under concurrency.** 24 serial cycles across 6 products.

## Status of the cause

Ran and refuted: #2609's `fan-out` cap raise (A/B above).
Ruled out by inspection: a `BLOCK_MS` change (the constant is unchanged).
Surviving: host contention, correlated across F1 and F2, not isolated.
Not attempted, deliberately: the load-the-host reproduction.
