# eparagony.pl upstream stub

Implements GitHub issue #3043 (F14, epic #2840). A single-process `node:http`
stub serving just enough of the eparagony.pl Documents REST API v3 for
OpenLinker's REAL, unmodified `EparagonyFiscalizationAdapter`
(`@openlinker/integrations-eparagony`) to run against it - so `F14`'s
measurement exercises OpenLinker's own bounded-poll / in-doubt / idempotent
logic, not a reimplementation of it.

## What it serves, and why only this

The real adapter needs two hosts (`apiBaseUrl`, `authBaseUrl`), both of which
this ONE process answers for - the config-shape validator only enforces
`https`, never a specific hostname, so there is no reason to stand up two
containers:

| Method | Path | Behaviour |
|---|---|---|
| `POST` | `/auth/token` | Accepts any client_credentials form body, answers `{access_token, expires_in: 3600}`. |
| `POST` | `/documents` | Requires `Idempotency-Key`. First call for a token: `202` + holds the document. Repeat call under the same token: `409 {errorCode: 118}` - the exact code the real adapter's `createDocument` reads as "our earlier attempt landed, read status instead". |
| `GET` | `/documents/:token/status` | Reports `READY` for `pollsUntilOutcome` reads, then the configured `forceOutcome` (`confirmed` / `error` / `hang`). Unknown token: `404 {errorCode: 92}`. |
| `GET` | `/printers/:id/status` | The connection-tester diagnostic (`printer_get` scope) - always `{status: 'online'}`. |

Everything else answers `404 {errorCode: 100}`.

## Why TLS

`EparagonyHttpClient` (`originOf`) throws on a non-`https:` base URL for
BOTH hosts - this is enforced in the real adapter, not something a lab stub
can route around. This process itself speaks plain HTTP; `docker-
compose.lab.yml` fronts it with an nginx TLS terminator generated by
`stand/lab-tls/generate-certs.sh` (the `wc-tls` precedent, #2854), and its CA
is folded into the same bundle the API/worker containers already trust via
`NODE_EXTRA_CA_CERTS`.

## The three outcomes, and why they are knobs rather than derived

`FiscalRegistrationService`'s whole reason to exist is that a fiscal
registration can end `registered` / `rejected` / `in-doubt`, and #3044 (F14)
needs to produce all three ON DEMAND to measure how the lock and the record
behave under each - a stub that only ever confirms would leave the
`in-doubt` arm (the one operators cannot resolve by retrying) permanently
unmeasured, which is the gap #3044's own acceptance criteria names.

- `forceOutcome: 'confirmed'` (default) - `pollsUntilOutcome` READY reads,
  then `CONFIRMED`.
- `forceOutcome: 'error'` - `pollsUntilOutcome` READY reads, then `ERROR`
  (the real adapter throws this as a terminal, non-retryable rejection -
  its own token is deterministic, so a retry under the same key cannot
  double-register).
- `forceOutcome: 'hang'` - never terminalises. Combined with a low
  `config.statusPollTimeoutMs` on the connection (the adapter clamps it to
  `[5000, 90000]` ms), this reliably produces the real adapter's
  poll-budget-exhausted throw, which core classifies `in-doubt` - never
  `rejected`, since the device may still complete.

The outcome is captured PER DOCUMENT at create time (mirrors invoicing-stub's
"latency is the arm's independent variable and survives a reset" rule) -
`/__stub/reset` clears every held document but leaves `forceOutcome` /
`pollsUntilOutcome` / `latencyMs` alone, so a sweep sets the knob once before
enqueuing an arm's jobs rather than racing the driver against in-flight
documents.

## Control surface

| Method | Path | Behaviour |
|---|---|---|
| `GET` | `/__stub/health` | `{ok: true}` - compose healthcheck target. |
| `GET` | `/__stub/config` | `{gitSha, latencyMs, pollsUntilOutcome, forceOutcome, requestsTotal, tokenRequestsTotal, createCount, confirmedCount, errorCount, documentsHeld}`. |
| `PUT` | `/__stub/config` | Sets `latencyMs` / `pollsUntilOutcome` / `forceOutcome` for every subsequent call. |
| `POST` | `/__stub/reset` | Clears held documents and counters. Knobs survive. |

## What it deliberately does not serve

- `GET /documents/{token}` (the buyer-facing document view) and the
  authority-confirmation-document read - no shipped scenario needs them.
- Every one of the vendor's documented `errorCode`s. The stub models exactly
  the three the real adapter branches on (118 already-exists, 92
  unknown-document-token, and a generic terminal ERROR) - a fourth code
  reaching this stub's default 404 fails loudly rather than measuring an
  error taxonomy nobody asked for.
- A genuinely invalid tax-rate / currency / amount rejection at create time -
  this stub has no concept of a malformed receipt, same "the mock is now the
  model" refusal `stubs/allegro/README.md` states by name.

## Design decisions

Same as `stubs/invoicing/README.md`'s: standalone `node:http`, zero
dependencies, `server.mjs` exports `{server, describeConfig, _resetForTest}`
for `test.mjs` to drive in-process on an ephemeral port.
