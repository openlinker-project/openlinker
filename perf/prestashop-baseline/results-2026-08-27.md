# PrestaShop adapter baseline — measured 2026-08-27

Stack: `ol-demo-fresh` (PrestaShop 8 on Apache/MySQL 8.4, OpenLinker api+worker
in containers on one Docker network). Catalogue seeded to **10 006 products /
30 008 combinations** (`PERFBASE-` prefix) because the demo store held only 6.

Instrument: PrestaShop's **own Apache access log**, read via
`docker logs --since` (the image symlinks `access.log -> /dev/stdout`).
Counted on the shop's side, not by any OpenLinker counter. Loopback
healthcheck traffic and non-`/api/` traffic are filtered out.

## 1. What one sweep costs today — MEASURED

Window: `master.product.syncAll` cold run, 00:28–00:36, 42 child jobs completed.

| Resource | Requests | Per completed product |
|---|---:|---:|
| `GET /api/products/<id>` | 142 | **3.00** |
| `GET /api/configurations` | 68 | 1.62 |
| `GET /api/currencies/<id>` | 66 | 1.57 |
| `GET /api/combinations` | 42 | 1.00 |
| `GET /api/product_options` | 40 | 0.95 |
| `GET /api/product_option_values` | 40 | 0.95 |
| `GET /api/stock_availables` | 21 | 0.50 |
| `GET /api/products` (enumeration) | 4 | one-off per tick |
| **Total** | **425** | **~9.6** |

Throughput: **~50 requests/min**, **~5.3 products/min**, execution
concurrency 2, mean shop-side response time ~2 s per request.

### The three hypotheses, answered

**(1) Triple `GET /api/products/<id>` — CONFIRMED, exactly 3×.**
Of the 58 distinct product ids touched in the window, **every one of the 42
that ran to completion was fetched exactly three times**; the remaining 16
were mid-flight. Not "about three" — three.

```
distinct_ids=58 total_fetches=142 mean=2.45
     16 ids fetched 1x     <- still in flight
     42 ids fetched 3x     <- completed
```

**(2) +2 requests to build the adapter — CONFIRMED, and it is worse than +2.**
`PrestashopShopCurrencyResolver` issues `GET /api/configurations` +
`GET /api/currencies/<id>` on every adapter construction. Measured at
**1.62 + 1.57 = 3.2 requests per product**, i.e. the adapter is built more
than once per child job. This is one-third of the entire request budget spent
re-reading a value (the shop's default currency, `PLN`) that cannot change
between two jobs a second apart.

**(3) The limiter is not the ceiling.**
The connection has no `config.rateLimit` at all. The observed ~50 req/min is
not a throttle — it is round-trip latency (~2 s) times execution concurrency
(2). Nothing is being held back to protect the shop; the shop is simply
answering as fast as it is asked. **The currency is cycle time, not shop
load**, which contradicts the issue's premise that synchronisation "puts
significant load on PrestaShop".

## 2. The bulk floor — MEASURED, and it needs no module

The same data for 100 products, fetched through **stock PrestaShop webservice
features that exist today** (`display=full`, `limit`, `filter[id_product]`):

| Call | Requests | Rows returned | Bytes | Time |
|---|---:|---:|---:|---:|
| `products?display=full&limit=100` | 1 | 100 products | 700 KB | 0.21 s |
| `combinations?filter[id_product]=[...]` | 1 | 300 combinations | 405 KB | 0.13 s |
| `stock_availables?filter[id_product]=[...]` | 1 | 400 stock rows | 228 KB | 0.05 s |
| **Total** | **3** | 100 products, fully hydrated | 1.33 MB | **0.38 s** |

Verified the payload is complete: 100 `<product>` elements, each carrying
`name`, `price`, `ean13`.

**3 requests and 0.38 s replaces ~960 requests and ~19 minutes.**

## 4. What this does and does not settle

Settled by measurement:

* The waste is real and it is the majority of the budget. Two of the three
  product reads are redundant, and the adapter-build pair is redundant on
  every job. Together they are **~54% of all requests**, removable inside the
  adapter with no PrestaShop-side code.
* **Bulk does not require a module.** The webservice already serves 100
  hydrated products in one request. The issue lists "Support batch operations
  where possible" as a module responsibility; the platform already supports
  them and OpenLinker does not use them.
* The store is not being hammered. ~50 req/min is modest. What is expensive is
  the **elapsed time** of a full cycle, and that is a consequence of asking
  one product at a time.

Not settled, and deliberately not guessed:

* A module's ceiling below 3 requests. It cannot be measured without a module,
  and the gap between "3 requests / 0.38 s" and "fewer than 3" is small enough
  that it is unlikely to be the deciding factor.
* Order creation (`POST/DELETE /api/specific_prices` per line) and the publish
  path — separate scenarios, not yet run.
* The store-response-time A/B under load — not yet run.
* Acceptance criteria 5–7 (retry, sync status, native data access) are
  **functionality, not performance**. No stopwatch decides them.

## 5. Caveats on these numbers

* The window measured is a **cold** run and was contaminated part-way by the
  scheduler's own 20-minute tick enqueueing a second sweep. Ratios per product
  are unaffected (they are ratios, and the 3× count is exact); absolute
  throughput may be slightly understated.
* One tick covers 100 products by design (`SWEEP_BUDGET_DEFAULT`), so every
  10 000-product figure in the tables above is **extrapolation**, marked as
  such.
* Repeats (median of runs 2 and 3) are still outstanding.
