# Stage B — the same measurements, after the adapter fix (#2489)

Branch `2489-etap0`, cut from the stage-A baseline. **Not to be merged before
the numbers are read** — merging it destroys what baseline A means.

Same catalogue (10 000 products / 30 000 combinations), same instrument (the
shop's own Apache access log), same method, same repeat counts. The only
difference is the code.

---

## What changed

### B1.1 — the adapter factory stops being rebuilt on every capability resolution

`prestashop-plugin.ts` constructed `new PrestashopAdapterFactory(...)` inside
`createCapabilityAdapter`, i.e. once per resolved capability. The factory's
resolver fields each carry a per-connection cache, and each says in its own
docblock that it is a *"process-singleton"* so that cache survives the adapter
instances the master sweep builds per product. It never was one, so the code
described a lifetime it did not have.

The factory is now built once in the plugin closure. This is safe because it
holds no per-connection state: its constructor takes only connection-independent
collaborators, and the connection is a parameter of `createAdapters`, never a
field.

### B1.2 — `GET /api/products/{id}` is fetched once per adapter instance

`getProduct` (`:187`), `getProductVariants` (`:395`) and `getProductCategories`
(`:699`) each fetched the same resource independently. A per-instance memo now
serves the second and third from the first. The **promise** is cached, not its
value, so two concurrent callers share one request; a rejection is evicted so a
transient failure does not pin an error for the rest of the job.

### B1.3 — `config.currency`: not needed

Planned as a belt to B1.1's braces. B1.1 removed the currency reads entirely
(0 remaining, see below), so it was not applied — a configuration change that
buys nothing is not worth the drift.

### Dropped from the plan, on stage-A evidence

Caching the VAT rate by tax group. Stage A measured **zero** `/api/taxes` and
`/api/tax_rules` requests across six catalogue and inventory sweep runs; they
appear only on the order path. It is not a catalogue cost, so it does not belong
in a change set justified by catalogue measurements.

### The memo collapsed three fetches to two, not to one

Measured: 199 fetches across 100 distinct products, i.e. **1.99 per product**,
where 1.00 was expected.

The reason is a lifetime, not a bug in the memo: an adapter instance lives for
one *capability resolution*, and a child job resolves `ProductMaster` more than
once. Two of the three reads share an instance and hit the memo; the third
lands on a freshly built instance and misses.

**The remaining 0.99 fetches per SKU is the measured size of the next step:**
memoising the adapter bundle itself per connection. That is a real lifetime
change with real consequences (credential rotation, config edits mid-run) and
belongs in its own decision, not smuggled into this one.

## What this cost

Two files, no new dependency, no migration, no schema change, no ADR-level
contract change:

* `libs/integrations/prestashop/src/prestashop-plugin.ts` — the factory moves
  out of a per-call scope into the plugin closure.
* `libs/integrations/prestashop/src/infrastructure/adapters/prestashop-product-master.adapter.ts`
  — one memo field and one private method; three call sites now go through it.

## Reading this against the module proposal

The two rows that matter: the catalogue sweep dropped **37.7%** and the
inventory sweep **66.7%**, from two localised changes in one adapter, with no
PrestaShop-side code at all.

The measured bulk floor — 3 requests and 0.38 s for 100 fully hydrated products,
taken through the stock PrestaShop webservice — is another two orders of
magnitude below baseline B, and the adapter method that reads it is already
written.

None of this addresses the module proposal's functional half (returns, partial
cancellation, cash on delivery, buyer tax id, whole-order discounts, bundles,
one-way multilingual) or acceptance criteria 5–7 (retry, sync status, native
data access). Those are product decisions; no stopwatch settles them.
