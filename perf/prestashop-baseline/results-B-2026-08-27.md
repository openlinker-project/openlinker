# Stage B — the same measurements, after the adapter fix (#2489)

Branch `2489-etap0`, cut from the stage-A baseline. **Not to be merged before
the numbers are read** — merging it destroys what baseline A means.

Same catalogue (10 000 products / 30 000 combinations), same instrument (the
shop's own Apache access log), same method, same repeat counts. The only
difference is the code.

---

## What changed

### B1.1 — the adapter factory stops being rebuilt on every capability resolution

`prestashop-plugin.ts` constructed `new PrestashopAdapterFactory(...)` inside
`createCapabilityAdapter`, i.e. once per resolved capability. The factory's
resolver fields each carry a per-connection cache, and each says in its own
docblock that it is a *"process-singleton"* so that cache survives the adapter
instances the master sweep builds per product. It never was one, so the code
described a lifetime it did not have.

The factory is now built once in the plugin closure. This is safe because it
holds no per-connection state: its constructor takes only connection-independent
collaborators, and the connection is a parameter of `createAdapters`, never a
field.

### B1.2 — `GET /api/products/{id}` is fetched once per adapter instance

`getProduct` (`:187`), `getProductVariants` (`:395`) and `getProductCategories`
(`:699`) each fetched the same resource independently. A per-instance memo now
serves the second and third from the first. The **promise** is cached, not its
value, so two concurrent callers share one request; a rejection is evicted so a
transient failure does not pin an error for the rest of the job.

### B1.3 — `config.currency`: not needed

Planned as a belt to B1.1's braces. B1.1 removed the currency reads entirely
(0 remaining, see below), so it was not applied — a configuration change that
buys nothing is not worth the drift.

### Dropped from the plan, on stage-A evidence

Caching the VAT rate by tax group. Stage A measured **zero** `/api/taxes` and
`/api/tax_rules` requests across six catalogue and inventory sweep runs; they
appear only on the order path. It is not a catalogue cost, so it does not belong
in a change set justified by catalogue measurements.

### The memo collapsed three fetches to two, not to one

Measured: 199 fetches across 100 distinct products, i.e. **1.99 per product**,
where 1.00 was expected.

The reason is a lifetime, not a bug in the memo: an adapter instance lives for
one *capability resolution*, and a child job resolves `ProductMaster` more than
once. Two of the three reads share an instance and hit the memo; the third
lands on a freshly built instance and misses.

**The remaining 0.99 fetches per SKU is the measured size of the next step:**
memoising the adapter bundle itself per connection. That is a real lifetime
change with real consequences (credential rotation, config edits mid-run) and
belongs in its own decision, not smuggled into this one.

# B1.4 — the third product fetch, found and removed

Baseline B left 1.99 product fetches per SKU where 1.00 was expected, and the
report above guessed the cause was the adapter bundle's lifetime. **That guess
was wrong**, and chasing it in the log rather than trusting it is what found the
real one.

`getProductCategories` — the suspected third caller — is never reached by a
catalogue sweep at all; its only caller in the tree is the shop-publish builder.
The extra fetch came from somewhere else entirely: `readProductTaxRate` is
called per product by `MasterProductSyncService` (`:270`), and
`PrestashopTaxRateResolver` fetches `products/{id}` **through its own code
path**, which the adapter's memo cannot see.

All that resolver reads off the product is `id_tax_rules_group`. It now accepts
the already-fetched product as an optional argument, and the adapter hands over
the one it just memoised. Omitting the argument keeps the previous behaviour
exactly — the resolver fetches for itself — so no other caller changes.

One supporting change: `PrestashopProduct` did not declare
`id_tax_rules_group`, though the resource carries it. It is declared now, marked
optional because PrestaShop omits it on a "No tax" product, which the resolver
already reads as a deliberate 0 rather than a gap.

# The two prerequisites for the bulk path, verified rather than assumed

Both are named in the module proposal as small blockers. Both are real, and
both were checked here rather than taken on trust.

**1. `filter[id]` is joined with a comma, and PrestaShop reads that as a RANGE.**

`prestashop-query.builder.ts:92` does `filters.ids.map(String).join(',')`, so
three ids go out as `filter[id]=[a,b,c]`. Measured against the live shop:

| Query | Rows returned |
|---|---:|
| `filter[id]=[100002,100005,100009]` | **1** |
| `filter[id]=[100002\|100005\|100009]` | **3** |

An OR list needs pipes. A bulk read that fetches N products by id therefore
cannot use this builder as it stands.

**2. No `sort` parameter is emitted at all.** The builder's own docblock lists
"sorting" among what it handles; no `sort` appears anywhere in the file. This
is the same gap ADR-048 records for `listExternalIds`, and it is what makes a
paged sweep unstable across ticks.

Neither is changed here. They are the first step of the bulk work, which is a
separate decision, and altering filter semantics without auditing every caller
is exactly the sort of change that wants a review rather than a measurement
session. They are recorded so the estimate for that work rests on something
checked.

# Correctness check — the fix is a request-count change, not a data change

A cache that returns the wrong thing is worse than the requests it saves, so the
data the sweep wrote after the fix was compared with the data it wrote before.

| | Before the fix | After the fix |
|---|---:|---:|
| `PERFBASE-` products with exactly 3 variants | — | **96** |
| products with any other variant count | — | **0** |
| variant rows written | 474 | 288 |
| rows with `taxRate` set | 0 | **0** |
| rows with `taxRateUnknownReason` set | 0 | **0** |
| rows with `taxRateReadAt` set | 0 | **0** |

Every product came back with its three variants, each carrying its EAN and its
price. No product acquired or lost a variant.

The tax columns are the ones the preload could plausibly have disturbed, since
the resolver now reads `id_tax_rules_group` off a product it did not fetch
itself. They are **byte-identical before and after** — and the reason is worth
recording: the PrestaShop webservice does not return `id_tax_rules_group` at all
for these products (verified directly against the live shop), so the resolver's
own fetch was already getting nothing. Handing it the memoised product changes
which request the field is absent from, not the answer.

That the rate is unset at all is a pre-existing condition of this catalogue,
present identically before the change, and is not something this work caused or
claims to fix.
