## Method

- Median of runs 2-4 of four runs. Run 1 is discarded: on a cold run the identifier mapping
  does not exist yet, so the sweep takes the create branch and reads more.
- `attempts_delta` checked after every run. Zero retries in every reported run.
- Contamination verified against each run's OWN window from `sync_jobs.updatedAt`, not the
  harness's 90-minute `createdAt` window (see *Harness corrections*).
- Figures labelled **measured**, **derived** (arithmetic on a measured window) or
  **extrapolated** (a full-cycle figure reached from one tick).

### CORRECTION - an earlier reading of this in the same campaign was wrong

An earlier draft of this report treated the 401s as cost that `results-A` had wrongly
counted, and concluded the baseline's "productive" cost was only ~6.00 per SKU. **The
control run disproves that**, and the correction is recorded rather than quietly edited.

The control (pre-epic code, permissions GRANTED, every response 200) still issues
**98 `product_options` + 98 `product_option_values` per 100 products**. On that code the
resolver is rebuilt per adapter instance and the adapter is built per product, so those
reads are made about once per product **whether they succeed or fail**. They are real
work, and `results-A`'s 7.96 is a real 7.96.

What actually changed is subtler and more interesting:

| | reads issued per 100 products | status |
|---|---:|---|
| baseline / control code | ~196 | 401 on the stand as found; 200 once permitted - the COUNT is the same either way |
| epic code, permission present | **0** (2 per process per 24 h) | cached process-wide by the hoisted factory |
| epic code, permission absent | **996** | never cached, so retried per product |

So the epic's process-scoped resolver cache is a very large win when the read succeeds
(196 -> ~0) and a **5x loss when it fails permanently** (196 -> 996). The hoist and the
`cache.set`-only-on-success are the same decision seen from two sides.

That makes the honest per-SKU comparison this:

### Why one missing permission costs two requests per SKU forever

`PrestashopAttributeResolver.getOptionValueMap` writes `this.cache.set(...)` only after
both reads return, so a throw caches nothing and the next product re-reads. Its caller
`PrestashopProductMasterAdapter.buildOptionValueResolver` catches and warns - "a transient
options failure must not break variant sync". The assumption is *transient*; a missing
permission is permanent, so the cost recurs per product indefinitely. Observable but never
aggregated: **1134** identical warnings in one 40-minute window, each naming the URL.

The exception is `PrestashopAuthenticationException`, the class ADR-008 routes to the
auth-failure classifier to flip a connection to `needs_reauth`. It is caught before it gets
there, so the connection stayed `active` throughout. That is defensible - a per-resource
permission gap is not an expired credential, and flipping would stop all syncing - but it
means a genuine 401 on this path reaches no operator-facing state.

**The epic already shipped the correct pattern next door.** Its own new
`prestashop-pack.resolver.ts` (#2598) catches, and caches a NEGATIVE result under a
separate `UNRESOLVED_CACHE_TTL_MS` of 60 s, so a failure costs one read per minute per
connection rather than one per product. `prestashop-attribute.resolver.ts` and
`prestashop-feature.resolver.ts` are both still on the old shape. Pre-existing defect,
reported because it dominates the measurement the epic is judged by, and because the fix
now has an in-tree precedent.

## The throughput headline needs two changes; one shipped as a default

The epic body: "With the correct cap raised: ~277 req/min and a p95 ratio of 0.995 ...
Applied to the catalogue: ~2.4 h instead of 26.5 h."

Read from the branch and from the database:

| | |
|---|---|
| `prestashop-plugin.ts:84` | `defaultRateLimit: { requestsPerMinute: 60, maxConcurrent: 4 }`, and its own comment calls these "Placeholder values pending the reporter's actual abuse-notice text (see #1810's own open question)" |
| connection `config->>'rateLimit'` | `(none)` |
| worker boot, lane caps in force | `realtime=4/2 bulk=12/8 fiscal=2/1 fan-out=8/4` |

**Measured, not argued:** all three set-1 runs sat flat at 60-61 requests/minute for
17 minutes each, with the epic's raised `bulk=12/8` cap in force and five batch children
genuinely running concurrently. Raising the lane cap changed how many OL jobs run at
once. It did not change how many requests per minute reached the shop, because the
limiter did.

The epic's body already says the connection limit alone achieved almost nothing
(50 -> 63 req/min) and that the lane cap was the real ceiling. Both statements are true
and they concern DIFFERENT ceilings; 277 req/min needed both raised. Only the lane cap
shipped as a default, so **an operator who deploys this epic and changes nothing gets
the request-count reduction in full and none of the throughput headline.**

That does not diminish the request-count result, which is independent of the limiter -
fewer requests through the same 60/min pipe is still a shorter cycle, and set 2 shows the
sweep dropping below the ceiling entirely. It does mean "~2.4 h instead of 26.5 h" must
be quoted with the configuration it requires.

## The Redis rate limiter degraded 85 times, and pacing held anyway

Worker warnings in one 40-minute window (read with an epoch `--since`; a bare `--since`
is interpreted in the DAEMON's local time and this container's clock runs behind the host):

| count | warning |
|---:|---|
| 1134 | `Failed to resolve PrestaShop option values ... Invalid API key for .../product_options` |
| 47 | Redis rate-limiter call `claimConcurrency` timed out after 1000ms |
| 32 | Redis rate-limiter call `checkPace` timed out after 1000ms |
| 6 | Redis rate-limiter call `release` timed out after 1000ms |

Not Redis: `redis-cli --latency` reports 0 ms, and both limiter keys are tiny STRINGs.
`DBSIZE` is 37 590 but 37 500+ of those are `jobdedup:*` on ADR-049's 7-day TTL
(30 431 for master sweeps alone), and a per-connection string key is unaffected by them.
The likely cause is the worker's own event loop: five concurrent batch children each
hydrate and JSON-parse a `display=full` page (~1.33 MB), and a blocked loop cannot
process a Redis reply inside the 1000 ms budget. That is a consequence of #2594's raised
`bulk` cap, so it belongs to #2644 bound 4.

**What saved it is by design.** `RedisRateLimiterAdapter` fails DEGRADED, not open: on a
Redis error it delegates the call to a per-process insurance limiter instead of admitting
unconditionally, and tracks the delegated call in its own counters so an operator's panel
does not read 0 in-flight during the episode. That is why the observed rate stayed flat
at 60-61/min through 85 timeouts.

**Caveat that follows, and this run could not test it:** the insurance limiter is PER
PROCESS. With N worker replicas a degraded episode means pacing is enforced per process
rather than across the fleet, so shop-side rate during degradation can approach N x the
declared limit. This run used ONE replica.

### Two things the cold run shows that the warm runs hide

**A cache stampede, new at this concurrency.** Run 1 carries 8 `configurations` and 8
`currencies` - one per concurrent child, and `bulk` perScope is 8. `results-B` reports
both at 0.00 after the etap-0 factory hoist, and they are back.

Note the attribution, because `results-A` got it wrong and it is easy to repeat: the
`configurations` read here is the PACK resolver's shop-wide `PS_PACK_STOCK_TYPE` lookup
(`PrestashopInventoryMasterAdapter.resolveShopPackStockType`), not the old adapter-build
pair. `currencies/<id>` is the shop-currency resolver's.

Cause, in code, and it is two independent axes rather than one:

| resolver | negative caching | in-flight de-duplication |
|---|---|---|
| `productResourceCache` (product memo) | n/a | **yes** - memoizes the `Promise` |
| `PrestashopPackResolver` (#2598, new in this epic) | **yes** - separate 60 s TTL for an unresolved answer | no - `readCached` stores the resolved **value** |
| `PrestashopShopCurrencyResolver` | partial | no - stores the **value** |
| `PrestashopAttributeResolver` | **no** - caches only on success | no - stores the **value** |

So the epic's own new resolver fixed the negative-caching axis and left the
de-duplication axis alone; only the product memo has the latter. At perScope 1 the
difference was invisible, because one child ever ran. At 8 it is eight simultaneous
identical requests per cold start, per shop-level resolver.

It is bounded - once per resolver per TTL (pack 10 min, currency 1 h, attribute 24 h),
not per product - and the warm runs show zero. But it is a cost #2594's cap raise
created, and it is the same latent weakness that made the missing permission cost 996
requests a tick rather than 2.

**The sweep has crossed from job-bound to rate-limit-bound.** 100 requests in 107 s is
~56/min against the declared 60. `results-A` measured this same sweep at ~22 req/min and
said explicitly "This sweep is not rate-limited - it is job-bound". That was true at 3
requests per position and 2-way concurrency; it is no longer true. It is why a 4x
concurrency raise bought only 1.52x: 100 requests cannot clear a 60/min limiter in under
100 s, and the measurement is 107 s.

Taken with set 1's catalogue sweep sitting flat at 60-61/min, **the same placeholder
`requestsPerMinute: 60` is now the binding constraint on both sweeps.** After this epic
the next real throughput gain on PrestaShop is a rate-limit decision - #1810's open
question about the reporter's actual abuse-notice text - not a concurrency decision.
That is worth stating because the epic's body frames the remaining bottleneck as
OpenLinker's own concurrency policy.

## A2 - does the shop slow down, measured with the fixed probe

**This is the first store-impact figure in this harness's history that can claim the
shop served correct pages.** The probe used for `results-A` and `results-B` never
checked the HTTP status code, so a fast error under load counted as a fast sample. It
now records `%{http_code}`, admits only 2xx into the percentiles, and exits non-zero if
a window recorded any error; `run-a2.sh` refuses to compute a ratio over such a window.

| phase | samples | median | p95 | errors | malformed |
|---|---:|---:|---:|---:|---:|
| idle 1 | 211 | 0.047 s | 0.057 s | **0** | 0 |
| under sweep | 216 | 0.047 s | 0.057 s | **0** | 0 |
| idle 2 | 217 | 0.045 s | 0.051 s | **0** | 0 |

    p95_idle_mean = 0.0539 s
    p95_under_sweep = 0.0568 s
    RATIO_B_over_A = 1.053

Measured. **The shop is 5.3% slower at p95 under a full catalogue sweep.**

### This corrects the epic body's flagship number, and in a specific way

The body reports **0.989** ("p95 under a full catalogue sweep is 0.989x idle. The shop
does not slow down") and **0.995** at raised tempo. Both are BELOW 1.0 - they assert the
shop answered *faster* while being swept. That is not a plausible physical result, and it
is exactly the artefact the unchecked probe produces: errors served fast, counted as fast
samples, pulling the percentile down.

The corrected direction is up, not down. The magnitude is still small, so the epic's
practical conclusion - a catalogue sweep does not meaningfully hurt the storefront -
survives. What does not survive is the specific claim that the shop "does not move",
and the sub-1.0 figures should not be quoted again.

### Deviations in this A2 run, stated

| deviation | why |
|---|---|
| `SWEEP_PAGE_LIMIT=2000` (default 500) | at the default the sweep covers 500 products in ~46 s and would leave most of a phase idle, pulling the ratio toward 1.0 for a reason that has nothing to do with the shop. 2000 products spans the phase. |
| `PHASE_SECS=120` (default 180) | matched to the sweep's duration at that budget, so phase B is loaded throughout. |
| `run-a2.sh` in-flight query fixed | it counted `master.product.syncByExternalId`, retired by #2593/#2594, so it read 0 forever and phase B aborted as "not loaded" on healthy code. |

The `INFLIGHT_MIN` default of 10 was NOT lowered: at `pageLimit=2000` the sweep enqueues
20 batch children, so the shipped threshold is exceeded honestly rather than relaxed.

### Two things worth reporting that a request count alone would hide

**Every unpin 404s.** All eight `DELETE /api/specific_prices/<id>` return 404, and
`ps_specific_price` holds zero rows afterwards - PrestaShop has already consumed the
cart-scoped rows by the time `cleanupPinnedPrices` runs. The deletion is best-effort and
the 404 is swallowed, so nothing breaks, but on a shop whose module lacks `line_prices`
eight of twenty-seven requests per order are guaranteed waste. On module 1.8.0 the
`line_prices` path removes them anyway, so this matters only for shops on an older module.

**All four A4 orders in this harness's history are priced at ZERO, and it is not the
epic's doing.** Orders 13 and 14 (this run, epic code, module 1.8.0) carry
`total_paid = 0`, every line `unit_price_tax_excl = 0`, and `current_state = 8`
(Payment error). So do orders **11 and 12 from the previous campaign** (etap-0 code,
module 1.2.0). Evidence gathered:

| fact | value |
|---|---|
| OpenLinker's own snapshot | `price: 149` per item, `total = 1192.00 PLN` - correct |
| pins POSTed | 8, all `201 Created` |
| `ps_product_shop.price` for all 10 000 PERFBASE products | `149.000000` |
| `ps_product_attribute.price` | `0.000000` (a combination delta, which is correct) |
| order line as written | `product_attribute_id = 0`, `original_product_price = 0.000000` |

OpenLinker holds the right prices and the pins are accepted; the value is lost inside
PrestaShop's own cart-to-order pricing for these synthetic products. **Cause not
established, and deliberately not chased here** - A4 measures what OpenLinker sends, and
that count is unaffected.

It is reported because it changes how every A4 figure in this harness should be read,
including `results-B`'s: the request counts are valid, and the orders they produced were
not correct orders. Anyone using A4 as evidence that the order path WORKS needs a
stand whose products price properly - which the previous campaign's own PERFBASE
catalogue did not provide either.

- **AC10** - a before/after comparison: **met** by this report together with `results-A`
  and `results-B`.

The three of them are met **without a PHP module** for the catalogue path. The one place a
shop-side change did pay was the order path, where the module's `line_prices` feature took
an eight-line order from 27 requests to 7 - and that is a conditional field on a controller
that already existed, not the twelve endpoints of the original design.

  pass/fail gate rather than a measurement, and the web container serves a baked-in bundle
  so the epic's `apps/web/dist` would have to be copied in first. Every other item in
  #2625 either produces a number the issue asks for or is a prerequisite of one.
- **A4's orders are priced at zero** on this stand, as they were in the previous campaign.
  The request counts are valid; the orders they produced are not correct orders.
- **Single replica throughout.** Lane caps bound one process.
