# Stage A — the six measurements that were missing (#2489)

Instrument: PrestaShop's own Apache access log, read via `docker logs --since`
(this image symlinks `access.log -> /dev/stdout`). Counted on the shop's side,
never by an OpenLinker-side counter. The container healthcheck (a loopback
`GET /` every ~30 s) and all non-`/api/` traffic are filtered out.

Catalogue under test: **10 000 products / 30 000 combinations**, all tagged
`PERFBASE-`.

## A1a — cost per SKU, catalogue sweep

Method: sweep cursor cleared, queue purged, `master.product.syncAll` enqueued at
the default budget (100 children), drained to zero, window sliced from the
shop's access log on its own Apache timestamps. Three runs; run 1 is the cold
run and is discarded. **Median of runs 2 and 3.**

The scheduler was taken out of the picture for the whole campaign: a second
worker container was started carrying `OL_WORKER_ROLE=jobs` only, so no cron
tick could enqueue work into a measured window. `attempts_delta = 0` on every
run, so no run was polluted by retries.

| Run | Requests | Products | Per SKU |
|---|---:|---:|---:|
| 1 (cold, discarded) | 805 | 100 | 8.05 |
| 2 | 796 | 100 | 7.96 |
| 3 | 796 | 100 | 7.96 |
| **median (2, 3)** | **796** | **100** | **7.96** |

Runs 2 and 3 are byte-identical in shape, which is what a deterministic code
path looks like.

### Where the 7.96 goes

| Request | Count per 100 products | Per SKU |
|---|---:|---:|
| `GET /api/products/<id>` | 300 | **3.00** |
| `GET /api/configurations` | 100 | 1.00 |
| `GET /api/currencies/<id>` | 100 | 1.00 |
| `GET /api/combinations` | 100 | 1.00 |
| `GET /api/product_options` | 98 | 0.98 |
| `GET /api/product_option_values` | 98 | 0.98 |
| `GET /api/products` (enumeration) | 1 per tick | 0.01 |

### The triple fetch, exactly

```
distinct_ids=100 total_fetches=300 mean=3.00
    100 ids fetched 3x
```

Every one of the 100 products was fetched exactly three times. Not "about
three" — three, for all of them, in both clean runs. The three call sites are
`getProduct` (`prestashop-product-master.adapter.ts:187`), `getProductVariants`
(`:395`) and `getProductCategories` (`:699`), each fetching the same resource.

### How much of this is waste

Two of the three product fetches are redundant, and the
`configurations` + `currencies` pair is re-read on every job to resolve a shop
currency that cannot change between two jobs a second apart.

**4 of 7.96 requests per SKU — 50.2% — are re-reads of something already known.**


## A1b — cycle time for the whole catalogue

**COMPUTED, not measured.** Measuring one full 10 000-SKU cycle at today's cost
takes over a day, which no session budget covers. It is computed from two
measured quantities and its inputs are shown so the arithmetic can be checked.

Measured inputs:

* **7.96 requests per SKU** (A1a, median of two clean runs)
* **50 requests/min** sustained, measured from the access log's own per-minute
  distribution across three runs (peak 55)
* one tick of 100 products took **977 s**, i.e. **6.14 products/min**

The connection declares no `config.rateLimit`, but the PrestaShop plugin
manifest declares `defaultRateLimit: { requestsPerMinute: 60, maxConcurrent: 4 }`
(`prestashop-plugin.ts:84`) and it is passed into the transport in
`createCapabilityAdapter`. The observed 50/min sitting just under that 60 is
the limiter, not a coincidence.

| | Value |
|---|---:|
| Requests for a 10 000-SKU cycle | 7.96 × 10 000 = **79 600** |
| At the measured 50 req/min | 1 592 min = **~26.5 h** |
| At the declared 60 req/min ceiling | 1 327 min = **~22.1 h** |
| Cross-check from products/min | 10 000 ÷ 6.14 = 1 629 min = **~27.1 h** |

The two independent routes agree within 2%.

**This corrects a claim from the first run.** That run reported "the limiter is
not the ceiling; ~50/min is latency times concurrency". The manifest default
applies, so the limiter *is* the ceiling. The conclusion it supported does not
change — the currency is cycle time, not shop load — but the mechanism does,
and the earlier statement was wrong.

## A6 — the denominator behind "+3.2"

**Answered, and it overturns the first run's number.**

The first run reported 3.2 `configurations` + `currencies` requests per product.
In a clean window it is:

| | Count | Per child job | Per product |
|---|---:|---:|---:|
| `GET /api/configurations` | 100 | 1.00 | 1.00 |
| `GET /api/currencies/<id>` | 100 | 1.00 | 1.00 |
| child jobs (`master.product.syncByExternalId`) | 100 | — | 1.00 |

One product spawns exactly one child job, so the two denominators coincide here
and the value is **+2 per adapter build, not +3.2**. The earlier 3.2 was an
artifact of a contaminated window in which several job types overlapped. The
working document's "+2 per child job" was right.


## A3 — inventory sweep cost

Same method as A1a, on `master.inventory.syncAll`. Three runs, all three
identical.

| Run | Requests | Stock positions | Per position | Elapsed |
|---|---:|---:|---:|---:|
| 1 (cold, discarded) | 300 | 100 | 3.00 | 700 s |
| 2 | 300 | 100 | 3.00 | 401 s |
| 3 | 300 | 100 | 3.00 | 406 s |
| **median (2, 3)** | **300** | **100** | **3.00** | **~404 s** |

### Where the 3.00 goes

| Request | Per position |
|---|---:|
| `GET /api/stock_availables` | 1.00 |
| `GET /api/configurations` | 1.00 |
| `GET /api/currencies/<id>` | 1.00 |

**Two of the three requests are the adapter-build pair — 66.7% of this sweep is
overhead**, a worse ratio than the catalogue sweep, because the useful work per
job is smaller.

### The `throwForAbsentStockRecords` probe, costed separately

`GET /api/products/<id>` appears **zero times** across all three runs. The
safety probe only fires when a product returns no stock rows at all, so on a
healthy catalogue it costs **nothing**; its cost is **1 request, on the
empty-stock path only**.

That is the number to weigh before removing it: the first run established that
the guard works (a product whose stock rows were deleted logged
`master_inventory_zero_stock_rows … NOT classified as a deletion` and staled
nothing), and it is not paid for in the steady state.

### This sweep is not rate-limited — it is job-bound

The catalogue sweep runs at ~50 req/min against a declared 60 ceiling. This one
runs at ~22 req/min, nowhere near the limit: 100 jobs in ~404 s is ~15 jobs/min
at 3 requests each. The constraint here is per-job overhead, not the shop.

## A4 — eight-line order

**NOT MEASURED. Reason: no supported path can dispatch a synthetic order.**

The attempt and why it failed, so the next person does not repeat it:

1. Every order on this stack has one line, so an eight-line order had to be
   built. One was synthesised (`make-8line-order.sh`) from eight real, already
   mapped `PERFBASE-` variants, reusing the customer of an order that already
   synced so the fixed cost would be identical and the difference purely
   per-line.
2. The only operator-facing dispatch route is
   `POST /orders/:id/destinations/:connectionId/retry`, which
   **re-enqueues the SOURCE-side `marketplace.order.sync` job**
   (`order-destination-retry.service.ts:95`). That job re-pulls the order from
   its source before dispatching, so the persisted snapshot is never
   authoritative — an eight-line snapshot is overwritten by whatever the
   marketplace returns.
3. Giving the synthetic order a source mapping therefore cannot help: it would
   dispatch the real one-line order under a different id.

Reaching this measurement needs a genuine eight-line purchase in the Allegro
sandbox, which is manual browser work.

### What is established instead

**Measured (one line, earlier run, order created in PrestaShop as order #10):**
one `POST /api/specific_prices` and one `DELETE /api/specific_prices/<id>`,
alongside one cart, one carrier read, one module `cartshipping`, one module
`importorder`, two VAT lookups and one country read.

**Derived from the source, not measured:** the per-line factor is 2 —
`pinLinePrices` runs an unconditional `for` loop over `order.items` creating one
specific price each
(`prestashop-order-processor-manager.adapter.ts:654`), and `cleanupPinnedPrices`
deletes them one at a time in a sequential `for` loop (`:816`).

So the shape is **k + 2n**, with k measured at ~9 for a one-line order and the
factor 2 read off the code. **The factor is not measured, and is labelled as
such.** An eight-line order would spend 16 requests on price pinning alone.


## A2 — does synchronisation slow the storefront down

Three phases of 180 s at 2 req/s over localhost, worker stopped for the idle
phases, catalogue sweep in flight for the loaded one. Lane caps and the
connection's rate limit at their defaults, because concurrency is what is under
test.

| Phase | Samples | median | p95 |
|---|---:|---:|---:|
| idle (1) | 320 | 0.035 s | 0.039 s |
| **sweep running** | 320 | 0.035 s | **0.038 s** |
| idle (2) | 320 | 0.034 s | 0.038 s |

**RATIO p95(load) / p95(idle) = 0.989.**

The storefront was, if anything, marginally faster under load — i.e. the
difference is inside the noise. The absolute numbers are a property of this
machine and are comparable with nothing; the ratio is the result.

**This contradicts the issue's premise.** #2489 opens with synchronisation
putting *"significant load on PrestaShop"* which *"can slow down the store"*.
At the measured rate the store does not notice. What costs is the **elapsed
time of a full cycle** (A1b), and that is a consequence of asking for one
product at a time.

# Stage A — what the six measurements say

| | Measured | Basis |
|---|---|---|
| Requests per SKU, catalogue | **7.96** | median of 2 clean runs |
| of which redundant | **4.00 (50.2%)** | 2 duplicate product fetches + the adapter-build pair |
| `GET /api/products/<id>` per product | **3.00 exactly** | 100/100 ids, both runs |
| Adapter-build overhead | **+2 per child job** | corrects the first run's 3.2 |
| Requests per stock position | **3.00** | 3 identical runs |
| of which redundant | **2.00 (66.7%)** | the same adapter-build pair |
| Empty-stock safety probe | **1 request, empty-stock path only** | 0 observed on a healthy catalogue |
| Storefront p95 under load ÷ idle | **0.989** | 3 phases, 960 samples |
| Queue growth, unattended | **~145 jobs/h** | 431 rows over ~3 h |
| Full 10 000-SKU cycle | **~26.5 h** | COMPUTED from 7.96/SKU and 50 req/min |
| Requests per 1-line order | ~9 + 2 per line | k measured, factor 2 read from source |
| Requests per 8-line order | **not measured** | no supported path dispatches a synthetic order |

**Two claims from the first run are corrected here:** the adapter-build overhead
is +2 per job, not +3.2 (contaminated window), and the ~50 req/min ceiling is
the manifest's declared rate limit, not latency times concurrency. Both
corrections were found by re-measuring in a clean window and are stated rather
than smoothed over.

## Method notes

* **The scheduler was removed from the measurement, not worked around.** A
  second worker container carrying `OL_WORKER_ROLE=jobs` replaced the default
  all-roles worker for the campaign, so no cron tick could enqueue into a
  measured window. `attempts_delta = 0` on all six sweep runs.
* **The log window was wrong at first and the numbers were rebuilt, not
  patched.** `docker logs --since` was handed a UTC timestamp while the daemon
  reads a bare timestamp as its own local time, so the first capture covered
  the whole night. Runs are now sliced on the Apache timestamps the log itself
  carries (`slice-window.py`), and the drivers pass epoch seconds.
* **The worker's debug logging was left on** — its env cannot be changed on a
  running container and the compose project directory this stack came from no
  longer exists. It does not affect the request counts, and the timings are
  bounded by the declared rate limit well above OpenLinker's own work.

# A4 — eight-line order, MEASURED (addendum, taken after the stage-A commit)

The earlier section reports A4 as not measured because the only operator-facing
dispatch route re-pulls the order from its source, so a synthesised snapshot is
never authoritative. **That is still true — the way around it was to make a real
order at a real source rather than to fake one.**

WooCommerce is an `OrderSource` on this stack. Eight products were created
there, the eight WooCommerce product ids were mapped onto eight internal
products that already carry PrestaShop mappings, and a genuine eight-line order
was placed in WooCommerce. OpenLinker ingested it through its ordinary poll and
dispatched it to PrestaShop, which created order **#11**
(`syncStatus: synced`). Measured on **unpatched** code, i.e. baseline A.

| Request | Count |
|---|---:|
| `POST /api/specific_prices` | **8** |
| `DELETE /api/specific_prices/<id>` | **8** |
| `GET /api/addresses` | 2 |
| `POST /index.php` [module `importorder`] | 1 |
| `POST /index.php` [module `cartshipping`] | 1 |
| `POST /api/carts` | 1 |
| `POST /api/addresses` | 1 |
| `GET /api/orders` | 1 |
| `GET /api/customers` | 1 |
| `GET /api/currencies/<id>` | 1 |
| `GET /api/currencies` | 1 |
| `GET /api/countries` | 1 |
| `GET /api/configurations` | 1 |
| `GET /api/carriers` | 1 |
| **total** | **29** |

### The shape, now measured rather than derived

**`k + 2n`, with k = 13 and the factor = 2. Both measured.**

At eight lines: 13 + 2×8 = 29, which is what the shop logged. The factor of 2
matches exactly what the source predicted (`pinLinePrices` creates one specific
price per line, `cleanupPinnedPrices` deletes them one at a time), so the code
reading is now confirmed rather than assumed.

**16 of the 29 requests — 55% — are pinning a price and then unpinning it.**
On a one-line order that is 2 of ~15; on an eight-line order it is the majority
of the whole order.

### Three obstacles worth recording, because they are the demo stack's, not OL's

1. **The WooCommerce connection could not authenticate over plain HTTP.** OL's
   WooCommerce client sends Basic auth only
   (`woocommerce-http-client.ts:282`), and WooCommerce refuses Basic over
   cleartext. A TLS reverse proxy in front of the shop plus a worker with
   certificate verification disabled was needed. **On a real deployment this is
   a non-issue** — the site is HTTPS — but it means the WooCommerce path cannot
   be exercised on a plain-HTTP local stack at all.
2. **PrestaShop rejected the buyer's first name** with
   `Property Customer->firstname is not valid` because the test data used "A4".
   PrestaShop's name validator disallows digits.
3. **A failed first attempt left a customer mapping conflict** — PrestaShop
   customer 13 was created and mapped, then the retry resolved a different
   internal customer (the name had changed) and refused to remap. The conflict
   guard behaved correctly; the row had to be cleared by hand.
