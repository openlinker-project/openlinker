**Code under measurement:** `epic/2590-prestashop-no-module` at `0572380e0`, which is

## 1. Live product deletion, catalogue path (#2647) - MEASURED, works

The single most important untested path in the epic. Until this hook existed, the only
route from a deletion to a paused offer was the `master.product.reconcile` audit, whose
full cycle at 100 000 products `results-D` measured at **41.7 days** - during which the
deleted product's offers keep selling (#1689).

Module upgraded 1.8.0 -> 1.10.0 on the stand; `actionProductDelete` confirmed registered in
`ps_hook_module`. Product `209498` (`PERFBASE-99496`), mapped, 3 variants, deleted through
`Product::delete()`.

| hop | evidence | wall clock |
|---|---|---|
| module wrote the outbox row | `ps_openlinker_webhook_outbox` id 7, `product.deleted`, `external_id=209498`, `pending` | synchronous with the delete (313 ms total) |
| delivery | `7 processed, 7 delivered, 0 failed`; row `delivered` | one cron pass, 210 ms |
| OpenLinker gate | `webhook_deliveries` -> `job_enqueued` | - |
| job | `master.product.syncByExternalId` -> `succeeded`, `outcome=business_failure`, `outcomeReason=master_deleted` | ~32 s after delivery |
| effect | `product_variants`: **3 of 3 `isStale`**; `MasterProductSyncService` logged `markedStale=3` | - |

**Detection latency is now bounded by the shop's cron cadence, not by the audit cycle.**
On a one-minute cron that is roughly 1.5 minutes against 41.7 days. The outbox write itself
is synchronous with the delete, so nothing is lost if the cron is late.

### The `parent::delete()` false path - exercised, and it is safe

`Product::delete()` returned **false** on this deletion, which is the path #2647 shipped
unverified. What actually happened: the product was gone from `ps_product` and
`ps_product_shop` (both 0 rows), three orphaned `ps_product_attribute` rows remained, and
the false came from cleanup after the hook.

Checked in the live container why that is safe rather than lucky: `classes/Product.php:1276-1282`
fires `Hook::exec('actionProductDelete', ...)` **after** `parent::delete()` and after the
`hasMultishopEntries()` early return. The hook cannot fire for a product that is still
there, so a false deletion event is not reachable on this path. The module correctly does
not gate on the return value - had it done so, this real deletion would have been silent.

## 2. Live deletion through the batched inventory sweep (#2648) - MEASURED, works

The risk this closes: a product missing from a page of 100 being swallowed by the batch.

Product `100002` (`PERFBASE-00001`) deleted in the shop, and its outbox row **forced to
`delivered` without sending**, so only the sweep could notice it.

| observation | result |
|---|---|
| batch child | `master.inventory.syncBatch` x1, `100 synced, 0 failed`, `prefetched=true` |
| adapter | `master_inventory_master_deleted psProductId=100002 - product absent at the master` |
| products context | `markedStale=3`, `variantPruneSkipped=false` |
| `inventory_items` | **3 of 3 `isStale`** |
| `product_variants` | **3 of 3 `isStale`** |
| the other 99 | synced normally |

The prefetch seeds an empty bucket for every id it asked about, so a deleted product is a
cache *hit* with zero rows rather than a miss, and the per-item deletion path runs
unchanged. #1689 is intact through the batch.

## 5. Store impact - the previous finding reproduces, and now has a mechanism

`results-D` reported a p95 ratio of **1.403** at 100 000 products and read it as a property
of catalogue size. Measured again here, and the fuller picture is that **cursor depth, not
catalogue size, is what the shop feels.**

Idle baseline, two windows: p95 **0.054 s** and **0.055 s** (mean 0.0545 s), zero errors.

| phase | cursor | budget | samples | p95 | ratio | errors |
|---|---|---:|---:|---:|---:|---:|
| under sweep | offset 0 | 500 | 109 | 0.053 s | **0.97** | 0 |
| under sweep | offset 0 | 2000 | 163 / 216 | 0.053 s | **0.97** | 0 |
| under sweep | **offset 98 000** | 2000 | 211 | **0.076 s** | **1.39** | 0 |

Every window verified to have had the sweep genuinely in flight: 20 batch children queued
or running mid-probe, tick elapsed 156 s and 160 s.

**A first reading of this measurement was wrong and is corrected here rather than quietly
dropped.** The offset-0 windows show no impact at all, and had the run stopped there the
report would have said the store is unaffected at budget 2000. It is not: the same budget
at a deep cursor costs +39%, which is `results-D`'s 1.403 within noise. `results-D` used
`SWEEP_PAGE_LIMIT=2000` against an advanced cursor; this run reproduces it and shows the
cheap end for contrast.

The mechanism `results-D` identified stands: request COUNT per tick is flat, but a
`products?display=full&limit=100` read costs 254 ms at offset 0 against 386 ms at offset
99 000, and the storefront shares MySQL with those reads.

**What this means for an operator:** impact is not constant across a cycle. A tick early in
a pass is free; a tick deep in one costs about 40% of p95. On this stand that is 76 ms
against 54 ms - a shop that still works - with zero errors in every window.

## 6. The calculator's model, checked against a measurement

#2653's page projects a run linearly from the measured per-tick cost. That linearity had
only ever been measured across catalogue *sizes* at a fixed budget, never across budgets.

| budget | predicted | measured |
|---:|---:|---:|
| 500 | 46 s | 46 s (calibration point) |
| 2000 | **184 s** | **156 s and 160 s** |

The model **over-predicts by about 16%**, which is the safe direction: an operator sizing
against a host process limit is told the run is longer than it will be. Not a defect.

The page states that it cannot predict where a shop breaks, and section 5 is why that
statement has to stay: the calculator models the tick, and the shop's own cost varies with
cursor depth, which the calculator does not model and does not claim to.

## What this run did NOT establish

- **A full replication cycle was never reached**, same as `results-D`. OpenLinker holds
  3 501 of 100 000 products. At 500 per 20 minutes a full pass is ~2.8 days.
- **No offer was mapped to the deleted products**, so the last hop of #1689 - quantity
  written to 0 on a marketplace - was not observed. Everything up to and including
  `isStale` was.
- **The module's PHPUnit suite still did not execute** - no `vendor/` in the tree.
- **The pre-epic control was not re-run.** `results-C`'s ratio stands; the catalogue read
  path has not changed since it was taken.
- **Probe A2 was not re-derived.** Its in-flight threshold of 10 is unreachable now that a
  tick is 5 children at the default budget; it is left as recorded in `results-C`.
- **Bounds 3, 5 and 7 of #2644 remain unexercised**, for the reasons that issue records.
- **Every figure is single-replica**, and the catalogue is synthetic - 3 variants, 9
  categories, 2 features, no bundles.
- **The cadence half of the settings was not exercised.** A budget change takes effect
  without a restart; a cadence change is reported by the API as applying at the next
  scheduler start, and that was not measured.
